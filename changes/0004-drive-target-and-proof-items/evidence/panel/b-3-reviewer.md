## Verdict
Accept both readings (`line` holds when any line satisfies the comparison; the value is JSON when it parses, else a string) as the safest reading; one tightening of R5's text, no park.

## Why
- Nothing fixes the semantics: intent.md lines 93-95 and the proposal's D5 (`docs/proposals/drive-target-and-proof.md` lines 66, 81) fix the shape only (`state: <file> <path> ==|contains|matches <value>`, `line` for a text file, `matches` a Python `re`). So it is a design guess, rightly flagged under the spec-template rule ("Guess made because the intent does not say"), for the panel to settle, not a departure from the intent.
- By REVIEW.md's bar neither reading breaks behaviour, leaks data or breaches a policy, so it is not Important. The only risk is a false pass when a drive writes the expected text itself, which is D7's named weakness (the adversarial reviewer's new angle, spec R15), not a product of either reading.
- "Any line" is the only reading under which the three verbs mean something on a text file: the grammar has no negation, and "every line equals `200`" or "every line matches" would make `==` and `matches` useless on a multi-line log, the usual text proof. A text proof that must be whole is a one-line file, which the same rule covers.
- JSON-when-it-parses is required by the one example the intent cites: the article's "the endpoint returns 200 with the new field" (p.28, intent line 24-25) is a number in a JSON state file, so `== 200` must equal the JSON number 200. A string-only reading would need the author to know the file's type at design time and would fail the article's case.
- The gap in R5 as written: "`==` compares the parsed values (so `200` equals the JSON number 200 and the text `200`)" is only true if the seen side of a `line` item goes through the same `parse_expected` (or `==` falls back to the string form); plan.md names `parse_expected(value)` for the expected side alone. Spec R5 asks for "one definition" and coding-standards rule 7 for explicit behaviour: the build applies the one parse to both sides of a `line` comparison, and R5 says so in one sentence. Inside files already in the plan (`artifacts.py`, `tests/test_proof.py`); no plan change.
- Nit, not a finding: on a failing `line` item every line fails, so "the first line that does not" is always the file's first line; the sentence can simply say the first line.
- Precedent: `checks.py:1521` (`RATCHET_PROOF_RE`) already reads a fixed-shape `## Proof` line by its first word and ignores prose; the item grammar follows that pattern, and the `plan-template` skill (R5, in the plan) must state both readings so the owner approving the plan at gate (b) (decision 2) reads the rule the gate will apply.
