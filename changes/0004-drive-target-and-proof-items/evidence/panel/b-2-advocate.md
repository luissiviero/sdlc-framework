## Verdict
Do not settle for naming the shortfall: subtract the re-check's overrun from the fix-at-(e) session cap through the same `limits.run_caps` subtraction this design already adds, so the job fits 260 without raising `timeout-minutes`.

## The case against
1. Naming the shortfall in a comment does not stop the failure. A job that runs past `timeout-minutes: 260` gets cancelled by GitHub. In `template/.github/workflows/sdlc-fix.yml` (lines 284-298) the park steps run only on `steps.setup.outcome == 'failure' || steps.phase.outcome == 'failure' || triage == 'park'`. A cancelled step's outcome is `cancelled`, not `failure`. So a fix round at (e) that hits the bound writes no gate record, gets no `sdlc:needs-human` label and no "what I need from you", and it sends no review request. That is a silent stall on the PR the owner is waiting on, and decisions 11, 29 and 31 say every stop is a park.
2. The intent asks for "no `timeout-minutes` it can avoid", and this overrun can be avoided. The design already makes `limits.run_caps` take minutes to subtract at a fix round whose gate phase is (e), and both readers (the runner's subprocess timeout and the gate's wall-clock check) already pass them. Subtracting another 30 minutes there, only on a fix round at (e) where R51's merge and re-check run in the same job, gives 45 + 150 + 55 + 10 = 260 of 260. The cap stays well above the design's own 30-minute floor, and no workflow file changes.
3. The choice the spec defends (leave it, since it is 290 today) carries a known defect into a change that rewrites this exact arithmetic. It also adds a stated, wrong figure to the template comment, which `sdlc_init.py` reads for `SDLC_JOB_TIMEOUT_MINUTES` beside the build-caps check (`build_caps_refusal`). That check passes the job as "holding the build caps" while the (e) round cannot finish inside it.
4. "Today's bug, not this change's" is weak here. The intent puts the fix round at (e) explicitly in scope ("says which of these it fixes and which it names"), and the fix uses the one mechanism the design builds.

What I would decide: extend R4's subtraction so that a fix round at (e) takes the re-check's minutes beyond the job's slack (30 by default, computed from the figures and not hard-coded) out of the session cap. Add a unit test that the (e) fix round's needed minutes stay within `SDLC_JOB_TIMEOUT_MINUTES`.

What would make me accept the obvious resolution: proof that a job cancelled at its timeout still parks, for example an `if: cancelled()` park path or a runner-side deadline that parks before 260. Or a recorded owner decision that a timeout at (e) is an accepted, visible failure mode.
