# Spec: security: authz: The runbook Go (cmd_go via _human_label_actor) accepts the
Change id: 0006. Status: proposed. Produced by: sdlc plugin 1.0.46, /sdlc-design prompt v1 (article p.14). Skills: coding-standards, security-baseline, ux-and-brand, data-conventions, definition-of-done (plugin 1.0.46); overrides: none; policy sources: none

## Requirements
- R1. A `sdlc:go` label applied by an account that is not the owner's performs nothing: no runbook runs, `status.yaml: runbook_authorized_by` stays `null`, no runbook record is written, the label stays on the pull request, and the command exits 0 with `performed: false` and a reason (decision 14: Go is the owner's per-incident act).
- R2. "The owner's account" is decision 34's one rule, `plugin/state/unpark.py is_owner_actor`: `sdlc.yaml: owner` when named, else the repository owner (the runner's `GITHUB_REPOSITORY_OWNER`, else the owner part of `--repo`); the comparison ignores case; a `[bot]`, the automation identity and an unknown owner fail closed. No second rule is written (decision 34, point 3: "One function ... decides it and fails closed").
- R3. The `sdlc.yaml` the rule reads is the owner's approved copy from the default branch, the one `cmd_go` already reads for the automation identity (`_approved_config`), never the pull request head's copy: a head that names the collaborator as `owner` changes nothing (decision 34, point 3; security-baseline rule 1, authorization checked on the server).
- R4. A label the owner's account applied still runs the runbook once, records the actor and removes the label, exactly as today (`cmd_go` after the actor check is unchanged).
- R5. The refusal's reason names the label and the actor and says the owner's account is required and the label was left where it is (ux-and-brand rule 4: what happened and what the person can do next; the existing "not by a person" wording stays for the bot and automation branch, which is a different reason).
- R6. The existing reasons for an unreadable label event, a missing `labeled` event, a bot or automation actor, an unreadable default-branch copy and a route that did not ask for Go keep their texts and their order; the owner check comes after the bot and automation check and before the proposal is judged.
- R7. A test that reproduces the weakness (a collaborator's label makes the runbook run) is written first and fails on the code the review scanned; after the fix it passes; no existing test is skipped, weakened or deleted (coding-standards rule 4; the intent's constraints).
- R8. No new dependency: `is_owner_actor` is already in the plugin (security-baseline rule 6; coding-standards rule 5).
- R9. No credential appears in the change, its tests or its evidence (security-baseline rule 3; the intent's constraints).
- R10. Build, test and lint targets of `sdlc.yaml` stay green (coding-standards rule 8; definition-of-done, build).
- Policies that do not apply: data-conventions (no new stored field, schema, migration, event or pipeline: `runbook_authorized_by` already records the owner's login, and the refused actor's login appears in the run's output only, as the bot branch's reason does today; a GitHub login is an account identifier, classified internal); ux-and-brand beyond rule 4 (no screen; the output is the CLI's JSON in the workflow log). Risk-list items `data migrations`, `money movement` and `production config` are not touched; `auth` is, declared under Flagged concerns.

## Design
- One file of the plugin changes, `plugin/detect/cli.py`: `_human_label_actor` gains one check between the bot/automation branch and the return, `is_owner_actor(actor, config, None, repo)`; `config` is the approved copy `cmd_go` already passes in, `repo` the `--repo` argument, and the environment is the process's own (the runner's `GITHUB_REPOSITORY_OWNER` in the Go step, the shell's by hand). On False it returns `(None, reason)` like the other refusals. `is_owner_actor` is imported at the module top beside the module's other plugin imports (`gate.policy`, `state.gitops`), as `plugin/ci/run_phase.py`, `merge_step.py` and `comment_dispatch.py` import it; `state.unpark` imports nothing from `detect`, so there is no cycle.
- `cmd_go` is unchanged: a `(None, reason)` from `_human_label_actor` already emits `performed: false` with the reason and returns 0 without judging the proposal, running anything, writing `status.yaml` or touching labels (the label stays, the rule of the un-park labels in `plugin/state/unpark.py`: "rejected and left on the PR"). The owner removes the collaborator's label and applies it again; `label_actor` reads the last `labeled` event, so the owner's own application is the one judged.
- The runbook workflow (`template/.github/workflows/sdlc-runbook.yml`) is unchanged: its `if:` keeps the coarse `[bot]` check decision 34 allows, and its comment "detect/cli.py go checks the actor again" stays true. The Go step holds the runbook secrets, so the check sits in that step, on the server (security-baseline rule 1), not in a workflow expression a head can influence.
- Error behaviour: the same JSON shape as every other refusal (`change_id`, `performed: false`, `reason`), exit 0, so the job stays green and the label stays for the owner's own application (as the bot refusal does).
- Interfaces, data shapes, the un-park labels, the dismissal's member rule (`_closing_reason`, a comment that closes an incident is still any member's) and the other commands stay as they are.

## Flagged concerns
- decided (decision 35): risk item 'auth': the change adds the owner check to the runbook Go's authorization, the one gate before a running-system action runs with the runbook secrets; the close-look banner shows it and the owner's merge accepts it (at the deploy gate, the owner's approving review).
- decided (by panel #1): The one-line `monkeypatch.setenv("GITHUB_REPOSITORY_OWNER", "the-owner")` in the `rollback_incident` fixture goes into the `fix(0006): reproducing test` commit before `lock-tests`, with no test body or assertion changed; the step-1 log must show every existing `rollback_incident` test passing with the fixture line alone, before the fix; plan.md's Risks line must say `owner_login` is the only direct reader and name `is_owner_actor` and its callers (run_phase, merge_step, comment_dispatch, review_request, release/cli, pr/digest, state/unpark) as the indirect ones. — The existing Go tests in `tests/test_detect_cli.py` authorize with the actor `the-owner` on the repository `o/r` and no owner named, so with the fix that actor is not the owner and five of them (the runbook runs, the App refusal's re-run, the route that asked for Go, the head-listed automation identity, the malformed head copy) would fail. The reproducing-test commit, before the test-file lock, must also make the fixture's owner explicit (the `rollback_incident` fixture sets `GITHUB_REPOSITORY_OWNER` to `the-owner` through `monkeypatch`, the pattern `tests/conftest.py` prescribes for a runner variable a test needs); the tests' bodies and assertions are untouched and they pass before the fix as they do today. The intent says "no pre-existing test is edited to make the fix pass": the fixture edit changes no test's assertion and weakens nothing (coding-standards rule 4), but it is an edit under `tests/` that the fix needs, so it is declared here rather than made silently.
- [x] What happens to a label a non-owner applied: decided the label stays on the pull request and the owner applies their own, per coding-standards rule 2 (match the surrounding code: the bot branch of `_human_label_actor` and the un-park labels of `plugin/state/unpark.py` both leave a rejected label where it is).
