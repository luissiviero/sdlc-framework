## 29. In CI a red target starts the next fix round by itself (amends 11 and PROGRESS choice 154)

*Reference: steps 16, 19, 28, 30 · NEW (2026-10-13), from study entry T10 (crosswalk rows test-loop and test-verify), brought forward as ROADMAP R10 (`docs/proposals/test-loop-closes-in-ci.md`); proposed, for the owner's review together with decision 28*

- A red target found by the runner parks the change, and the owner's act is the round (what the framework does today, choice 154 of 0.3.2): a "Request changes" review (decision 22), a `workflow_dispatch` of `sdlc-fix.yml` or an un-park label starts the next fix round; the article's run, fix and re-run loop needs the owner between rounds.
- The runner dispatches the next fix round itself: when its commands step finds a red target, it dispatches a fix round explicitly (events caused by the workflow token start no run that proceeds by itself), with the failing logs as the round's constraint; the iteration count goes up by one, the runner runs the targets again after the round, and the change parks only at the iteration cap (`gate.max_iterations`, 3, or `max_iterations_non_routine`, 2) with its partial evidence, as any limit does (decision 11). In CI the verifier's report names the record it read, by phase and commit, and says that the final tree's result is the runner's, shown in the check run `sdlc/d`. The runner's single run of build, test and lint after the session, outside the sandbox, stays. **[RECOMMENDED]**
- The targets run inside the sandbox again, so the session sees a red target itself: rejected in choices 133 and 154, since the sandbox denies a nested `.env` to every process the session starts, and renaming fixtures or narrowing the deny rule was not chosen.
- A helper that runs the targets for the session outside the sandbox while it works: a hole in the sandbox that the session controls.

**To settle with the alternative (target-design T10, "Open"):**

| Question | Answers | Recommended, and why |
|---|---|---|
| Whether the automatic rounds share the iteration cap with the owner's "Request changes" rounds | One counter, as today (`plugin/gate/limits.py`: "fix iterations per change, one counter across the phases"); a count of their own | One counter: the cap bounds the cost of a change whatever starts a round, and a second count would need its own setting and its own reset |
| Whether a target that cannot be fixed from the session (a missing target, a timeout, an infrastructure failure) starts a round | Every red target starts a round; these park at once | A missing target and an infrastructure failure park at once: a missing target is an `sdlc.yaml` gap, a guardrail file no run may edit, and an infrastructure failure is a hard park under decision 21. A timeout starts a round, since the change under test may be what hangs, and the cap still bounds it |
| The verifier's exact wording, and whether the PR's summary also says which run its evidence came from | Settled in the design; settled here | Settled in the design, from T10's sentence above; the PR summary names the run, in the shape R11's "the run on every record" gives every record |

**Accepted:** pending the owner's review

**Why the recommendation:** The article's loop is run, fix and re-run until the check passes, "so what reaches the engineer has already passed it" (p.27). Since plugin 0.3.2 no project target runs inside the CI session: the runner runs them once after the session, outside the sandbox, and parks the change on a red target (`plugin/gate/gate.py`, `run_deferred_commands`), so each round waits for the owner (choice 154, `docs/progress/session-18.md`). The owner chose the blend on the crosswalk row test-loop on 2026-10-03: keep the runner's single run, and have a red target start the next round by itself, so that what reaches the owner has passed the check or used up its rounds; and on the row test-verify: keep the split, and have the verifier say which tree it read, so nobody reading `verifier.md` later takes the earlier tree's results for the final ones (`docs/reviews/2026-09-28-playbook-vs-framework/target-design.md`, T10). The two sandbox alternatives were considered and not chosen there. Decision 11's "park, never page" stands: a limit hit still parks and nobody is notified; only the park on the first red target goes.

**What it amends:** decision 11 (as amended by 21), since a red target found by the runner no longer parks at once; PROGRESS choice 154 (`docs/progress/session-18.md`), whose "the owner's `/sdlc-fix` is the round" no longer holds in CI. Choice 154's split of the run (the runner runs the targets, the verifier reads) stays.

**Order:** accepted by the owner on 2026-10-09 "to run before 1.0.0", after R6 and before the carried gaps (ROADMAP R10). Since then 1.0.0 has become the item-11 PR alone, and `HANDOFF.md`'s order puts R7, R5, R6 and R10 after that read; the two sources disagree on whether R10 precedes 1.0.0 (an open question for the owner). It changes `plugin/` and the fix workflow, so it ships as a plugin version with tests.
