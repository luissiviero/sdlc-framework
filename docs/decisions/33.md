## 33. The automation pushes and opens pull requests as a GitHub App (amends 5)

*Reference: steps 6, 30 · NEW (2026-10-16), from the owner's question of 2026-10-15 on the pipeline's waits; ROADMAP R49, `docs/proposals/pipeline-speed.md`; the App is the one R22 (T18) creates.*

- Today (decision 5): the automation identity is the workflow token, "a GitHub App only when its limits bite". Its limits bite: an event the token causes starts no workflow run (the framework dispatches the next phase explicitly), and the project's own CI on a head the automation pushed ends `action_required` until the owner approves the runs (`docs/notes/23.md`).
- **Accepted:** the automation's pushes and pull requests use a GitHub App installed on the project, so the project's CI runs on them by itself; the App's key is a repository secret no model session can read; the App has branch-only write access and is never a bypass actor of the default branch's rules, except as R22 (T18) settles for its merge step. *[2026-10-20, choice 242 (decision 36): R22 settles it with a merge App of its own, so this App is never a bypass actor, its merge step included; not a reopening]*
- Rejected: a personal access token (tied to a person's account, broader than needed); keeping the workflow token (an approval click and a wait per pushed head).

**What it gives up:** a one-time App setup per project, done in a desktop browser (R21), and a key to guard.

**What it amends:** decision 5 (the automation identity). Decision 4 is kept: only the owner merges to the default branch, and the App's merge on the owner's approval is R22's to settle.

**Accepted:** the owner, 2026-10-16 ("Approved", on the table of 2026-10-15, row 6).
