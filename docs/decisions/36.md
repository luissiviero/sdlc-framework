## 36. Gate (e) is the owner's approving review; a GitHub App merges on it (amends 13, 4 and 5)

*Reference: steps 6, 29, 32 · NEW (2026-10-20), from study entry T18 (the crosswalk row deploy-approve, option C4; C3 and C1 its fallbacks), ROADMAP R22 (`docs/proposals/gate-e-approving-review.md`); accepted with R21 to R45 on 2026-10-16 (`docs/handoffs/2026-10-15-decision-table-r21-r45.md`, row R22 and open point 10; PR #215)*

*[2026-10-25, R45's first rename PR (decision 39, rows 1 to 6, 8, 16 to 27, 42 to 44 and 47; plugin 1.0.43): the phases this decision names by letter are named intent (a), design (b), build (c), test (d), deploy (e) and maintain (f) in branches, labels, `status.yaml`, check runs, evidence files and the gate sentences ("gate (deploy)"), and `/sdlc-plan` is `/sdlc-intent`; the letters are read for one release. The decision's substance is unchanged.]*

- Today (decisions 13, 4 and 5): gate (e) is the owner's merge of the build PR. The (e) run posts the review tally as the `sdlc/review` check run, marks the PR ready with `sdlc:e-ready` and never merges (`plugin/commands/sdlc-deploy.md`); the draft state is the only guard against an early merge, nothing requires an approving review, and the framework's record names the (e) merge commit and the pull request, never who merged. Decision 4's ruleset lets only the owner's account merge to the default branch, with no required review, and on the sample it holds live (ruleset 24078926, "Restrict updates", `docs/notes/53.md`). Decision 33 moved the automation's pushes and pull requests from decision 5's workflow token to the project's GitHub App, "the one R22 (T18) creates"; the model session still opens the design and build PRs with the workflow token (`docs/notes/48.md`).
- **Accepted:**
  1. **The approval is the gate.** Gate (e) becomes the owner's approving review on the build PR, informed by the REVIEW.md findings and the close-look banner (decision 35). The automation never approves it. On a declared production the release label stays the second act, given in the same visit (R13).
  2. **The approval is the only act.** The owner's review starts a workflow by itself. A deterministic step with no model checks that the approval is the owner's account (R17's `is_owner_actor`, fail closed, decision 34), that the PR is a framework build PR at `sdlc:e-ready`, and that `sdlc/review` is green on the head it merges. It checks that head against the review findings, not the check alone, since a phase session can post a check: `review-findings.json` names the reviewed commit, and every commit after it must be evidence or the run record. Then it merges through the GitHub App, a bypass actor of "Restrict updates". The workflow token is never a bypass actor. *[2026-10-20, choice 242: the merge App is one of its own, not decision 33's App: GitHub grants a bypass to an actor, not to a job, so decision 33's App, whose token the phase runners hold, is never a bypass actor]*
  3. **The check on the final head.** The runner posts `sdlc/review` again on the build PR's final head, after its own last commit.
  4. **Approving early.** If the owner approves before the check is green, the (e) run starts the merge workflow explicitly when the check turns green. A merge that cannot happen (a red check, a conflict) leaves the PR open and shows in the digest. *[2026-10-22, choice 250 (plugin 1.0.22): an approval given before the (e) run committed gate (e)'s record reading `wait` does not count; the owner approves again on the head, and the digest says so]*
  5. **Two rulesets.** Ruleset 1 stays as today: "Restrict updates" with the owner's bypass Exempt, so only the owner and the App can merge, from the phone too. *[2026-10-20, choice 242: the sample's ruleset 1 has its bypass in `pull_request` mode (`docs/notes/53.md`); it moves to Exempt when R22 sets up ruleset 2 there, recorded in a note]* *[2026-10-22: done on the sample, both rulesets read in NOTES §56]* *[2026-10-22, choice 251: ruleset 1 keeps the owner Exempt, and ruleset 2 gains "Require a pull request before merging", "Block force pushes" and "Restrict deletions", renamed "review and no direct writes on main (decision 36, choice 251)". Exempt alone let anything acting as the owner's login commit to `main` directly (NOTES §57)]* Ruleset 2 is new and requires only the `sdlc/review` check, with no required approval; the owner's bypass in it is "for pull requests only". Every pull request that is not a framework build PR gets a passing `sdlc/review` ("not a build PR") on each new head, posted by the steps that open or update it, or by a small workflow on the pull requests and pushes people make. So intent, design, incident and the owner's own PRs merge as today, while merging a build PR whose review is not green needs the web UI's bypass checkbox, a deliberate act. Ruleset 2 comes after R36's check on runbook PRs (the decision table, R36 "just before R22"). *[2026-10-22, choice 249, point 1, noted by the R22 double check (M1): ruleset 2 is created now, before R36, since every runbook PR gets the passing "not a build PR" check]*
  6. **One-time setup per project,** in `/sdlc-init` step 6: the App installed, its key a repository secret, the App a bypass actor of ruleset 1, ruleset 2 created. *[2026-10-20, choice 242: the merge App's key is a secret of a GitHub environment only the default branch can use, read only by the merge job]* *[2026-10-20, choice 249: where environments are not available (a private repository on a free plan), the owner merges after approving (fallback C1); the key is never a repository secret]*
  7. **The fallbacks, chosen by the live checks before the design.** C3, if a check the automation posts cannot satisfy a required check: no ruleset 2; the App still merges on the approval, and an early merge by hand stays possible and is flagged (the digest, and the (e) run's second PR). C1, if the App proves impractical: the owner merges after approving, one more click. The owner chose C3 as the fallback (the decision table's open point 10). *[2026-10-20, choice 242: both are kept, for different failures: C3 when a check the automation posts cannot satisfy a required check, which still needs the App; C1 when the App itself does not work]*
  8. **B's record.** The runner records the (e) approval and the merge (who, when, the findings tally, the banner shown) as lines of R11's approvals list.
- Rejected: A, the merge alone, and B alone, which only records and flags an early merge; C2, a second ruleset that requires an approval and the check (it applies to every pull request into the branch, so it would block every intent, design, incident and standing PR, and the owner's own intent PRs, decision 4's reason); a required check under the owner's Exempt bypass (no rule runs for the owner); GitHub's auto-merge (it merges as whoever enabled it, not verified, so the automation would be blocked by ruleset 1, and the owner enabling it is a click again); an automatic revert PR on an early merge (noise, while the release already holds back).

**Where it meets R51:** *[2026-10-22, R65's part 3 (docs-lint check 11): "R51 (rank 10)" stood here; ROADMAP's Order column holds the rank]* the R51 race analysis finds a window between the gate (e) offer and the merge (`docs/reviews/2026-10-20-r51-race-analysis.md`, rows 5 and 6). The merge step's head rule closes row 6 on the App's path: an "Update branch" after the offer adds a merge commit that is neither evidence nor the run record, so the step refuses and the PR waits in the digest; the owner's own merge of that head is held by ruleset 2 if a required check binds the head commit (to verify, below). Row 5, a build PR behind the default branch when it merges, is not closed by the approval, because the step judges the head and not the base; R51's re-check of the base is what closes it, and whether that re-check runs in this deterministic step before the App merges or at the release is R51's design. The approval never stands in for it.

**Why:** The article's gate is a code owner's approval through branch protection, informed by the findings: "Findings do not approve or block a PR on their own, and branch protection still requires approval from a code owner", and a platform engineer "can read the severity counts that the check run publishes as a machine-readable tally" (p.33); "the agent that wrote the code has no way to approve it" (p.34); approval comes from a "human through branch protection, informed by the findings" (p.35). The agent "has no route to push to main" (p.40), and "each non-interactive run acts under the agent's own identity" (p.41). The owner asked for that form with no extra click: the approval is the one act, and a step with no model turns it into the merge.

**What it gives up:** a one-time setup per project in a desktop browser (the App as a bypass actor, ruleset 2) and a key to guard; a passing check posted on every other pull request; a second actor on the default branch, the App, which merges only on the owner's approval.

**What it amends:** decision 13 (gate (e) becomes the owner's approving review, on which the App merges; on a declared production the release label stays the second act), decision 4 (a second actor, the App, may merge to the default branch, only on the owner's approval; a ruleset gains a required check, not the required approval decision 4 rejected; the workflow token stays branch-only) and decision 5 (its "GitHub App only when its limits bite" is taken for the merge; decision 33 already took it for the automation's pushes and pull requests, so this file amends only the merge part). Kept: 11 and 20 (a blocked merge leaves the PR open, shows in the digest and notifies no one beyond decision 31's review request); 28 and 29. Read: 27 (the owner-account question it left to T17, T18 and T24 is answered for this merge by R17's shared `is_owner_actor`, decision 34).
