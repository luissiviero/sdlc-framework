## 40. The project's policy sources in `policies/` are a guardrail path (amends 6)

*Reference: steps 7, 15, 20 · NEW (2026-10-23), from ROADMAP R27 (`docs/proposals/policy-sources.md`), the study entry T1 confirmed by the owner on 2026-10-09*

- Today (decision 6): the guardrails a run cannot change are `.claude/**`, `CLAUDE.md`, `REVIEW.md`, `sdlc.yaml` and the hook scripts, held in three layers: (i) the protected-path hook, the shell guard and the `Edit(...)` deny rules in the project settings; (ii) the managed settings file on the owner's machine; (iii) in CI, the hooks, the permissions and the sandbox's `denyWrite` list loaded from the pinned plugin, never from the PR branch.
- **Accepted:**
  1. **The list gains the project's `policies/` folder.** It holds the owner's policy sources, one file per policy skill (ROADMAP R27). A run never edits the policy that judges it.
  2. **The same three layers hold it.** (i) The hook, the shell guard and an `Edit(/policies/**)` deny rule in the project settings; (ii) the same rule in the managed settings file; (iii) the rule and a `denyWrite` entry in the CI settings of the pinned plugin. The gate's guardrail check and the runner's guardrail park read the same list, so a branch that changes `policies/` parks like any guardrail edit (decision 11).
  3. **The owner writes the sources** in a reviewed PR, as for every guardrail file. Claude may draft one in a session the owner opens, without the protected-path hook, never in a run. The owner's merge of that PR is the policy owner's sign-off (article p.22, step 5).
  4. **The exceptions are decision 6's own:** `/sdlc-init`'s install script, whose output rides in the change-0000 PR, creates the folder; a branch whose intent says "Framework change: yes" is exempt from the park, as for the other guardrails (OPERATING_MODEL section 3).
  5. **The code follows in a plugin version of its own,** after this file: R27's build.
- Rejected: leaving `policies/` writable by a run (a run could rewrite the policy the gate and the review pass judge it by); a separate list for the policy sources (four layers already read one list, `ALWAYS_PROTECTED` in `plugin/hooks/protected_paths.py`).

**Why:** The study's crosswalk row build-skills (`docs/reviews/2026-09-28-playbook-vs-framework.md`, line 135) adds the owner's policy sources "in the project's `policies/` folder (a guardrail path, extending D6's list; Claude may draft one in a PR the owner merges, never in a run)". The article asks for "one policy with a named owner and a written source of truth" (p.21), and a skill's text is "a control, though an advisory one" (p.22), so the source the skill reads must be out of the run's reach.

**What it gives up:** a run cannot correct a typo in a policy source; it reports the edit it needed and the owner makes it, as for `CLAUDE.md` today.

**What it amends:** decision 6, its list of guardrail paths, which gains `policies/`. Kept: decision 6's three layers and the hook with no exception.

**Accepted:** the owner, at the close of the study on 2026-10-09 (the record, section 8, part 1, T1's row: "D6 (`policies/` a guardrail path)", line 223); R27 accepted on 2026-10-16 (PR #215). Written as a decision file on 2026-10-23, before R27's build, in a documentation PR of its own, as the same record asks ("a decision file goes with any entry that amends one, written before the intent", line 219).
