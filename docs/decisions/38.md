## 38. When both model secrets are set, the subscription token wins (amends 1)

*Reference: step 3 · NEW (2026-10-20), from ROADMAP R60's list of every optional feature (`docs/reviews/2026-10-20-lifecycle-axis-ports/options.md`, section 1, row "Model credential")*

- Today (decision 1, its applied note of 2026-09-21): every workflow accepts both secrets, "`ANTHROPIC_API_KEY` preferred, `CLAUDE_CODE_OAUTH_TOKEN` otherwise". One function decides it, `choose_auth` in `plugin/ci/auth.py`, called by the phase runner and by the substrate smoke script (`.github/scripts/substrate_smoke.py`). The runner hands the session only the chosen secret (`credential_env`, `plugin/ci/run_phase.py:2207`), and only the key's path runs `--bare`. The eval runner hands its session "the credential of the environment as it is" (`plugin/evals/run.py`, step 3), and there the CLI picks the key on its own: "In non-interactive mode (`-p`), the key is always used when present" (`docs/notes/2.md`, quoting the CLI's environment-variables page).
- **Accepted:**
  1. **The credential stays a project's choice.** A project sets either secret, as today.
  2. **When both are set, `CLAUDE_CODE_OAUTH_TOKEN` wins.** The run draws on the owner's subscription window and runs without `--bare`, since bare mode does not read the token. The key is removed from the session's environment, because the CLI would otherwise use it.
  3. **Every run follows the one rule.** The phase runner and the smoke script follow it through `choose_auth` and `credential_env`; the eval runner hands its session the same single credential instead of the environment as it is.
  4. **The code follows in a plugin version of its own,** after this file: the order and the reason strings in `plugin/ci/auth.py`, the eval runner, their tests, and the sentences that say the key wins (the module's docstring, `plugin/evals/run.py`'s step 3). `docs/notes/2.md` is annotated beside its sentences (choice 126), not rewritten.
- Rejected: keeping the key first (today's rule, which the owner changed); a setting that names which secret wins (one more option, against the purpose of the list it comes from).

**Why:** The owner's answer of 2026-10-20 on the row "Model credential": "approved as recommended, with one change (2026-10-20): when both secrets are set, `CLAUDE_CODE_OAUTH_TOKEN` wins". The row keeps the credential a project's choice because "It follows the owner's account, not the pipeline." The answer records no further reason.

**What it gives up:** a project that holds both secrets runs on the subscription window, not on the key's per-token billing and its workspace spend limit (`docs/notes/2.md`). Moving a project from the token to the key, the path decision 1's note describes ("starts on the token and moves to the key from `/usage` data"), now means deleting the token secret, not only adding the key.

**What it amends:** decision 1, its applied note of 2026-09-21 ("`ANTHROPIC_API_KEY` preferred, `CLAUDE_CODE_OAUTH_TOKEN` otherwise"): the order is reversed. Kept: decision 1's hosted CI and both secrets accepted; the per-change budget cap (`gate.max_budget_usd`, never `null` by the same list's row "Dollar cap per change").

**Accepted:** the owner, 2026-10-20 (`options.md`, section 1, row "Model credential"). Written as a decision file on 2026-10-20, before the code that changes the order, in a documentation PR of its own.
