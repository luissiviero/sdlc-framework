## The problem

The confidence gate judges artifacts: the spec's shape, the plan against the diff, the three targets' exit codes, the evidence files, the review findings, the guardrails, the limits. Nothing judges the product. Three things follow:

- **The agent cannot show that the product works, only that the suite passes.** `sdlc.yaml` has `commands.build`, `test`, `lint` and `setup` and nothing that runs the product (`template/sdlc.yaml:35-41`). The (d) run's screenshot loop exists, but it keys on a mock or screen the plan names and, "without a browser or screenshot tool in this session", writes a README saying so (`plugin/commands/sdlc-test.md:75-84`).
- **Proof is a test or a screenshot, never a state.** `plan.md`'s `## Proof` lists "the mock or screenshot to match" beside the tests (`plan-template/SKILL.md:31-33`); the spec's Acceptance asks for "the screenshot or mock to match for UI" (`spec-template/SKILL.md:41`). A CLI, a library or a data pipeline has no screen, so its proof is the suite alone.
- **The verifier never looks at the product's output.** It runs the targets by hand, reads the previous phase's record in CI, and exercises code through direct calls (`plugin/agents/verifier.md` steps 2 to 4). It reads no screenshot and compares no state with an expectation written before the build.

ArtCraft's agents ship working features because they can act on the product and look at the result without a person: a scripted session judged by its exit status, a state dump "so agents can verify what they did without a screenshot", and a Definition of Done that reads "you have driven it through the control channel and reviewed a screenshot"[^artcraft]. Their mechanism is product architecture (a control protocol, a command registry) and does not transfer; the step in the loop does. *[2026-10-13, the citations re-read at the study's commits: lightcraft `control-protocol.md:258-259` says what CI *could* do with the exit status, and no ArtCraft workflow does it; photocraft `agent_tasks.rs:3-4` sets the state checks against engine internals, not against screenshots; the assert step is filmcraft `agents.md` §3 (`:250-256`), its Definition of Done (`:309-320`) has the drive and the screenshot (`:317`, quoted literally). "The step in the loop does" is partial: see the annotation under "Running the drive inside the session".]*

## What the article says

The verifier runs in a fresh context so that its verdict "is not colored by the assumptions that produced the code" (p.25-27 *[2026-10-13: p.26-27]*); the test phase is "run the tests, run the build, take the screenshot" and iterate (p.27-29 *[2026-10-13: p.26-28; the article's own example of a state as the quantifiable target, "the endpoint returns 200 with the new field", is p.28 step 3]*); the design mock is the visual target the build matches (p.12-13); the pull request is the audit record that carries the evidence (p.34-35)[^playbook]. The framework has each of these as a prompt line or a conditional loop; this proposal makes them steps the runner performs and the gate records.

## The proposal

Six sub-changes, in the order they depend on one another. Two more were considered and set aside (below).

1. **A fourth optional target, `commands.drive`.** One command that exercises the product headless and writes its outputs under `changes/<id>-<slug>/evidence/proof/` (PNG screenshots, JSON or text state files), exit status non-zero when any step failed. Empty means none, like `deploy.command`. The command is the project's: a Playwright script for a web app, a Python script that runs the CLI and dumps its state for a tool, a snapshot renderer for a desktop app. The framework never asks a project to adopt an architecture; it asks for one command. *[D3, accepted 2026-10-13: the command is one fixed string and the folder changes with every change, so the runner's step and `collect.py` set `SDLC_PROOF_DIR` (the absolute proof folder) and `SDLC_CHANGE_ID` in the drive's environment; the drive writes there and nowhere else; the step clears `proof/` before each run, so a stale file never counts, and writes `proof/manifest.json` (the commit, the run, the phase, each file with its size), so the record names the run that produced the proof.]*
2. **The runner runs it after the session, and a red drive is a red target.** The commands step gains a fourth entry beside build, test and lint, under the same timeout (`gate.command_timeout`), in the same credential-free step, on the working tree the session left; its exit code and output tail join the gate record's `commands` check and `evidence/drive.log`; the outputs land with the evidence commit. Under T10 a red drive dispatches the next fix round with `drive.log` as its constraint; at the cap it parks. Nothing new runs inside the session. *[D1 and D4, accepted 2026-10-13: the "commands step" is gate code (`plugin/gate/gate.py` `run_deferred_commands` and `write_deferred_logs`, `plugin/gate/checks.py` `run_targets` and `judge_targets`); `run_phase.py` holds only the timeout line (`commands_timeout_seconds`, 3 × `command_timeout`, to scale), and the three workflow templates' `timeout-minutes: 200` assume three targets. The drive runs at gates (c), (d) and (e), never (b), where the tree holds no implementation, and by hand in `evidence/collect.py`. Built after R10, so a red drive follows decision 29: a round, a timeout a round, an infrastructure failure one re-run, the cap a park; before R10 it would park as any red target does. The lists that know three logs, `EVIDENCE_TARGETS` (`artifacts.py:70`), `LOG_FILES` (`description.py:61`), `HEADER_REQUIRED_AT` (`checks.py:418`), `commands_summary` and the check run, gain `drive.log`.]*
3. **Proof items may name a state with an expected value.** `## Proof` gains a third kind beside the test and the screenshot: `state: evidence/proof/<file>, <path> == <value>` (or `contains`, `matches`). The gate's `evidence` check verifies that every proof file the plan names exists after the runner's step, as it does for screenshots today; the comparison of values is the verifier's. *[D2 and D5, accepted 2026-10-13: Proof is free prose today (`plan-template/SKILL.md:31-33`) and nothing parses any section's content, and the gate checks no screenshot (the annotation under "Proof and screenshots"), so the check is new. The shape is fixed per item: `- test: <name>`; `- screenshot: evidence/proof/<file>.png`, with `vs mock/<file>` when the spec carries a `Mock:` line; `- state: evidence/proof/<file> <path> == | contains | matches <value>`, where `<path>` is a dotted JSON key or `line` for a text file and `matches` is a Python `re`; prose stays allowed beside the items. **The comparison of values is the gate's, in the runner's step**, reading the items from the approved `plan.md` (`GateContext.approved_artifact`, `checks.py:124-135`), because the (c) session may edit `plan.md` (plan sync; `sdlc-build.md:87`); an item added during (c) is reported, never the bar. It belongs to the judgment of the drive's run, not to `check_evidence`, which gate (c) does not re-judge after the step (`gate.py:433-446`). Gate (b) refuses a plan whose Proof names a `state` or `screenshot` item while `commands.drive` is empty (D4), so the park comes at the design, not after the build.]*
4. **The verifier reads the proof and reports per item.** Its card gains a step: open the proof files the runner produced for the phase before yours (a PNG through the Read tool, a state file as text), compare each with the plan's Proof item, and report one line per item, `matches`, `differs` (with what was seen) or `not produced`, each marked measured. The verdict `does not match the plan` covers a `differs`. The writer still never judges; the judge now sees the product. *[D2, accepted 2026-10-13: narrowed. The verifier runs at (c) and (d) only (`sdlc-build.md:105-116`, `sdlc-test.md:86-93`, none at (e)), reads `gate-b.json` at (c) and `gate-c.json` at (d) (`verifier.md:26-30`), and so never sees the final tree's proof. It keeps the images: at (d) it compares (c)'s screenshots with the mock and names the tree it read, in decision 29's wording; the `state` items are the gate's (the annotation above). `does not match the plan` still covers a `differs`.]*
5. **The PR body shows the proof.** T27's block gains a "Proof" line per item: the item, the outcome from `verifier.md`, and a link to the file at the head commit. Images stay under a size cap the gate's `evidence` check enforces (ArtCraft caps golden PNGs at 50 KB; the value is to settle), so the repository does not grow with every change; a larger image is reduced by the drive command or refused. *[D6 and D9, accepted 2026-10-13: T27's block does not exist yet, so now the evidence line gains "proof N, state items M of K matching" and the per-item Proof line comes with T27, as a second change; the outcome comes from the runner's record, not from `verifier.md`, which never reads the final tree. The cap is `gate.proof_image_kb`, 50 by default (filmcraft `crates/testkit/src/golden.rs:15`, `MAX_GOLDEN_BYTES = 50*1024`, checked when a golden is blessed, not in CI; the goldens are committed, the largest 42,952 bytes), and 10 images per run; an image over either limit is deleted by the runner's step before the evidence commit, because `commit_run_record` commits the whole change folder even on a park (`run_phase.py:1996-2021`), and is reported `not produced`, a park only when the approved plan named it.]*
6. **`/sdlc-init` proposes the command where the tool already exists.** Node with Playwright in `package.json`: `npx playwright test proof/ --reporter=json`; Python: an empty `proof/run.py` skeleton that exits 0 and writes nothing, named so the owner sees the slot; anything else: `""` with a comment. The owner confirms as for the three targets. *[D8, accepted 2026-10-13: the Playwright line only when `@playwright/test` is in `package.json`, writing to `$SDLC_PROOF_DIR` (Playwright writes to its own output folder otherwise), with the browser install added to `commands.setup`; for Python and everything else `""` with a comment naming the slot. No skeleton: a drive that exits 0 and writes nothing is a green drive that proves nothing, and project content written by the plugin.]*

## How it is judged

On the sample repository and the next project: a change whose plan names a state item ships with `evidence/proof/` filled by the runner, `verifier.md` reporting the item, and the PR body showing it; a change whose product behaviour is wrong while its suite is green is caught by the drive step or by the verifier's `differs` before the owner's (e) review. The failure is a merged change whose product did not do what the plan promised while the proof folder is empty or unread. *[D7, accepted 2026-10-13: one more thing to judge. The writer authors the drive script in (c) and could write the expected value instead of reading it from the product. The adversarial reviewer at (c) and (d) reads the drive's diff with one more angle, "does the drive read the value from the product, or write it?", and the drive's files are listed in the plan's "Files that change". Named, not closed: it is the weakness feature tests already have.]*

## Considered and not chosen

- **A project audit test that every user-facing action is reachable headless** (effectcraft's `ui_agent_audit.rs`): product architecture, not process; at most one sentence in the `ux-conventions` skill that a new screen must be reachable by the drive command.
- **The session driving the live product through a project MCP server registered in the repository** (filmcraft's `.mcp.json`): it runs inside the sandbox the drive step avoids, puts a project-controlled server inside a privileged session, and leaves no committed record; sub-change 1 gives the same evidence deterministically. Its place is T20, where a preview environment is a URL the verifier can call.
- **Running the drive inside the session** so the agent iterates on the result as ArtCraft's agents do: the sandbox denies the nested `.env*`, and a helper that runs it outside the sandbox for the session was rejected by T10 as a hole the session controls. *[D11, accepted 2026-10-13: this is what ArtCraft and the article do. The agent drives the product in its own session and iterates (filmcraft `docs/agents.md:250-256`, lightcraft `AGENTS.md:120-121`; article p.27-28, "Claude iterates until the check passes"); no ArtCraft CI workflow runs a drive, and lightcraft's "CI and nightly runs can judge a snapshot by its exit status" (`docs/control-protocol.md:259`) is unused at `b3d392b`. Setting it aside stands, for the sandbox and T10's reasons; "the step in the loop does [transfer]" in The problem overstates it: what transfers is a check after the session plus decision 29's rounds, so the fidelity is partial.]*
- **Proof files as workflow artifacts instead of committed files**: the record would outlive nothing (T32 keeps transcripts as artifacts because they are large and sensitive; proof files are small and are the evidence the owner approves), so they are committed under the cap.
