## The problem

Gate (e) is the owner's merge of the build PR (decision 13)[^decision-13]. The draft state is the only guard against an early merge: the build PR opens as a draft at (c) and is marked ready with `sdlc:e-ready` at (e). Since 0.3.1 an early merge releases nothing and a change releases once (issue #66), but an early merge still puts code the review has not judged on the default branch, and the review's fixes then arrive only with the (e) run's second PR. Nothing requires an approving review, and who merged at (e) is GitHub's record only: the framework's own record names the merge commit and the pull request, never the actor[^crosswalk].

The owner preferred the article's version, an approval informed by the findings, and asked for a form with no extra click. The owner first chose C2; after the independent review found that C2's second ruleset would apply to every pull request into the default branch and block intent, design and incident PRs, the owner chose between two corrected forms and took C4, under which those PRs merge as today.

## What the article says

A code owner approves through branch protection, informed by the findings: "Findings do not approve or block a PR on their own, and branch protection still requires approval from a code owner"; a platform engineer who wants to gate merges on findings "can read the severity counts that the check run publishes as a machine-readable tally" (p.33 step 3; the prerequisites call such branch protection "worthwhile"). "Separation of duties is preserved, because the agent that wrote the code has no way to approve it" (p.34), and "Approval comes from a human through branch protection, informed by the findings" (p.35). The stage table reserves human review for regulated and critical code, and the chain of commits records "who approved it" (p.6). Anything the agent writes arrives as a PR, with no route to push to main, and each non-interactive run acts under the agent's own identity (p.40 step 2, p.41)[^playbook].

## The proposal

The owner's choice, condensed; nothing added to it.

1. **The approval is the gate.** Gate (e) becomes the owner's approving review on the build PR, informed by the REVIEW.md findings and the banner (R24, T9), as in the article (amends decision 13). The agent cannot approve it, because the automation identity authored it. On a declared production the release label stays the second act, given in the same visit (R13).
2. **The approval is the only act.** A review the owner submits starts workflows (only the workflow token's events do not, decision 5, `docs/notes/11.md` §11a), so the approval fires a merge workflow by itself. A deterministic step, with no model, checks that the approval is the owner's, that the PR is a framework build PR at `sdlc:e-ready`, and that `sdlc/review` is green on the head it merges; and it checks that head against the review findings, not the check alone, since a phase session can post a check: `review-findings.json` names the reviewed commit, and no commit after it may be anything but evidence and the run record. Then it merges through a dedicated GitHub App that is a bypass actor of "Restrict updates" (T1's direction; amends decisions 4 and 5: a second actor may merge, only on the owner's approval). The workflow token is never a bypass actor (decision 4). *[2026-10-20, choice 242: the merge App is one of its own, not decision 33's App, whose token the phase runners hold; its key is a secret of a GitHub environment only the default branch can use, read only by the merge job (decision 36, points 2 and 6)]*
3. **The check on the final head.** The runner posts `sdlc/review` again on the build PR's final head, after its own last commit; today it re-posts only `sdlc/d`, and before that commit.
4. **Approving early.** If the owner approves before the check is green, the (e) run starts the merge workflow explicitly when the check turns green, as the runner already dispatches the next phase. A merge that cannot happen (a red check, a conflict) leaves the PR open and shows in the digest; nothing notifies the owner (decisions 11 and 20).
5. **Two rulesets.** Ruleset 1 stays as today: "Restrict updates", the owner's bypass Exempt, so only the owner and the App can merge, from the phone too. Ruleset 2 is new and requires only the `sdlc/review` check, with no required approval (decision 4's reason holds: the owner's own intent PRs could not pass one); the owner's bypass in it is "for pull requests only". Every pull request that is not a framework build PR gets a passing `sdlc/review` ("not a build PR") on each new head. The steps that open or update an automation PR (design, incident, dismissal, the standing PRs, ticket intents, fix-round pushes to a PR that is not a build PR) post it themselves, since the workflow token's PRs and pushes start no workflow run that proceeds by itself (their `pull_request` runs wait for approval); a runbook PR carries its own `sdlc/review` (R36, T14); a small workflow posts it on the pull requests and pushes people make. So intent, design, incident and the owner's own PRs merge as today, from the phone too, while merging a build PR whose review is not green needs the web UI's bypass checkbox: a deliberate act. *[2026-10-20, choice 242: the sample's ruleset 1 has its bypass in `pull_request` mode (`docs/notes/53.md`); it moves to Exempt when R22 sets up ruleset 2 there, recorded in a note (decision 36, point 5)]*

The workflow token stays as the in-job fallback, as the model session's token and in the workflows that mint no App token. This carries decision 33 out and amends no decision. `CLAUDE.md`'s fallback sentence ("the explicit dispatch stays for the fallback") is the owner's edit, given in the owner's format by this build's session. The merge App of point 2 is set up in the same step]*
7. **Fallbacks.** C3, if a check posted by the automation cannot satisfy a required check: no ruleset 2; the App still merges on the approval, and an early merge by hand stays possible and is flagged (the digest, and the (e) run's second PR). C1, if the App proves impractical: the owner merges after approving, one more click. *[2026-10-20, choice 242: both kept, for different failures: C3 when a check the automation posts cannot satisfy a required check, C1 when the App does not work (decision 36, point 7)]*
8. **B's record, in every form.** The runner records the (e) approval and the merge (who, when, the findings tally, the banner shown) beside the plan acceptance and the (c) and (d) labels *[2026-10-20, R60's answers (`options.md`, row "Profile"): `standard` becomes the only profile and the per-change override goes, so the `full` profile's `sdlc:c-approved` and `sdlc:d-approved` labels go with it; the lines sit beside the plan acceptance alone, and the merge step reads nothing of (c) or (d).
