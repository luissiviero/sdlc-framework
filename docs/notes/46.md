## 46. Facts read on 2026-10-17 by the pipeline sprint session: an issue_comment run on the sample, for R17 (decision 34)

The session is `ccr-4900ade8-1qc1s9`. Decision 34 asks for one live check before the comment dispatcher is designed: which workflow file an `issue_comment` run uses, and what its token holds. The probe was a throwaway workflow on the sample (PR #64): no model, no checkout, and the comment's text read only in the job's `if:`. It ran on `issue_comment` `created` and on a `workflow_dispatch` of itself. Its `if:` passed a dispatch, or a comment on a pull request whose body starts with `@claude probe`. The session posted two comments, through the GitHub tools that act as the owner's account, on PR #65. That PR's head (`probe/r17-remove`, `378ced2`) deletes the probe file.

- **An `issue_comment` run uses the default branch's workflow file and commit, never the pull request's head** (verified, run 39065672021): `GITHUB_REF=refs/heads/main`, `GITHUB_SHA` and `GITHUB_WORKFLOW_SHA` both `208a091` (the default branch's head at that moment, read through the API in the same run), and `GITHUB_WORKFLOW_REF=…/sdlc-probe-comment.yml@refs/heads/main`. The run started although the PR's head (`378ced2`) has no probe file. The Actions API lists the run with `head_branch: main`, `head_sha: 208a091`. A dispatcher added to a project therefore fires only once it is on the default branch, and a PR cannot change the dispatcher that judges its own comments.
- **The owner's own comment arrives as `author_association: OWNER`** (verified, the same run): `comment.user.login` `luissiviero`, `comment.user.type` `User`, `author_association` `OWNER`, `github.repository_owner` `luissiviero`, and `GITHUB_ACTOR` and `GITHUB_TRIGGERING_ACTOR` the comment's author. On this personal repository, the coarse `if:` of decision 34 (`author_association == 'OWNER'`, the author not a `[bot]`) and the exact check (the comment's login equals the repository owner) agree.
- **The payload carries no pull request head** (verified by the probe's own API read): the head ref, sha and repository came from `GET /repos/{repo}/pulls/65` (`probe/r17-remove`, `378ced2`, `luissiviero/sdlc-sample-python`, state `open`), not from the event. `github.event.issue.pull_request` is set, so the `if:` can tell a PR comment from an issue comment.
- **The token holds exactly the job's `permissions:` block** (verified, the "Set up job" section of job 117492693205): `Actions: write`, `Contents: read`, `Metadata: read`, `PullRequests: read`.
- **A `workflow_dispatch` sent with that token starts a run** (verified): `POST /repos/{repo}/actions/workflows/sdlc-probe-comment.yml/dispatches` with `ref: main` returned `204`, and run 39065678295 (`event: workflow_dispatch`, actor `github-actions[bot]`) started five seconds later with `from_run=39065672021`. This is NOTES §11's exception for `workflow_dispatch`, now seen from an `issue_comment` run. The dispatched run's actor is `github-actions[bot]`, not the owner: a round the dispatcher starts cannot take the owner's identity from its own actor, so the dispatch must carry what the round needs (the comment's link).
- **A comment the `if:` refuses still creates a run, skipped at once** (verified, run 39065673214, `conclusion: skipped`, from the comment without the prefix). The cost the decision names under "What it gives up" is real: every comment on every issue and pull request creates one skipped run.
- **Not verified: the token on a pull request from a fork.** The check needs a second account. The run is in the default branch's context (above), so the job's `permissions:` block would apply as written, which is why the dispatcher must refuse a head in another repository whatever the answer (decision 34, point 2).

PR #65 removes the probe; the runs above stay in the sample's Actions history.
