## 60. Facts read on 2026-10-23 for ROADMAP R44: sandbox.credentials, the sandbox's own refusals under .git, and the action tags' commits

### sandbox
- **The shape of `sandbox.credentials`** (verified, `cc-settings-reference`, `cc-sandboxing`): an object with `files` and `envVars`, each an array of entries with `path` or `name` and a `mode` of `deny` or `mask`. It is the playbook's shape (p.37), so plugin 1.0.27's `plugin/ci/settings.ci.json` uses it as the article prints it. There is no built-in list: only the entries given are protected.
- **What `deny` does** (verified, `cc-sandboxing`, "Protect credentials"): a file path is denied for reads inside the sandbox, as `filesystem.denyRead` does; a variable is unset before each sandboxed command runs. The file protection belongs to the filesystem layer; the variable protection holds even with filesystem isolation off. `mask` entries are honoured only from user settings, managed settings and the `--settings` flag, and need Claude Code 2.1.221 or later; 1.0.27 uses `deny` only.
- **The `envVars` deny holds on a runner** (verified, `case-0007`; added 2026-10-23 with PR #351): eval case `0007-sandbox-credentials-hidden` passed in `Framework evals` on Claude Code 2.1.278, the version that workflow installs. A sandboxed `python -c` found `PATH` and `HOME` set and `CLAUDE_CODE_OAUTH_TOKEN` unset, while the runner had handed that token to the session's own process (`ci/auth.py credential_env`). The run proves the deny for that variable only: `ANTHROPIC_API_KEY` was empty in the step's environment, so its `unset` proves nothing. The `files` half (`~/.ssh`, `~/.aws/credentials`) and Claude Code 2.1.304 are not run live.
- **`--settings` takes an inline JSON value** (verified, `cc-sandboxing`: `claude --settings '{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false}}'`). 1.0.27's eval runner passes one to each case's session on a runner.
- **Edit deny rules feed the sandbox** (verified, `cc-settings-reference`, `sandbox.filesystem.denyWrite`): Claude Code "adds the paths from your `Edit(...)` deny permission rules" to `denyWrite`. So an `Edit(/.git/**)` rule in the CI settings would also refuse the sandboxed `git add` and `git commit` the session makes of its own work. 1.0.27 therefore denies `.git/config` and `.git/hooks` there, not the whole folder, and its protected-paths hook, which judges file tools only, refuses all of `.git/**`.
- **What the sandbox already refuses** (verified, `cc-sandboxing`, "Protected paths"; `cc-sandbox-environments`): in the working directory, writes to `.git/hooks` and `.git/config`, and in it and the directories above it, writes to `.mcp.json` and the `.claude` settings, skills, agents, commands and hooks. No `allowWrite` lifts these. On Linux the runtime builds the list once at launch. So a sandboxed `git config filter.x.clean …` in the project root is refused by the sandbox itself. The `Write` tool is not a sandboxed command: the permission rules and the protected-paths hook judge it. That the refusal holds on a runner is not verified live.
