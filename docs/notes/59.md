## 59. R51's two GitHub facts (2026-10-23)

### git
- **GH-ref, the same object id** (verified, `ghref`). With `origin/main` at `8d910d4` as `$SHA` and `$REF` a new branch:
  1. `git push origin $SHA:$REF` created it, exit 0.
  2. The same push again answered "Everything up-to-date", exit 0.
  3. `git push --force-with-lease=$REF: origin $SHA:$REF`, the empty expected value that means "the ref must not exist", also answered "Everything up-to-date", exit 0. Git compares the advertised value with the object it would send and stops there, before the lease is judged.
  4. The empty lease with another commit (`a07d6f8`, an ancestor) was refused: `! [rejected] … (stale info)`, exit 1.
- **A child commit fast-forwards** (verified, `ghref`). Two commits made with `git commit-tree` on `main`'s tree, each with `8d910d4` as parent and its own message: a plain push of the first to the ref that held `8d910d4` was accepted (`8d910d4..d3c9fa9`, exit 0). The empty lease with the second, its sibling, was refused (`stale info`, exit 1). The same empty lease created a new ref with that commit (`* [new branch]`, exit 0).
- **What follows for an id reservation:** neither half of the analysis's check 1 is enough alone. Two allocations that push the same default-branch tip both succeed (point 3), and a plain push of an allocation's own commit fast-forwards over a reservation of the tip (the bullet above). A commit unique to the allocation, pushed with the empty lease, is refused whenever the ref exists, whatever it holds. The refusal reads `(stale info)`; a non-fast-forward reads `(non-fast-forward)` or `(fetch first)`.
- **The probe branches stay** (`ghref`). `git push origin --delete` of `claude/r51-ghref-probe` and `claude/r51-ghref-probe2` was refused by the session's proxy (HTTP 403), a policy refusal not worked around; the owner deletes them.

### github-actions
- **GH-queue** (read, `docs`; not reproduced live). "By default, any existing `pending` job or workflow in the same concurrency group will be canceled and the new queued job or workflow will take its place." With `cancel-in-progress: false` one run is running and at most one is pending. Runs wait "in first-in-first-out (FIFO) order according to the time each one started waiting on the concurrency group, not the time each workflow was dispatched … ordering is not guaranteed." This repeats what NOTES §11 read on 2026-09-21.
- **New since NOTES §11** (read, `docs`; not tried live): an optional `queue` key on `concurrency`. `single`, the default, keeps the rule above; `max` lets "up to 100 jobs or workflow runs" wait, and further runs are cancelled; `queue: max` with `cancel-in-progress: true` is a validation error. No framework workflow sets it. A design that needs no pending run kept does not rely on it.
