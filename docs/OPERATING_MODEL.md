# Operating model

> The loop keeps running. Human judgement stays above it. — *The AI-Native SDLC playbook*, p.50

This file is the first artifact of the framework (build guide step 1; finalised in session 1). It states what the framework does, which artifact every phase commits, when a human is involved, and how change requests flow. Everything else in the repo implements it. Rationale and article citations live in `docs/BUILD_GUIDE.md`; the choices behind it in `docs/decisions/index.md`, one file per decision; platform facts verified against the Claude Code docs in `docs/notes/index.md`, one file per section.

## 1. Purpose

A framework that connects to any GitHub-hosted project (any size, any type: service, library, research code, data pipeline; GitHub only, decision 23: every trigger, the automation identity, the labels, the check runs and the digest issue are GitHub-specific, and `/sdlc-init` refuses an `origin` on another host) and drives each change through six phases:

| Phase | What runs | Artifact committed | Read by |
|---|---|---|---|
| (a) plan | interactive brainstorm with the owner | `intent.md` | (b) |
| (b) design | autonomous: spec pass with policy skills, then a read-only planning run | `spec.md` + `plan.md` | (c) |
| (c) build | autonomous: implementation under auto-accept with hooks, simplifier, verifier | the diff and its tests, on the build PR | (d) |
| (d) test | autonomous: fresh-context full run — tests, build, lint, screenshots, verifier | `evidence/` + PR check run | (e) |
| (e) deploy | autonomous: review passes, fix loop until green, release prepared per the project's adapter | reviewed PR / release | production |
| (f) maintain | standing loop: deterministic detection → diagnose → propose | incident record (`lessons/`) → new `intent.md` | (a) |

Principle (article p.6–8): every phase ends by committing its artifact; the accepted artifact fires the next phase. The chain of commits is the audit trail.

## 2. Roles

One person owns every role the article names (originator, product owner, tech lead, engineer, code owner, release manager, service owner). Separation of duties is therefore rebuilt from:

- **writer ≠ judge** — the agent that produced an artifact never judges it; a different agent in a fresh context reviews it, and only the owner approves;
- **an automation identity** distinct from the owner's account for every non-interactive run (the CI workflow token), so the log separates what the agent did from what the owner approved;
- **branch rules** — only the owner's account can merge to `main`; the automation identity has branch-only write access; no bypass rights. The rule is a GitHub branch ruleset on the default branch that the owner creates by hand (decision 4; `/sdlc-init` §6 says how): *Restrict updates* with the repository admin as the only bypass actor — the one form that keeps a merge to the owner, because the workflow token holds `contents: write` and the phase session may run `gh`, so a rule that only requires a pull request or only stops direct pushes still lets the token merge; a classic protection rule on a user-owned repository cannot restrict who pushes at all. The owner's bypass mode is *Exempt* (since 0.2.26; NOTES §17, verified 2026-09-27): the rules do not run for the owner, so a merge from the GitHub mobile app goes through on a tap although the app still labels the pull request "Unable to merge" (it shows the general merge state, `blocked` for everyone the rules apply to); under "Allow for pull requests only" the app showed the same label with no bypass control and the owner merged from the web UI through its bypass checkbox; `gh pr merge` refuses a `blocked` pull request whatever the mode (the REST merge endpoint through `gh api` does not). The cost of Exempt is no bypass audit entry for the owner's merges (the merge commit and `merged_by` remain the record); the rules still run for every other actor, the workflow token included. The framework never creates it, because a session must not be able to, and nothing in the plugin blocks a push or a merge to `main` — the ruleset is the guard. Since 0.2.25 the daily digest (§7) opens with a notice while the default branch has no such rule (`pr/github.py default_branch_protection`: the branch's active rules must include an `update` rule; the 1.0.0 readiness review of 2026-09-26 found the framework's own `main` unprotected, and the sample's classic rule does not count).

## 3. Profiles — which gates are human

Set per project in `sdlc.yaml` by `/sdlc-init`; overridable per change in `changes/<id>-<slug>/status.yaml` (`profile_override`).

| Profile | Human gates | Automated gates | For |
|---|---|---|---|
| **Standard** (default) | (a) merge intent PR · (b) merge spec+plan PR · (e) merge build PR | (c), (d) | most projects |
| **Full** | (a), (b), (c) review + label, (d) review + label, (e) merge (+ release label) | — | live production, money at stake |

(Lite — gates (a) and (e) only — was withdrawn by decision 21 and removed in plugin 0.2.14: it took the human out of gate (b), which the article keeps human (p.14, p.15). A `sdlc.yaml` or `status.yaml` that still says `lite` reads as Standard.)

Automated gates are passed by the **confidence gate** (`plugin/gate/`, session 2): deterministic checks (artifact matches its template; no open flagged concern in `spec.md`; tests, build, lint green; evidence present; no Important review findings; `plan.md` ↔ diff consistent; no diff touching `.claude/**`, `CLAUDE.md`, `REVIEW.md`, `sdlc.yaml` unless the change is the framework itself — `intent.md` says `Framework change: yes`; no risk-list hit the owner has not accepted; run limits) followed by the adversarial reviewer agent's verdict, written in a fresh context as `evidence/adversarial-review-<phase>.json`: *continue* or *escalate* (= park), required at (b), (c) and (d) in every profile. The gate runs inside the phase run itself (`gate/cli.py check` in the session, its verdict written to `evidence/gate-<phase>.json`) — except its `commands` check, which since 0.3.0 (issue #91, choice 133) a CI session's gate records as deferred and the runner runs after the model's session, outside Claude Code's sandbox (where `Read(**/.env*)` makes a nested `.env*` unreadable and a test suite that copies a fixture holding one fails), on the working tree the session left: `gate/cli.py run-commands` rewrites the record and `status.yaml` with the real runs, a red target parks the change as before, a session that fails after its gate or a step that cannot run parks it too (the session has already pushed the deferred record and labelled the PR), the runner's guard refuses to start the next phase on a record whose targets never ran, the step runs without the job's credentials, and a gate run by hand runs the targets itself; since 0.3.2 (item 3b) the same holds for the three command logs the `evidence` check reads at (d) and (e): inside a CI session `evidence/collect.py` runs nothing and leaves a deferred mark as each log's first line, the gate accepts the mark only while the runner's step is still to come, that step writes the three logs from its one run of the targets and re-judges the `evidence` check beside the `commands` one, and the verifier in a CI session reads the newest gate record and the logs instead of running the targets — and in CI the runner dispatches the next phase from that file: the (c) and (d) gates of the Standard profile are the run's own check, and the owner reviews their outcome at (e), on the build PR that carries the evidence, the findings and the plan conformance (the design, decision 18; the 1.0.0 readiness review of 2026-09-26 upheld it), while the runner keeps its own guards around the run — the guardrail check by the merge base's intent, the preflight, the label actor and, since 0.2.26, the owner-only fields of `status.yaml` (§6). The gate judges committed work against what the owner approved: the intent as merged at gate (a), `sdlc.yaml` as on the base branch when the diff changes it, the change's `profile_override` and `review_override` as the base branch's `status.yaml` carries them (since 0.2.26, choice 103: a branch that wrote `profile_override: standard` skipped the Full profile's (c)/(d) label gates before; the branch's own values are ignored and the result's `config_note` says so), HEAD rather than the working tree (every diff-reading check — `plan_sync`, `design_scope`, `guardrails`, `risk_list` — reads the merge base…HEAD file list; `design_scope` runs at gate (a) too since 0.2.26, change 0000 exempt, so the intent PR carries the intent alone; `clean_tree` is the one check that looks at the working tree, and it parks on uncommitted work outside the change folder). The checks that read an artifact rather than a diff — `artifacts`, `open_concerns`, `plan_sync`'s reading of `plan.md` and `panel`'s of the ledger and the spec — read the change folder in the working tree by design: the phase commits its artifact before the gate, the panel commits each decision before the verdict, and the evidence commit after the gate lands whatever else the folder holds, so the working-tree copy is what the evidence commit lands (`commit-phase` commits the whole folder); no check enforces that the folder is committed — `clean_tree` skips it and does not run at (a) or (b) — which is why `risk_list` alone reads the spec's concerns at HEAD. The same checks run at a human gate: all green → the run stops with `sdlc:<phase>-ready`; a failed check parks there too.

**Review mode** (decision 21; build guide step 16a): `sdlc.yaml: review: parked | deferred`, per change `status.yaml: review_override`. Under `parked` (the default) a judgment item parks the change for the owner. Under `deferred`, before the gate, the run puts each item of a **fixed list** to a review panel and continues: an open flagged concern in `spec.md`, a concern naming contradicting policy skills, an `escalate` verdict of the adversarial reviewer (its routine / non-routine classification never parks; it only lowers the iteration cap), an Important review finding whose fix the run cannot determine, and the verifier's "does not match the plan". The panel is three fresh contexts (`plugin/panel/`): a reviewer (the REVIEW.md pass over the item), a devil's advocate (the adversarial reviewer, blind to the reviewer and on a different model, `sdlc.yaml: panel_advocate_model`, because three judges on one model share its blind spots), and a conciliator that reads both verdicts and writes one decision with a rationale of at most five lines. Since 0.2.30 the two blind verdicts are enforced, not only asked for: the `panel_blind` hook refuses a Read, Grep or shell command that would show one verdict while the other is not yet written, and records beside the advocate's verdict which agent wrote it and on which model (`<phase>-<n>-advocate.model.json`, read from that sub-agent's own transcript); `record` refuses an item whose reviewer or advocate file has no `## Verdict`, or whose advocate record does not name the devil's advocate on `panel_advocate_model`, and the ledger carries the verdicts from those files; and a CI run that added panel decisions parks when no model in its `modelUsage` is `panel_advocate_model` (`evidence/panel-models-<phase>.json`; a session already on that model is a warning in the PR summary, not a park). `panel/cli.py record` applies the decision (a concern is closed in `spec.md` as `decided (by panel #n): <decision> — <concern>`, `n` its ledger line; an `escalate` decided `continue` and a finding decided `settled` pass their gate checks), counts one panel call against `gate.max_panel_calls` (default 4; a panel call is not a fix iteration — the first deferred run spent the whole non-routine cap on two concerns, so since 0.2.15 the two counts are separate and the `sdlc:reset-iterations` label resets both), writes one line to the ledger `evidence/decisions-<phase>.json` (the `.md` beside it is what the owner reads: item, the two verdicts, the decision, the rationale, the cost), and commits the change folder, so the decision is in HEAD before the adversarial reviewer judges it. The gate's `panel` check refuses a ledger line without a decision or a rationale, a line since 0.2.30 whose two member files are not both committed with a verdict or whose advocate record does not name the advocate on its model, a concern closed by the panel whose `#n` no ledger of the phases so far carries (a concern closed at (b) stays closed through (c)–(e) and its line stays in `decisions-b.json`; the wording after the marker may be tidied; the number may not), and any line about a never-to-panel item. The PR at the next human gate opens with "Decisions taken for you (N)"; a review comment on any line overturns it through `/sdlc-fix`. What never goes to the panel and still parks, in both modes: a risk-list hit, a guardrail file change, a run limit, an infrastructure failure, anything that merges to `main` or deploys.

## 4. Gate mechanics

| Gate | Human form | Event that starts the next phase |
|---|---|---|
| (a) | merge of the intent PR | merge → design workflow |
| (b) | merge of the spec+plan PR (every profile) | merge → build workflow |
| (c) | Full only: approving review + label `sdlc:c-approved` on the build PR | label → test workflow. Standard: the build job dispatches the test job |
| (d) | Full only: approving review + label `sdlc:d-approved` | label → review workflow. Standard: the test job dispatches the review job |
| (e) | merge of the build PR; plus the release label `sdlc:release-approved` only when `sdlc.yaml` declares a real production | merge → `sdlc-release.yml` runs the adapter's `deploy.command`; with `deploy.production: true` it waits until the release approval exists (the label event re-runs it) |
| (f) | triage of each incident intent PR: merge (fix now) · label (schedule) · close with a reason (dismiss) | merge = gate (a) of that intent |

GitHub rule the design respects: events caused by the workflow token do not start new workflow runs, except `workflow_dispatch` / `repository_dispatch`. The owner's merges, reviews and labels fire workflows normally; every automated transition dispatches the next phase explicitly with the change id.

**Closing a PR at gates (a)–(e) without merging abandons the change** (decision 25): `sdlc-abandon.yml` records `status.yaml: phase: abandoned` (with the reason) on the closed PR's head and on every other `sdlc/<id>/*` branch of the change on the remote, the branches are kept, and every workflow's guard, `commit-phase` and `/sdlc-fix` skip the change from then on; `state/cli.py show|list` display it. Gate (f) needs nothing more than the row above: per-finding triage is the whole gate, and closing an incident intent PR both dismisses the finding (its signature suppressed, step 39, B5) and abandons its change.

**Gate (e) is derived from the merge, never written to `main`** (build guide step 32; decision 13). The automation identity has branch-only write access, so nothing records the owner's merge in `status.yaml`. Instead every reader that opens a `status.yaml` from the default branch (`state/status.py read_status(..., on_default_branch=True)`: the release workflow, `state/cli.py show|list` on the default branch) reads a change at phase (e) as gate (e) `passed`, "merged by the owner", and any park lifted. The file itself is unchanged. **The release itself runs once per change, and only on a copy gate (e) judged** (0.3.1, issues #66 and #68; `release/cli.py`): the deploy run sets phase (e) at its start, before the REVIEW.md pass, so a build PR merged while that run is still running carries phase (e) and no gate (e) result — the release skips it (the sample's change 0002 released such a merge, PR #17, and then the run's second build PR again) and releases the pull request the run opens afterwards, which carries the result; a merged copy whose `gate-e.json` still carries the deferred `commands` mark (a job that died between the session and the runner's step, issue #91) is skipped the same way, as the runner's guard skips it for the next phase; a merged copy whose gate (e) parked (a risk-list hit, a guardrail change, the iteration cap) has its park reason printed in the release log and waits for `sdlc:release-approved`, whether or not the project declares production (the merge alone lifted every park before, with no second look and no mention of it); and after `deploy.command` exits 0 the workflow's second job, `record` — the only one with a write token; the release job, which runs the project's toolchain and command, keeps a read-only one — commits `released_at`, `released_sha` and `released_pr` into `status.yaml` on top of the change's work branch `sdlc/<id>/c` and pushes it there and to the ref `refs/sdlc/released/<id>`, which no branch deletion removes and no pull request comes from — never on the default branch — so a second merge of the same change, the `labeled` event or a dispatch finds the record (in the merged copy, on the ref or on the branch) and releases nothing again. A remote the release cannot read is exit 2, never a release (fail closed); a record that cannot be pushed is red, so a release that ran without its record is seen. Nothing is recorded for `deploy.action: none`, an empty command or a failed command: nothing ran, and a dispatch may retry. A mixed change — runs recorded before 0.3.1 and after — counts only the ledger's entries once it has any.

**Release approval** (build guide step 29; decision 13; article p.35–37, adapted). Approval exists when the owner has applied the label `sdlc:release-approved` on the build PR: the framework reads the actor of the last `labeled` event from the PR's timeline, never from an environment variable (the article's p.36 example reads `$RELEASE_APPROVAL`), and a label applied by the automation identity or by any `[bot]` account does not count. The label is the only form: a signed tag was considered and rejected, because a session that may run `git` can sign a tag itself, so a tag is not an owner-only act (decision 5: the automation identity separates what the run did from what the owner approved, so a run cannot approve itself; decision 11 is park-never-page); the same rule makes the hook block any command that names `sdlc:release-approved` (`gh pr edit --add-label`, the REST endpoint, a script) — the label is applied on GitHub by the owner. It is required only when `sdlc.yaml: deploy.production` is true. The PR it is read from is the change's own build PR as `status.yaml` records it (`build_pr`, written by `pr/cli.py upsert` when the PR of `sdlc/<id>/c` is opened or found and committed by the runner, since 0.2.27): the release workflow refuses an event PR that is not the recorded one, and the hook accepts the recorded PR only while it is that change's (head `sdlc/<id>/c`) and the checkout is the PR's own head commit (open or merged) or its merge commit — before, the hook found "the most recent PR from the current branch's name", merged or closed, so a checkout of any `sdlc/<id>/c` rebuilt with any commits inherited that change's label (the 1.0.0 readiness review, group B); the check binds the committed content, not the working tree; a change whose `status.yaml` records no build PR is not approved until the next `upsert` records it. Two things read it: the release workflow before it runs `deploy.command` (and only for the build PR, head `sdlc/<id>/c`), and the production-gate hook (`plugin/hooks/production_gate.py`, PreToolUse on `Bash` and `PowerShell`) inside any Claude session on the project, which guards the command patterns of the project's adapter (`plugin/hooks/production_gate.py: DEFAULT_GUARDED` per `deploy.action`, plus `sdlc.yaml: deploy.guarded_commands`, plus the article's own trigger: a command naming both `deploy` and `production`), matched against every part of a chained or wrapped command, the program read by its bare name (a path, `.exe`, `.cmd`) and with the options between it and its verb dropped (`terraform -chdir=x apply`, `kubectl --context p apply`, `gh -R o/r release create`; 0.2.27). The hook only allows or blocks, never asks (the article's p.35 prose prefers a hook that asks; the run is unattended, so the block text carries the route: the owner applies the label on the build PR, then re-runs), fails closed when the approval cannot be verified, and finishes inside its own timeout because a hook that reaches the timeout does not block (NOTES §8). Every allow and block decision is one timestamped JSON line in `changes/<id>-<slug>/evidence/hook-log.jsonl` (fallback `changes/.hook-log.jsonl`; `SDLC_HOOK_LOG` overrides), article p.37. The hook is inert when `deploy.production` is false.

### 4.1 Composition of the phase runs (build guide step 24; B3)

Every run is one slash command (`/sdlc-design`, `/sdlc-build`, `/sdlc-test`, `/sdlc-deploy`), by hand or as a `claude -p` job. The same skeleton for all: **register** (`gate/cli.py start-run`, the wall clock) → **work** → **commit** on the phase's branch (`state/cli.py commit-phase`) → **adversarial verdict** for HEAD (`sdlc:adversarial-reviewer`, fresh context) → **panel** under deferred review (`panel/cli.py items`, three fresh contexts per item, `panel/cli.py record`, which commits the decision; after the last item the verdict is re-run once for the new HEAD, and nothing else is committed before the gate) → **gate** (`gate/cli.py check`: `continue` / `wait` / `park`, writes `evidence/gate-<phase>.json`) → **commit the evidence** → **surface** (open or update the PR with the ≤5-bullet summary, apply the label the gate printed) → **hand over** (a `continue` dispatches the next run; a `wait` or `park` stops). A run never asks the owner anything: a gap is a flagged concern, a parked reason or a review comment. Re-running a command on the same branch is safe and is how review comments are applied (`/sdlc-fix` re-runs the phase with the comments as constraints and bumps `status.iterations`).

| Phase · command | Inputs (as the owner approved them) | Branch | Work, in order | Artifact | Exit |
|---|---|---|---|---|---|
| (b) `/sdlc-design` | `intent.md` as merged at (a) | `sdlc/<id>/b` from the default branch | policy skills loaded → `spec.md` (prompt v1, p.14) → read-only planning run → `plan.md` → commit → verdict → panel (deferred review) → gate (b) | `spec.md`, `plan.md` | `wait` in every profile, PR with `sdlc:b-ready`; the owner's merge starts (c). A park still opens the PR (`sdlc:needs-human`, "what I need from you") |
| (c) `/sdlc-build` | `spec.md` + `plan.md` as merged at (b) | `sdlc/<id>/c` from the default branch; the build PR lives here through (d) and (e) | preflight → permission mode (`acceptEdits` only when it allows; never bypass) → fix-type: the reproducing test first, committed, shown to fail → implementation under the hooks, `plan.md` updated in the same commit when the work departs from it → code-simplifier → verifier → `evidence/verifier.md` → commit → verdict → panel → gate (c) | the diff and its tests; `evidence/verifier.md` | Standard: `continue` → (d); the PR is opened as a draft. Full: `wait`, `sdlc:c-ready`; approving review + `sdlc:c-approved` starts (d) |
| (d) `/sdlc-test` | the build branch after gate (c) | `sdlc/<id>/c` (same PR) | fresh context → `evidence/collect.py` runs the three `sdlc.yaml` commands into `test.log`, `build.log`, `lint.log` (in CI, since 0.3.2, it leaves a deferred mark in each and the runner's step after the session writes the three logs from its own run of the targets and re-judges the gate; a red target parks there) → a failing target is fixed and re-run (each round bumps `iterations`; the cap parks; not in CI, where the session never sees the targets' result) → screenshot loop against the mock when `plan.md` Proof names one → verifier → `evidence/verifier.md` → commit → verdict → panel → gate (d) → check-run summary | `evidence/` | Standard: `continue` → (e). Full: `wait`, `sdlc:d-ready`; approving review + `sdlc:d-approved` starts (e) |
| (e) `/sdlc-deploy` | the build branch after gate (d) | `sdlc/<id>/c` (same PR) | the release artifact prepared per the adapter and committed, nothing executed (`publish package`: the build artifact and the version bump; `regenerate report`: the report; `schedule job`: the schedule entry; `promote to paper trading`: the promotion record; `deploy service`: the manifest or changelog; `none`: nothing; an artifact outside the change folder is listed in `plan.md` in the same commit) → review pass in a fresh context with `REVIEW.md` → `evidence/review-findings.json` (in CI the review step of the deploy job has already run this pass on the branch as (d) left it, §4.2, so the command re-runs it only when HEAD moved since that pass — the release artifact's commit, an incident's lesson and eval, a panel's commit; the findings file names the commit it judged and a stale one is re-requested; the order PROGRESS session 4 built: the artifact before the pass the command runs, after the pass CI runs first) → fix loop while an Important finding stands and the cap holds (`/sdlc-fix` semantics: fix, re-run (d)'s collection, re-review; under deferred review a finding the run cannot fix goes to the panel) → gate (e), which judges HEAD with the release artifact in it → `release/notes.py` writes `evidence/release-notes.md` (commits since the base, evidence status, findings tally, links), committed with the gate evidence → PR summary regenerated (findings by severity, plan conformance, counters, the release note) | reviewed PR, ready for review, `sdlc:e-ready`, `evidence/release-notes.md` | always `wait` (human in every profile); the owner's merge is the gate and starts `sdlc-release.yml`; with `deploy.production: true` the PR body says the release label is the second act |
| (f) `/sdlc-maintain` | `evidence/detection.json` as the detection script filed it (or a scan finding, §4.2 `sdlc-scan.yml`), `bands.yaml`, `lessons/` | `sdlc/<id>/a` of the incident change the detection filed (`entry_route: incident`; the change stays at phase `f` there: the owner's merge of its PR is gate (a), decision 25) | read `lessons/` and the detection record first → investigate read-only (the bands' diagnose tools: `Read,Grep,Bash(gh run view *)`, plus `Glob`, `Write`, `Bash(gh run list *)`, `python`, `git`; never `Edit`) → `intent.md` in the incident shape (skill `intent-template`, `## Evidence` required) + `evidence/proposal.json` (the route: `pull_request` at 2σ; at 3σ a listed runbook with its arguments) → commit → `detect/cli.py dispatch` (deterministic: validates the proposal against the **default branch's** `bands.yaml` and `sdlc.yaml` — an edit in the session changes no authorization —, resolves the authorization — decisions 14 and 26; a forced finding never pre-approves a runbook — and runs a pre-approved runbook now on a branch of its own, its PR opened; records `go-requested` for a `go` route; in CI this is the workflow's own step after the model's, `detect/cli.py finish`, where a project runbook's secrets live) → commit → gate (f) (`artifacts` with Evidence, `design_scope`, `guardrails`, `risk_list`, `detection`, `route`; no toolchain, no verdict, no panel) → evidence commit | `intent.md`, `evidence/proposal.json`, `evidence/runbook-<name>.json` | always `wait` (human in every profile): the intent PR opens with `sdlc:f-ready` and `incident`, or parks with `sdlc:needs-human` ("Go requested": apply `sdlc:go`; a failed runbook; a refused proposal). Gate (f) = the owner's triage (§4): merge, `schedule`, close with a comment |

Rules the table relies on. **Wait sits where the label is read**: in the Full profile the (c) and (d) runs stop after the gate; the owner's label starts the next run (CI: the `labeled` event; by hand: the next command). **Evidence is committed after the gate** so the verdict judges the artifact commit; each phase produces its own verdict. **The PR is the audit record** (p.34–35): opened at (c) as a draft in every profile, marked ready at (e), never split. **Iterations are one counter per change** (`status.yaml: iterations`, bumped by every fix round in (c), (d), (e) and `/sdlc-fix`; the cap of `sdlc.yaml: gate` applies to the sum, and the owner resets it with `set-iterations`); `set-iterations`, `accept-risk` and `unlock-tests` are owner actions (§8; decisions 5 and 24: the automation identity's commit or label never counts as the owner's act) and the gate's `owner_actions` check parks when a run's own commit introduced them (the test-lock lift since 0.2.25: until then only the hook read `tests_locked`, so a run that set it to false, turned the fix into a feature or ran `unlock-tests` itself edited the frozen tests unnoticed; the gate's `test_lock` check, the same version, refuses a committed change under `test_paths` between the lock commit and HEAD while the lock stands, which the hook — edit tools only, the working tree — cannot see; a lift or an acceptance whose recorded actor the run wrote itself is the runner's to catch since 0.2.26, §6; the check judges every commit that gained a risk item, not the newest only, and a drop of `panel_calls` like a drop of `iterations`, since one label resets both). **Nothing in a run edits guardrail files or `intent.md`** — with one exception (decision 22): a fix round on the *unmerged* intent PR applies the owner's review comments to `intent.md`; once merged at gate (a) the intent is never edited again (the gate's `guardrails` check refuses it). **Spend is known only in CI**: `record-spend` is fed by `run_phase.py` from the `claude -p` result; a by-hand or cloud-session run has no spend figure, so `gate.max_budget_usd` binds unattended runs only, while iterations and the wall clock bind every run.

### 4.2 Merge-triggered workflows (build guide step 30; decisions 1, 5; B3)

One workflow per transition, installed into the project by `/sdlc-init` from `template/.github/workflows/`; every step is `python` or `claude`. Rules. **Events from the workflow token never start these workflows** (GitHub: only `workflow_dispatch` and `repository_dispatch` do), so the hand-over column is an explicit `workflow_dispatch` with the change id; the owner's merges and labels fire normally. **Concurrency is keyed on the change's work branch**: `group: sdlc-${{ inputs.head_ref || github.event.pull_request.head.ref }}`, `cancel-in-progress: false` (GitHub keeps one running and one pending run per group); every dispatch passes `change_id` and `head_ref` (the next phase's work branch, `sdlc/<id>/b` or `sdlc/<id>/c`), and a merge- or label-fired run keys on the PR's head branch, so all runs of one change serialise. The abandon and runbook workflows have their own groups, `sdlc-abandon-<head ref>` and `sdlc-runbook-<head ref>` (0.2.22): a close without a merge also fires the merge-guarded design and build workflows, a label event also fires the fix, test and deploy workflows whose guards skip, and on a shared group GitHub displaced one pending run at random (live, the sample's PRs #34 and #35, 2026-09-25); the abandon run is the only writer of the end state (decision 25) and the Go must never be the run displaced (decision 14). A merge-fired design or build workflow starts for every merged PR: a 20-second "find the change" step (`run_phase.py --find-change`) reads the PR's files and ends the job green when they touch no `changes/<id>-<slug>/` folder, before any install; the earlier head-name rule missed intent PRs pushed from a web session. **Permissions per job**, least privilege, and no deploy or runbook secret in any step that runs a model: the phase jobs (design, build, test, deploy, fix) declare `contents: write`, `pull-requests: write`, `issues: write`, `checks: write` and `actions: write` (build, test and fix use the last to dispatch the next workflow; design and deploy carry it too and dispatch nothing); the detect job the same but `actions: read` (it reads the runs API and dispatches no workflow); the abandon job `contents: write` and `pull-requests: write`; the runbook and scan jobs `contents: write`, `pull-requests: write` and `issues: write`; the digest `contents: read`, `issues: write` and `pull-requests: read`; the release job `contents: read`, `pull-requests: read` and `issues: read` (the project's own toolchain and `deploy.command` run there and must not be able to push), and the release workflow's second job, `record`, `contents: write` alone (0.3.1, issue #66: it runs the framework's record step and nothing of the project's); the evals job `contents: read`. The project's own secrets reach three steps only, and only when the owner adds them to that step's `env:` — the release step (`deploy.command`), the detect job's `finish` step and the runbook job's Go step (a project runbook with a command). **Every step that runs a phase names the default branch** (`SDLC_DEFAULT_BRANCH` in its `env:`, since 0.2.25; before, only the pin step did, and a project whose default branch is neither `main` nor `master` parked at every gate with "no base branch", because a runner checkout has no `origin/HEAD` to guess it from). **The pinned framework** is checked out from `luissiviero/sdlc-framework` at the version the **default branch's** `sdlc.yaml` pins (`sdlc_pin.py --ref refs/remotes/origin/<default>`, since 0.2.17; the ref fully qualified and the script itself read from the default branch's copy — `git show <ref>:.github/scripts/sdlc_pin.py | python -`, the one `run:` line that is not plain `python`, under `shell: bash` so a failed `git show` fails the step instead of piping an empty script — since 0.2.24, because a tag named `origin/<default>` would shadow the short refname; on a `pull_request` event GitHub runs the head's own workflow file, so this closes the script's copy only, not the workflow's; a public repository, no token) and loaded with `--plugin-dir`; hooks and permissions come from that checkout (decision 6 layer iii). **A job whose two steps share one checkout across a model's session checks the framework out again between them** (the deploy job's review pass and phase (e), the detect job's phase (f) and `finish`; 0.2.27, the review of the 0.2.26 diff, M4): the framework tree the session could reach is removed (`python -c "import shutil; shutil.rmtree('framework', …)"`) and checked out afresh by the runner's own `actions/checkout` at the pin the first step read (a step output, which lives in the runner) — a check of a tree the session controls is defeated by `update-index --skip-worktree`, a moved tag, a planted `__pycache__` or a planted verifier on the local ref (the review of the 0.2.27 diff) — and then `plugin/ci/checkout_check.py`, run from that fresh copy, refuses a `remote.origin.url` that is not the repository or a fetch refspec that is not the default, any `url.*.insteadOf`, `include`, `core.hooksPath`, `core.fsmonitor`, proxy, `pushurl` or command-running key in the project's local config (the redirect keys in the global one too), a framework commit that is not what the framework's origin carries for the tag (`ls-remote`), and a pin the default branch does not carry after a fetch by the repository's URL — exit 3, the job red before the step that holds the secrets. What stays open, recorded: git reads the project's local config for every command, so a key the denylist does not name could still run something (a fresh clone of the project itself would close it; a roadmap candidate), and the head's workflow file on a `pull_request` event stays GitHub's rule (above). The pin is the project's, not the branch's: a phase branch carries the `sdlc.yaml` it started from and a PR may stay open across several releases, so read from the head it would run the framework it was created under for its whole life (the first overturn rounds on the sample repository, 2026-09-24, ran 0.2.14 on `sdlc/0002/b` while `main` pinned 0.2.16) — the same rule as the run's configuration, which the gate already reads from the base branch's copy. ## 5. Change requests

At any human gate, "ask for changes" = review comments on that PR, submitted as a "Request changes" review. That submission starts the fix round by itself (decision 22): `sdlc-fix.yml` runs `/sdlc-fix <id>` on the PR's own head, which reads the unresolved comments and failing checks, re-runs the phase with them as constraints, and pushes to the same branch. This applies to intent, spec+plan and build PRs alike — on the unmerged intent PR the round corrects `intent.md` without re-running the brainstorm — and no owner-launched command is needed; `/sdlc-fix` stays for by-hand runs. A review submitted by the workflow token, any `[bot]` account, or anyone who is not a member of the repository (`author_association` other than `OWNER`, `MEMBER`, `COLLABORATOR`) starts nothing.

## 6. Park, never page

When a confidence gate fails (under deferred review: on anything but the fixed list the panel settles, §3), a run limit is hit (iterations, wall-clock, budget, pause flag), or a risk-list item is touched (auth, data migrations, money movement, production config), the run **parks**: it finishes every artifact it can, writes a "what I need from you" section into the PR description, records the reason in `status.yaml`, labels the PR `sdlc:needs-human`, and notifies nobody. Parked and finished work waits in the review queue. The owner un-parks by settling the item on the PR (decision 24): a "Request changes" review (→ the fix round), or one of three labels — `sdlc:accept-risk` (accepts the risk-list hits the last gate reported), `sdlc:reset-iterations` (the fix-iteration and panel-call counts back to 0 after either cap), `sdlc:unlock-tests` (thaws the test-file lock of a fix-type change). Each label starts the fix round, which performs it, records the label's actor in `status.yaml` (`risk_accepted_by`, `iterations_reset_by` with its stamp `iterations_reset_at`, `tests_unlocked_by`), removes the label from the PR (one application is one act) and re-runs the phase; a label applied by the automation identity or a `[bot]` is rejected and left where it is, and the gate's `owner_actions` check re-judges the recorded actor. The gate believes a recorded actor that is a person, and the session can write `status.yaml`, so in CI the runner (`ci/run_phase.py`, loaded from the pinned framework checkout the session cannot edit) is the check (since 0.2.26, choice 103): it reads the owner-only fields right before the `claude -p` session — its own label handling included — and again right after, and a `risk_accepted_by`, `tests_unlocked_by` or `iterations_reset_by` entry the session added that the runner did not record and the default branch's copy does not carry, or an `iterations` or `panel_calls` count lower than before the session, restores the fields to their pre-session values and parks the change before any commit of the run (`owner_fields` in `evidence/gate-<phase>.json`, naming the field, the session's value and the expected one); a change of `profile_override` or `review_override` on the branch is reported, never honoured (§3). By hand the gate's commit-author rules are the check, as before. The CLI commands `accept-risk`, `set-iterations` and `unlock-tests` stay for by-hand runs (their commit author is the act); `paused: false` stays in `sdlc.yaml`, because pausing is a reviewed change. `paused` and `deploy.production` are booleans: `yes`, `on` or a quoted word is a string to YAML 1.2, and since 0.2.26 every reader (the gate's `limits`, the preflight, the runner's guard, the production-gate hook, the release workflow) fails closed on it instead of reading it as unset.

## 7. Review queue

The queue is the PR list filtered by `sdlc:*-ready` (a run stopped at a human gate) and `sdlc:needs-human` (parked). Every PR the framework opens or updates starts with a ≤5-bullet summary: what changed and why, evidence status, review findings by severity, plan conformance, and — if parked — what is needed; under deferred review "Decisions taken for you (N)" stands above the bullets, one line per panel decision of the phases the PR covers, and a review comment on a line overturns it. A scheduled job rewrites the body of one pinned issue ("SDLC review queue") with the digest. Nothing pushes to the owner: the framework never comments, assigns, @mentions or requests a review; the owner sets the repository watch to "Participating and @mentions", and may turn off GitHub's default e-mail for failed Actions runs — a parked phase is a green job by design (only an infrastructure failure is red).

## 8. Conventions

- One folder per change: `changes/<id>-<slug>/` with `intent.md`, `spec.md`, `plan.md`, `evidence/`, `status.yaml` (phase, profile override, change type feature/fix, entry route idea/ticket/incident, gate result, parked reason, iteration count, external reference; since 0.3.1 the release record `released_at` / `released_sha` / `released_pr`, written by the release workflow on the work branch, issue #66). `<id>` is a four-digit sequence allocated from the folder (`0000` is the framework's own installation); `<slug>` is the kebab-case title. `plugin/state/` is the only writer.
- Branches `sdlc/<id>/<phase>`: `a` carries the intent PR, `b` the spec+plan PR, `c` the build PR that stays open through (d) and (e). A fix round runs on the PR's own head, which for an intent PR pushed from a web session is a `claude/…` branch. Labels `sdlc:<phase>-ready`, `sdlc:<phase>-approved` (Full only), `sdlc:release-approved` (the owner's release approval on a declared production, §4), the owner's un-park verbs `sdlc:accept-risk`, `sdlc:reset-iterations`, `sdlc:unlock-tests` (§6), `sdlc:needs-human`; phase (f): `incident` (every intent PR the maintain loop or the security review opens: the triage queue is the set of open PRs carrying it, step 39), `schedule` (the owner's "not now"; nothing runs), `sdlc:go` (the owner's per-incident authorization of a runbook whose route says `go`, decision 14; read by `sdlc-runbook.yml`, performed once and removed). Every label is created by the first CI run (`run_phase.ensure_labels`); the gate labels are exclusive (one at a time, set by the PR upsert), the owner's labels are never removed by an upsert. `status.yaml: phase: abandoned` is the end state of a change whose PR was closed without a merge (§4). An incident change stays at phase `f` on `sdlc/<id>/a` until its intent PR is merged (the design workflow reads a merged change at `f` as at `a`); its PR title is `maintain(<id>): …`.
- `evidence/` also holds the run's own records beside the toolchain logs: `diff-<phase>.patch` (the merge base…HEAD diff the adversarial reviewer judges — the reviewer has no shell, the run writes the diff and passes HEAD's sha), `release-notes.md` (phase (e)), `hook-log.jsonl` (the hooks' allow/block decisions), `decisions-<phase>.json` and `.md` (the panel's ledger, decision 21) with the members' files under `evidence/panel/`, and for an incident change `detection.json` (the finding as the detection script recorded it: metric, tier, rule, mean, sigma, the latest point, the failed runs, the default branch's commits in the breach window, `forced`) or `scan-finding.json` (a security review's finding: signature, class, bounded), `proposal.json` (the diagnosis's route) and `runbook-<name>.json` (what the runbook did, or `go-requested`), all committed with the evidence commit; and the CI runner's own records, `claude-<phase>.json` + `.stderr.txt` (the headless run's result and stderr, one file per run: the second run of a phase — a fix round, a re-run — is `claude-<phase>-2.json`, and so on) and `run-<phase>.json` (start time, the last session's spend) with `spend.json` (the change's spend ledger since 0.3.1, issue #71: one entry per run — the review pass and each fix round their own — and the total the budget cap is compared with), which the runner stores after a run ends and commits under `run(<phase>): …`; they describe the run that produced them, never the diff a later reviewer judges.
- The repo is the source of truth for every artifact; any external tracker holds the issue number ↔ commit SHA link.
- `plan.md` is produced at the end of phase (b) by a read-only run (Read/Grep/Glob only) and approved with `spec.md`; the implementation run of phase (c) is the first run with edit and shell tools on source. (Phase (a) writes only `changes/<id>-<slug>/intent.md`, interactively with the owner — or, in a fix round on the unmerged intent PR, from the owner's review comments, decision 22.) In (c) a hook on `git commit` denies a commit that changes source without changing `plan.md` in the same commit.
- Process content (commands, skills, agents, hooks, gate logic) lives in the plugin, pinned per project by version; project content (`CLAUDE.md` body, test commands, protected paths, `sdlc.yaml`, `REVIEW.md`, `bands.yaml`, `evals/`) lives in the project.
- Every hook, gate check, detection script and eval check is Python with no third-party dependency; one task runner works on Windows and Linux. Hooks are registered in exec form (`python` plus the script path), so no shell is involved on any platform. A hook reads its JSON input from the byte stream as UTF-8 and the CLIs whose output a model reads write UTF-8 (0.2.25): Windows' console encoding is not UTF-8, and a text-mode stdin turned a project path with an accented letter into one no protected path matched, so the hook allowed the edit. Until B3 the phase commands run by hand, on the owner's PC or in a Claude Code cloud session; from B3 they run in GitHub Actions under the automation identity.
- Test-file lock for fix-type changes (build guide step 25; article p.28 step 4, p.35): in a change whose `status.yaml` says `change_type: fix`, the build run writes and commits the reproducing test first and then sets `status.yaml: tests_locked: true`; from that commit until the owner's merge the plugin's PreToolUse hook denies every edit under the project's test paths on the `sdlc/<id>/c` branch (phases (c), (d), (e) share it), and `REVIEW.md` rejects a diff that touches a pre-existing test in a fix task. Test paths are `sdlc.yaml: test_paths` (globs; `/sdlc-init` writes the defaults for the detected language). Only the owner unlocks (`state/cli.py unlock-tests`, or the `sdlc:unlock-tests` label, §6), in a reviewed PR, when the test itself was wrong; the gate's `owner_actions` check parks a lift that a run's own commit introduced without a recorded owner actor (0.2.25).
- Guardrails protect themselves in three layers (decision 6). (i) The protected-path hook in the plugin covers `.claude/**`, `CLAUDE.md`, `REVIEW.md`, `sdlc.yaml` (the copies at the project root; a same-named file in a subdirectory is project content unless `protected_paths` lists it) and the plugin's own files, and a Bash/PowerShell command that would write to the same paths (`plugin/hooks/shell_guard.py`, change 0002), with `Edit(...)` deny rules in the project settings as a second net; the hook has no exception. The only sanctioned writer of guardrail files in a run is `/sdlc-init`'s install script, which only adds (rules, keys, sections) and whose output rides in the change-0000 PR — with the workflows and the pin script under `.github/` and `lessons/` (the commit of `/sdlc-init` step 5 lists them since 0.2.25; before, a project set up by the book merged with no automation); every other guardrail change is made by the owner in a reviewed PR. (ii) On the owner's machine a *managed* settings file (system path, see `docs/owner-machine/`) sets `allowManagedPermissionRulesOnly` and `allowManagedHooksOnly`; because those keys ignore project permission rules and block non-managed plugin hooks, that file also carries the permission rules and force-enables `sdlc@sdlc-framework`. Cloud sessions never read it: there, the repo's `.claude/settings.json` and the plugin it declares are the layers. (iii) CI loads hooks and permissions from the pinned plugin, never from the PR branch, and the sandbox's `filesystem.denyWrite` block in `plugin/ci/settings.ci.json` (change 0002) is CI-pinned content the same way, carrying one more block beside hooks and permissions. Bypass-permissions mode is never used and is disabled in every settings file.

## 9. Phase adapters (per project, in `sdlc.yaml`)

- `profile`: standard | full (lite was removed in 0.2.14, decision 21; a file that still says it reads as standard)
- `review`: parked | deferred — whether a judgment item of the fixed list parks the change or goes to the review panel (§3); `panel_advocate_model`: the model alias of the devil's advocate (default `opus`)
- `commands.build` / `commands.test` / `commands.lint`: the one-command targets that exit non-zero on failure (detected or created by `/sdlc-init`); the framework refuses to enter phase (c) without them
- `protected_paths`: the project's own frozen paths, added to the always-protected set
- `risk_list`: touching any item parks the change at its next gate (default: auth, data migrations, money movement, production config)
- `plan_sync.exempt`: globs (besides `changes/**`) whose changes do not require a `plan.md` update in (c); `hooks.format_on_edit`: switch for the formatter hook
- `paused` and `gate.*` (`max_iterations`, `max_iterations_non_routine`, `max_panel_calls`, `max_wall_clock_minutes`, `max_budget_usd`, `command_timeout`): the run limits every gate enforces; a limit hit parks with the partial evidence
- `bands.yaml` (next to `sdlc.yaml`): the control bands of phase (f) — metric, source, baseline (`rolling_<N>d`), rules (`western_electric`), the three σ tiers (1σ `log`, 2σ `diagnose` with its `tools`, 3σ `propose` with its routes) and, per 3σ route, `authorization: preapproved | go`; optional `direction: above | below | both` and `min_sigma` (`plugin/detect/stats.py`). Project content the owner tunes in a reviewed PR: a dismissal never rewrites it (step 39)
- `commands.setup`: the one command that installs what the three targets need; every CI phase job runs it before the phase (`plugin/ci/project_setup.py`); empty = nothing to install
- `test_paths`: the globs of the project's test files that the test-file lock freezes in a fix-type change (§8)
- `automation_identity`: the login(s) whose commits and label applications never count as the owner's act (default `github-actions[bot]`); read by the gate's `owner_actions` check and by the release approval
- `plugin`: name, marketplace and pinned version of the process in force; `plugin.claude_code`: the Claude Code CLI version the phase jobs install (the framework's minimum is 2.1.278)
- `deploy.action`: what makes a merged change live (publish package · schedule job · regenerate report · promote to paper trading · deploy service · none)
- `deploy.command`: the one command `sdlc-release.yml` runs after the owner's merge (and, with a declared production, after the release approval) — e.g. `python -m build && twine upload dist/*`; empty = the release is prepared in the PR and nothing runs. It runs on the GitHub runner with the repository's own secrets; the framework holds no deploy credential
- `deploy.production`: true/false — turns on the release approval (§4): the release workflow waits for it, `/sdlc-deploy` says so in the PR body, and the production-gate hook guards the adapter's commands inside Claude sessions
- `deploy.guarded_commands`: shell-style patterns the production-gate hook blocks until the approval exists, added to the plugin's defaults for the adapter; read only when `deploy.production` is true
- Deploy, status and rollback as tools (build guide step 31; article p.40 step 4 "Deploy, status, and rollback become tools"): not built. The plugin ships no runtime dependency (§8) and no project has named a real deployment yet, so the interface is recorded here and built when an adapter needs it: three MCP tools, `deploy(change_id)` (runs `deploy.command` for a merged change and returns the run record), `status(change_id)` (the last release's outcome and the current metric from `maintain.source`) and `rollback(change_id)` (runs the `rollback` runbook of `maintain.runbooks`); every call passes through the production-gate hook, so on a declared production none of them runs without the release approval, and `rollback` is the pre-approved runbook only under decision 26 (B5). Until then the release workflow is the one deploy route and the DORA measures come from the CI system and the deployment tooling, as the article says (p.41), not from the framework
- `maintain.metric` and `maintain.source`: the watched metric and where the detection script reads it (default for every new project: CI test failure rate from the CI API)
- `maintain.runbooks`: the project's own runbooks, each with a `name` (what a `runbook:<name>` route of `bands.yaml` refers to), a `command` (no shell; `&&` steps; run on the runner with the repository's own secrets) and `authorization: preapproved | go` — CI-scoped reversible actions are pre-approved, anything touching a running system waits for the owner's "Go" as a parked item (decision 14); a `go` here is stricter than the bands' value and wins. The plugin ships two runbooks that need no entry: `quarantine-flaky-test` (adds `--deselect <node id>` to pytest's `addopts` on a branch and opens the PR; never edits the test; Python projects only) and `revert-pr` (`git revert` on a branch from the default branch and the PR; never merges). `rehearsed_at` (decision 26): on a project with `deploy.production: true`, a runbook whose name contains `rollback` and whose `rehearsed_at` is a date the owner set after a staging rehearsal is pre-approved whatever the two files say
- `lessons/` (the incident record, step 36): one file per incident, `lessons/<yyyy-mm>-<slug>.md`, written when the fix ships (the (e) run of an incident change, §4.1 step 0b) and read before every diagnosis; `evals/cases/<id>-<slug>/` (the eval of that incident, step 35) beside it. Both are project content. Each lesson opens with a frontmatter block (type, title, description, tags, change, detected, fixed, generated, status, stale_after, sources) a script can follow, and `plugin/lessons/index.py` keeps a generated `lessons/index.md` (a heading per tag, `## Retired`, `## Unsorted`) that the (f) run reads first so it opens only the lessons its tags name.
