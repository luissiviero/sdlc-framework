# Operating model

> The loop keeps running. Human judgement stays above it. — *The AI-Native SDLC playbook*, p.50

This file is the first artifact of the framework (build guide step 1; finalised in session 1). It states what the framework does, which artifact every phase commits, when a human is involved, and how change requests flow. Everything else in the repo implements it. Rationale and article citations live in `docs/BUILD_GUIDE.md`; the choices behind it in `docs/decisions/index.md`, one file per decision; platform facts verified against the Claude Code docs in `docs/notes/index.md`, one file per section.

## 1. Purpose

A framework that connects to any GitHub-hosted project (any size, any type: service, library, research code, data pipeline; GitHub only, decision 23: every trigger, the automation identity, the labels, the check runs and the digest issue are GitHub-specific, and `/sdlc-init` refuses an `origin` on another host) and drives each change through six phases:

| Phase | What runs | Artifact committed | Read by |
|---|---|---|---|
| (a) plan | interactive brainstorm with the owner | `intent.md` | (b) |
| (b) design | autonomous: spec pass with policy skills, then a read-only planning run | `spec.md` + `plan.md` | (c) |
| (c) build | autonomous: implementation under auto-accept with hooks, simplifier, verifier | the diff and its tests, on the build PR | (d) |
| (d) test | autonomous: fresh-context full run — tests, build, lint, screenshots, verifier | `evidence/` + PR check run | (e) |
| (e) deploy | autonomous: review passes, fix loop until green, release prepared per the project's adapter | reviewed PR / release | production |
| (f) maintain | standing loop: deterministic detection → diagnose → propose | incident record (`lessons/`) → new `intent.md` | (a) |

Principle (article p.6–8): every phase ends by committing its artifact; the accepted artifact fires the next phase. The chain of commits is the audit trail.

## 2. Roles

One person owns every role the article names (originator, product owner, tech lead, engineer, code owner, release manager, service owner). Separation of duties is therefore rebuilt from:

- **writer ≠ judge** — the agent that produced an artifact never judges it; a different agent in a fresh context reviews it, and only the owner approves;
- **an automation identity** distinct from the owner's account for every non-interactive run (the project's GitHub App when the repository variable `SDLC_APP_ID` is set, else the CI workflow token; decision 5 as amended by 33), so the log separates what the agent did from what the owner approved;
- **branch rules** — only the owner's account can merge to `main`, and since 1.0.18 the merge App, only on the owner's approving review (decision 36); the automation identity has branch-only write access; no bypass rights. The rule is a GitHub branch ruleset on the default branch that the owner creates by hand (decision 4; `/sdlc-init` §6 says how): *Restrict updates* with the repository admin as the only bypass actor besides the merge App — the one form that keeps a merge to the owner, because the automation's token (the workflow token, or the project's GitHub App's, decision 33) holds `contents: write` and the phase session may run `gh`, so a rule that only requires a pull request or only stops direct pushes still lets the token merge; a classic protection rule on a user-owned repository cannot restrict who pushes at all. The owner's bypass mode is *Exempt* (since 0.2.26; NOTES §17, verified 2026-09-27): the rules do not run for the owner, so a merge from the GitHub mobile app goes through on a tap although the app still labels the pull request "Unable to merge" (it shows the general merge state, `blocked` for everyone the rules apply to); under "Allow for pull requests only" the app showed the same label with no bypass control and the owner merged from the web UI through its bypass checkbox; `gh pr merge` refuses a `blocked` pull request whatever the mode (the REST merge endpoint through `gh api` does not). The cost of Exempt is no bypass audit entry for the owner's merges (the merge commit and `merged_by` remain the record); the rules still run for every other actor, the workflow token included. The project's GitHub App (decision 33) is never a bypass actor: the phase runners hold its token, and GitHub grants a bypass to an actor, not to a job. Since 1.0.18 (decision 36, choice 242 point 4) a merge App of its own is the ruleset's second bypass actor, in "for pull requests only" mode; it merges a build PR only on the owner's approving review, through `sdlc-merge.yml`'s deterministic step, and its key is a secret of the `sdlc-merge` environment, which only the default branch can use. A second ruleset requires only the `sdlc/review` check, which every pull request that is not a build PR receives as a passing "not a build PR", so an unreviewed build PR merges only through the web UI's bypass checkbox. The framework never creates either ruleset, because a session must not be able to, and nothing in the plugin blocks a push or a merge to `main` — the ruleset is the guard. Since 0.2.25 the daily digest (§7) opens with a notice while the default branch has no such rule (`pr/github.py default_branch_protection`: the branch's active rules must include an `update` rule; the 1.0.0 readiness review of 2026-09-26 found the framework's own `main` unprotected, and the sample's classic rule does not count).

## 3. Profiles — which gates are human

Set per project in `sdlc.yaml` by `/sdlc-init`; overridable per change in `changes/<id>-<slug>/status.yaml` (`profile_override`).

| Profile | Human gates | Automated gates | For |
|---|---|---|---|
| **Standard** (default) | (a) merge intent PR · (b) merge spec+plan PR · (e) approve build PR (the merge App merges it; decision 36); on the fast lane (decision 30, §4) the owner's own intent PR needs no (a) merge and (b) waits only for a non-routine plan | (c), (d) | most projects |
| **Full** | (a), (b), (c) review + label, (d) review + label, (e) approving review (+ release label) | — | live production, money at stake |

(Lite — gates (a) and (e) only — was withdrawn by decision 21 and removed in plugin 0.2.14: it took the human out of gate (b), which the article keeps human (p.14, p.15). A `sdlc.yaml` or `status.yaml` that still says `lite` reads as Standard.)

Automated gates are passed by the **confidence gate** (`plugin/gate/`, session 2): deterministic checks (artifact matches its template; no open flagged concern in `spec.md`; tests, build, lint green; evidence present; no Important review findings; `plan.md` ↔ diff consistent; no diff touching `.claude/**`, `CLAUDE.md`, `REVIEW.md`, `sdlc.yaml` unless the change is the framework itself — `intent.md` says `Framework change: yes`; no escalation by the gate's reviewer on a risk-list item — a risk-list hit itself never parks since decision 35 (plugin 1.0.15): it is reported in the gate record and shown in the "Needs your close look" banner of the PR the owner merges, and that merge accepts it; run limits) followed by the adversarial reviewer agent's verdict, written in a fresh context as `evidence/adversarial-review-<phase>.json`: *continue* or *escalate* (= park), required at (b), (c) and (d) in every profile. Since 1.0.14 (ROADMAP R7) the `panel_blind` hook writes `adversarial-review-<phase>.model.json` beside the verdict (the writer, the models of its transcript, the verdict's `head`, the time), and when `sdlc.yaml: adversarial_model` is set the gate's `reviewer_model` check parks a verdict whose writer was not the reviewer or did not run on that model; it is a hard park, never the panel's. Since 1.0.16 (ROADMAP R63) the runner also parks after the session, as `cli_model`, when the session's stderr carries a `[claude-code:unrecognized_model]` line for a model the run was configured with and the session result's `modelUsage` shows that model did not run: the pinned CLI ran that sub-agent on another model (NOTES §54), and the park names `plugin.claude_code` as the pin to raise. The gate runs inside the phase run itself (`gate/cli.py check` in the session, its verdict written to `evidence/gate-<phase>.json`) — except its `commands` check, which since 0.3.0 (issue #91, choice 133) a CI session's gate records as deferred and the runner runs after the model's session, outside Claude Code's sandbox (where `Read(**/.env*)` makes a nested `.env*` unreadable and a test suite that copies a fixture holding one fails), on the working tree the session left: `gate/cli.py run-commands` rewrites the record and `status.yaml` with the real runs, a red target (a non-zero exit or a timeout) at gates (c), (d) and (e) starts the next fix round by itself since 1.0.3 (at (a), (b) and (f) a round may not touch the code, so it parks as before; decision 29: the runner dispatches `sdlc-fix.yml` with the failing targets as the round's constraint, the PR carries `sdlc:fixing` instead of `sdlc:needs-human` while the record keeps its park and the check run stays red, and the change parks for the owner only at the iteration cap, §4.2 and §5), a missing target parks at once, a step that crashes or a target that does not start is re-run once and then parks, a session that fails after its gate or a step that cannot run parks it too (the session has already pushed the deferred record and labelled the PR), the runner's guard refuses to start the next phase on a record whose targets never ran, the step runs without the job's credentials, and a gate run by hand runs the targets itself; since 0.3.2 (item 3b) the same holds for the three command logs the `evidence` check reads at (d) and (e): inside a CI session `evidence/collect.py` runs nothing and leaves a deferred mark as each log's first line, the gate accepts the mark only while the runner's step is still to come, that step writes the three logs from its one run of the targets and re-judges the `evidence` check beside the `commands` one, and the verifier in a CI session reads the newest gate record and the logs instead of running the targets — and in CI the runner dispatches the next phase from that file: the (c) and (d) gates of the Standard profile are the run's own check, and the owner reviews their outcome at (e), on the build PR that carries the evidence, the findings and the plan conformance (the design, decision 18; the 1.0.0 readiness review of 2026-09-26 upheld it), while the runner keeps its own guards around the run — the guardrail check by the merge base's intent, the preflight, the label actor and, since 0.2.26, the owner-only fields of `status.yaml` (§6). The gate judges committed work against what the owner approved: the intent as merged at gate (a), `sdlc.yaml` as on the base branch when the diff changes it, the change's `profile_override` and `review_override` as the base branch's `status.yaml` carries them (since 0.2.26, choice 103: a branch that wrote `profile_override: standard` skipped the Full profile's (c)/(d) label gates before; the branch's own values are ignored and the result's `config_note` says so), HEAD rather than the working tree (every diff-reading check — `plan_sync`, `design_scope`, `guardrails`, `risk_list`, `ratchets` — reads the merge base…HEAD file list; `design_scope` runs at gate (a) too since 0.2.26, change 0000 exempt, so the intent PR carries the intent alone; `clean_tree` is the one check that looks at the working tree, and it parks on uncommitted work outside the change folder). The checks that read an artifact rather than a diff — `artifacts`, `open_concerns`, `plan_sync`'s reading of `plan.md` and `panel`'s of the ledger and the spec — read the change folder in the working tree by design: the phase commits its artifact before the gate, the panel commits each decision before the verdict, and the evidence commit after the gate lands whatever else the folder holds, so the working-tree copy is what the evidence commit lands (`commit-phase` commits the whole folder); no check enforces that the folder is committed — `clean_tree` skips it and does not run at (a) or (b) — which is why `risk_list` alone reads the spec's concerns at HEAD. The same checks run at a human gate: all green → the run stops with `sdlc:<phase>-ready`; a failed check parks there too.

**Review mode** (decision 21; build guide step 16a): `sdlc.yaml: review: parked | deferred`, per change `status.yaml: review_override`. `deferred` is the default `/sdlc-init` proposes and the template carries since plugin 1.0.8 (decision 32); `parked` stays available per project and per change, and a `sdlc.yaml` without the key still reads as `parked`. Under `parked` a judgment item parks the change for the owner. Under `deferred`, before the gate, the run puts each item of a **fixed list** to a review panel and continues: an open flagged concern in `spec.md`, a concern naming contradicting policy skills, an `escalate` verdict of the adversarial reviewer (its routine / non-routine classification never parks; it only lowers the iteration cap), an Important review finding whose fix the run cannot determine, and the verifier's "does not match the plan". The panel is three fresh contexts (`plugin/panel/`): a reviewer (the REVIEW.md pass over the item), a devil's advocate (the adversarial reviewer, blind to the reviewer and on a different model, `sdlc.yaml: panel_advocate_model`, because three judges on one model share its blind spots), and a conciliator that reads both verdicts and writes one decision with a rationale of at most five lines. Since 0.2.30 the two blind verdicts are enforced, not only asked for: the `panel_blind` hook refuses a Read, Grep or shell command that would show one verdict while the other is not yet written, and records beside the advocate's verdict which agent wrote it and on which model (`<phase>-<n>-advocate.model.json`, read from that sub-agent's own transcript); `record` refuses an item whose reviewer or advocate file has no `## Verdict`, or whose advocate record does not name the devil's advocate on `panel_advocate_model`, and the ledger carries the verdicts from those files; and a CI run that added panel decisions parks when no model in its `modelUsage` is `panel_advocate_model` (`evidence/panel-models-<phase>.json`; a session already on that model is a warning in the PR summary, not a park). `panel/cli.py record` applies the decision (a concern is closed in `spec.md` as `decided (by panel #n): <decision> — <concern>`, `n` its ledger line; an `escalate` decided `continue` and a finding decided `settled` pass their gate checks; an `escalate` the panel upholds, a decision that does not start with the word `continue`, parks: the gate's `panel` check fails closed on it since 1.0.8, choice 205; the owner lets the phase continue by overturning that line with a review comment, and a verdict that escalates again on the same reasons then passes, while new reasons are a new item), counts one panel call against `gate.max_panel_calls` (default 4; a panel call is not a fix iteration — the first deferred run spent the whole non-routine cap on two concerns, so since 0.2.15 the two counts are separate and the `sdlc:reset-iterations` label resets both), writes one line to the ledger `evidence/decisions-<phase>.json` (the `.md` beside it is what the owner reads: item, the two verdicts, the decision, the rationale, the cost), and commits the change folder, so the decision is in HEAD before the adversarial reviewer judges it. The gate's `panel` check refuses a ledger line without a decision or a rationale, a line since 0.2.30 whose two member files are not both committed with a verdict or whose advocate record does not name the advocate on its model, a concern closed by the panel whose `#n` no ledger of the phases so far carries (a concern closed at (b) stays closed through (c)–(e) and its line stays in `decisions-b.json`; the wording after the marker may be tidied; the number may not), and any line about a never-to-panel item. The PR at the next human gate opens with "Decisions taken for you (N)"; a review comment on any line overturns it through `/sdlc-fix`. What never goes to the panel and still parks, in both modes: an escalation on a risk-list item (a hit itself parks nothing, decision 35), a guardrail file change, a run limit, an infrastructure failure, anything that merges to `main` or deploys.

## 4. Gate mechanics

| Gate | Human form | Event that starts the next phase |
|---|---|---|
| (a) | merge of the intent PR; on the fast lane (below) the owner's own account opening it | merge → design workflow; on the fast lane the PR's opening → design workflow |
| (b) | merge of the spec+plan PR (every profile); on the fast lane only for a non-routine plan | merge → build workflow; on the fast lane a routine plan's gate → the design job dispatches the build |
| (c) | Full only: approving review + label `sdlc:c-approved` on the build PR, applied by the owner's account (decision 34) | label → test workflow. Standard: the build job dispatches the test job |
| (d) | Full only: approving review + label `sdlc:d-approved`, applied by the owner's account (decision 34) | label → review workflow. Standard: the test job dispatches the review job |
| (e) | the owner's approving review of the build PR (decision 36, since 1.0.18; the owner's merge before it, and still when no merge App is set up, fallback C1); plus the release label `sdlc:release-approved`, in the same visit, only when `sdlc.yaml` declares a real production | approval → `sdlc-merge.yml` checks it and merges through the merge App → `sdlc-release.yml` runs the adapter's `deploy.command`; with `deploy.production: true` it waits until the release approval exists (the label event re-runs it) |
| (f) | triage of each incident intent PR: merge (fix now) · label (schedule) · close with a reason (dismiss) | merge = gate (a) of that intent |

GitHub rule the design respects: events caused by the workflow token do not start new workflow runs, except `workflow_dispatch` / `repository_dispatch`. Since 1.0.9 (decision 33) a project that sets the repository variable `SDLC_APP_ID` and the secret `SDLC_APP_PRIVATE_KEY` has the automation push, open pull requests, label and dispatch with its GitHub App's installation token instead, and the events the App causes do start workflow runs: the project's CI runs on the automation's heads with no approval click (`docs/notes/48.md`; the workflow token's runs that wait for an approval are `docs/notes/23.md`). Since 1.0.18 the App is required (R22, the owner's answer of R60): without the variable the runner stops every run of a workflow that mints the App's token, with the reason, and `/sdlc-init` stops at the App's setup; the workflow token stays the in-job fallback once the App's token is 50 minutes old, the model session's token, and the token of the workflows that mint no App token. The owner's merges, reviews and labels fire workflows normally; every automated transition still dispatches the next phase explicitly with the change id, which the fallback needs.

**The fast lane** (decision 30, ROADMAP R46; every profile but Full, where (a) and (b) stay the owner's merges exactly as above). Gate (a): an intent PR the owner's own account opens (or reopens) is accepted by that act. `sdlc-design.yml` starts on the `opened` event, its find step checks the author and the event's sender (who opened or reopened the PR) with `is_owner_actor` against the default branch's `sdlc.yaml` (decision 34's one rule), the profile as the gate reads it (the default branch's `sdlc.yaml` and override; a `profile_override: full` on the PR's head keeps gate (a) too), that every file of the PR is inside exactly one change folder whose `intent.md` is on the PR's head at phase `a`, and that no open pull request has the head `sdlc/<id>/b` yet (a pushed design branch with no PR may run again, as `rerun_reason` allows); a draft, a fork's head, a `[bot]` or any other author or sender, an incident intent (phase `f`, the automation's) and a refused check keep gate (a), the merge. GitHub runs no `pull_request` workflow for a PR in merge conflict, so a conflicting intent PR takes no fast lane until the conflict is resolved, or is merged as before. The runner cuts `sdlc/<id>/b` from the PR's head and records it in `status.yaml: fast_lane.a` (`sha`, `pr`) in a local commit; nothing is pushed before the setup and the guard. Gate (b): when every check of the design's gate passes, the profile is not Full and the adversarial reviewer itself said `continue` and classed the plan exactly `routine`, the gate in a CI session says `continue` with no label (a gate run by hand still waits); the design run's runner (never a fix round's) confirms it from the default branch's profile, the verdict file and the branch (no commit after the judged one outside the change folder's `evidence/` and `status.yaml`), records `fast_lane.b` (`sha` of the commit the gate judged, `classification: routine`, the design PR's number), commits it with the evidence and dispatches `sdlc-build.yml`. Since plugin 1.0.11 a pushed `fast_lane.b` in a CI run has a build behind it or waits at (b): a design PR GitHub refuses to open does not hold the build back (the run still ends red, and the build PR closes the intent PR as superseded instead, unless its head moved), and a dispatch that fails (refused, or no answer) drops `fast_lane.b` again and puts the design back to the `wait` at (b) with `sdlc:b-ready`, so the owner's merge starts the build. The build cuts `sdlc/<id>/c` from `origin/sdlc/<id>/b` only when that branch's record, its `gate-b.json`, its verdict and the commits after the judged one say the same again, the default branch's profile is not Full and the default branch's copy of the change is not past (a); otherwise it starts from the default branch as before and the (c) guard refuses (a design PR the owner merged by hand takes the default branch, and a merge of a design PR whose build already started on the fast lane starts no second build). A `non-routine`, missing or invalid classification, an `escalate` the panel settled, a park, a risk-list hit, a fix round at (b) and Full wait at (b) with `sdlc:b-ready` as before. Each recorded commit is the "approved copy" of the phases after it (`gate/diff.py approved_base`: `fast_lane.a` for (b), `fast_lane.b` for (c), (d), (e), the review pass and their fix rounds), used only while it is an ancestor of HEAD and not of the default branch, so a merged, squash-merged or never-fast change reads the merge base exactly as before: the intent the guardrail exemption reads, the intent rule of the `guardrails` check, the approved `plan.md` of `ratchets`. The PR's own diff, the review pass and the owner's view at (e) stay against the default branch. `fast_lane` is the runner's: a session that changes it parks like any owner-only field (§6). Once the design PR exists the intent PR is labelled `sdlc:superseded` and closed with the automation's token (the project's GitHub App's when `SDLC_APP_ID` is set, decision 33, else the workflow token; `run_phase.supersede_pr`; the sample's #77 was closed by the App, NOTES §50), no comment (decision 20); once the build PR exists, the design PR the same way. An intent PR whose head moved after the design started (the owner pushed again) is left open, and a PR that already carries the label (the owner reopened it) is never closed again. The build PR then carries the intent, spec and plan with the code and says so, so the owner reviews everything at (e), which is unchanged. One state still needs the owner's hand: when the runner cannot push that demotion either (the run ends red and says so), a later event on the intent PR skips as "design done"; the owner's merge of the design PR, or with none a `workflow_dispatch` of `sdlc-build.yml` with the change id, resumes it. What it gives up: the owner's look at a routine design before code is written; a wrong routine design costs one build's spend and is caught at (e).

**Closing a PR at gates (a)–(e) without merging abandons the change** (decision 25): `sdlc-abandon.yml` records `status.yaml: phase: abandoned` (with the reason) on the closed PR's head and on every other `sdlc/<id>/*` branch of the change on the remote, the branches are kept, and every workflow's guard, `commit-phase` and `/sdlc-fix` skip the change from then on; `state/cli.py show|list` display it. A PR the fast lane superseded is not abandoned: the runner labels it `sdlc:superseded` before it closes it, and the workflow skips a PR with that label (also once the runner's own close starts workflows, R49). The owner's own close of a PR without the label abandons the change as before. Gate (f) needs nothing more than the row above: per-finding triage is the whole gate, and closing an incident intent PR both dismisses the finding (its signature suppressed, step 39, B5) and abandons its change.

**Gate (e) is derived from the merge, never written to `main`** (build guide step 32; decision 13). Since 1.0.18 the merge follows the owner's approving review (decision 36), and the merge App merges only on it, so a merge on the default branch still means gate (e) passed. The automation identity has branch-only write access, so nothing records the merge in `status.yaml`. Instead every reader that opens a `status.yaml` from the default branch (`state/status.py read_status(..., on_default_branch=True)`: the release workflow, `state/cli.py show|list` on the default branch) reads a change at phase (e) as gate (e) `passed`, "merged at gate (e)", and any park lifted. The file itself is unchanged. **The release itself runs once per change, and only on a copy gate (e) judged** (0.3.1, issues #66 and #68; `release/cli.py`): the deploy run sets phase (e) at its start, before the REVIEW.md pass, so a build PR merged while that run is still running carries phase (e) and no gate (e) result — the release skips it (the sample's change 0002 released such a merge, PR #17, and then the run's second build PR again) and releases the pull request the run opens afterwards, which carries the result; a merged copy whose `gate-e.json` still carries the deferred `commands` mark (a job that died between the session and the runner's step, issue #91) is skipped the same way, as the runner's guard skips it for the next phase; a merged copy whose gate (e) parked (a guardrail change, the iteration cap, an escalation on a risk-list item; a risk-list hit itself no longer parks since decision 35, so without a declared production a hit the (e) merge accepted releases on that merge) has its park reason printed in the release log and waits for `sdlc:release-approved`, whether or not the project declares production (the merge alone lifted every park before, with no second look and no mention of it); and after `deploy.command` exits 0 the workflow's second job, `record` — the only one with a write token; the release job, which runs the project's toolchain and command, keeps a read-only one — commits `released_at`, `released_sha` and `released_pr` into `status.yaml` on top of the change's work branch `sdlc/<id>/c` and pushes it there and to the ref `refs/sdlc/released/<id>`, which no branch deletion removes and no pull request comes from — never on the default branch — so a second merge of the same change, the `labeled` event or a dispatch finds the record (in the merged copy, on the ref or on the branch) and releases nothing again. A remote the release cannot read is exit 2, never a release (fail closed); a record that cannot be pushed is red, so a release that ran without its record is seen. Nothing is recorded for `deploy.action: none`, an empty command or a failed command: nothing ran, and a dispatch may retry. A mixed change — runs recorded before 0.3.1 and after — counts only the ledger's entries once it has any.

**Release approval** (build guide step 29; decision 13; article p.35–37, adapted). Approval exists when the owner has applied the label `sdlc:release-approved` on the build PR: the framework reads the actor of the last `labeled` event from the PR's timeline, never from an environment variable (the article's p.36 example reads `$RELEASE_APPROVAL`), and a label applied by the automation identity or by any `[bot]` account does not count. The label is the only form: a signed tag was considered and rejected, because a session that may run `git` can sign a tag itself, so a tag is not an owner-only act (decision 5: the automation identity separates what the run did from what the owner approved, so a run cannot approve itself; decision 11 is park-never-page); the same rule makes the hook block any command that names `sdlc:release-approved` (`gh pr edit --add-label`, the REST endpoint, a script) — the label is applied on GitHub by the owner. It is required only when `sdlc.yaml: deploy.production` is true. The PR it is read from is the change's own build PR as `status.yaml` records it (`build_pr`, written by `pr/cli.py upsert` when the PR of `sdlc/<id>/c` is opened or found and committed by the runner, since 0.2.27): the release workflow refuses an event PR that is not the recorded one, and the hook accepts the recorded PR only while it is that change's (head `sdlc/<id>/c`) and the checkout is the PR's own head commit (open or merged) or its merge commit — before, the hook found "the most recent PR from the current branch's name", merged or closed, so a checkout of any `sdlc/<id>/c` rebuilt with any commits inherited that change's label (the 1.0.0 readiness review, group B); the check binds the committed content, not the working tree; a change whose `status.yaml` records no build PR is not approved until the next `upsert` records it. Two things read it: the release workflow before it runs `deploy.command` (and only for the build PR, head `sdlc/<id>/c`), and the production-gate hook (`plugin/hooks/production_gate.py`, PreToolUse on `Bash` and `PowerShell`) inside any Claude session on the project, which guards the command patterns of the project's adapter (`plugin/hooks/production_gate.py: DEFAULT_GUARDED` per `deploy.action`, plus `sdlc.yaml: deploy.guarded_commands`, plus the article's own trigger: a command naming both `deploy` and `production`), matched against every part of a chained or wrapped command, the program read by its bare name (a path, `.exe`, `.cmd`) and with the options between it and its verb dropped (`terraform -chdir=x apply`, `kubectl --context p apply`, `gh -R o/r release create`; 0.2.27). The hook only allows or blocks, never asks (the article's p.35 prose prefers a hook that asks; the run is unattended, so the block text carries the route: the owner applies the label on the build PR, then re-runs), fails closed when the approval cannot be verified, and finishes inside its own timeout because a hook that reaches the timeout does not block (NOTES §8). Every allow and block decision is one timestamped JSON line in `changes/<id>-<slug>/evidence/hook-log.jsonl` (fallback `changes/.hook-log.jsonl`; `SDLC_HOOK_LOG` overrides), article p.37. The hook is inert when `deploy.production` is false.

### 4.1 Composition of the phase runs (build guide step 24; B3)

Every run is one slash command (`/sdlc-design`, `/sdlc-build`, `/sdlc-test`, `/sdlc-deploy`), by hand or as a `claude -p` job. The same skeleton for all: **register** (`gate/cli.py start-run`, the wall clock) → **work** → **commit** on the phase's branch (`state/cli.py commit-phase`) → **adversarial verdict** for HEAD (`sdlc:adversarial-reviewer`, fresh context) → **panel** under deferred review (`panel/cli.py items`, three fresh contexts per item, `panel/cli.py record`, which commits the decision; after the last item the verdict is re-run once for the new HEAD, and nothing else is committed before the gate) → **gate** (`gate/cli.py check`: `continue` / `wait` / `park`, writes `evidence/gate-<phase>.json`) → **commit the evidence** → **surface** (open or update the PR with the ≤5-bullet summary, apply the label the gate printed) → **hand over** (a `continue` dispatches the next run; a `wait` or `park` stops). A run never asks the owner anything: a gap is a flagged concern, a parked reason or a review comment. Re-running a command on the same branch is safe and is how review comments are applied (`/sdlc-fix` re-runs the phase with the comments as constraints and bumps `status.iterations`).

Rules the table relies on. **Wait sits where the label is read**: in the Full profile the (c) and (d) runs stop after the gate; the owner's label starts the next run (CI: the `labeled` event; by hand: the next command). **Evidence is committed after the gate** so the verdict judges the artifact commit; each phase produces its own verdict. **The PR is the audit record** (p.34–35): opened at (c) as a draft in every profile, marked ready at (e), never split. **Iterations are one counter per change** (`status.yaml: iterations`, bumped by every fix round in (c), (d), (e) and `/sdlc-fix`; the cap of `sdlc.yaml: gate` applies to the sum, the runner's automatic rounds of decision 29 included, and the owner resets it with `set-iterations` or `sdlc:reset-iterations`; at the cap of the automatic rounds a fresh-context, read-only judge may reset the count once per change, marked `iterations_reset_by: sdlc-runner:<run>` and recorded in `evidence/auto-reset.json`, the only reset not made by the owner that the owner-field checks accept; the second cap parks); `set-iterations`, `accept-risk` and `unlock-tests` are owner actions (§8; decisions 5 and 24: the automation identity's commit or label never counts as the owner's act) and the gate's `owner_actions` check parks when a run's own commit introduced them (the test-lock lift since 0.2.25: until then only the hook read `tests_locked`, so a run that set it to false, turned the fix into a feature or ran `unlock-tests` itself edited the frozen tests unnoticed; the gate's `test_lock` check, the same version, refuses a committed change under `test_paths` between the lock commit and HEAD while the lock stands, which the hook — edit tools only, the working tree — cannot see; a lift or an acceptance whose recorded actor the run wrote itself is the runner's to catch since 0.2.26, §6; the check judges every commit that gained a risk item, not the newest only, and a drop of `panel_calls` like a drop of `iterations`, since one label resets both). **Nothing in a run edits guardrail files or `intent.md`** — with one exception (decision 22): a fix round on the *unmerged* intent PR applies the owner's review comments to `intent.md`; once merged at gate (a) the intent is never edited again (the gate's `guardrails` check refuses it). **Spend is known only in CI**: `record-spend` is fed by `run_phase.py` from the `claude -p` result; a by-hand or cloud-session run has no spend figure, so `gate.max_budget_usd` binds unattended runs only, while iterations and the wall clock bind every run.

Rules. **Events from the workflow token never start these workflows** (GitHub: only `workflow_dispatch` and `repository_dispatch` do), so the hand-over column is an explicit `workflow_dispatch` with the change id; the owner's merges and labels fire normally. **Events from the App do start them** (decision 33, since 1.0.9), and every job condition skips them: the design job skips a PR a `[bot]` opened (no fast lane), the design and build jobs a close without a merge, the abandon job a PR labelled `sdlc:superseded` (the runner labels before it closes), and the test, deploy, fix and runbook jobs a label a `[bot]` applied; the runner itself applies none of the owner's labels, and `run_phase.py label_applied_by_a_human` rejects any `[bot]` actor besides. **The App's token**: the eight workflows that push or open pull requests (design, build, test, deploy, fix, detect, runbook, scan) mint it in each job's first step (`actions/create-github-app-token`, skipped without `vars.SDLC_APP_ID`), and the project checkout's `token:` and every `GITHUB_TOKEN` of the job read `steps.app.outputs.token || github.token`; the abandon, comment, digest, release and evals workflows keep the workflow token, since nothing they push needs a CI run. The private key appears only in the mint step's `with:`, never in an `env:`, so it never reaches the runner script or a session. The mint step passes `permission-*` inputs, so the App's token carries no more than the job's `permissions:` block grants the workflow token, for the scopes the App holds (contents, pull requests, issues, checks and actions). **The token expires an hour after it is minted**, and a phase job may run for more than three hours: the step after the mint writes `SDLC_APP_TOKEN_MINTED_AT` to `$GITHUB_ENV`, every step that holds the App's token also holds the workflow token as `SDLC_WORKFLOW_TOKEN`, and once the App's token is older than 50 minutes `plugin/ci/app_token.py` switches the run to the workflow token — `GITHUB_TOKEN` and `GH_TOKEN` in the process environment and the runner's env dict. `pr/github.py` makes the check before every request, `state/gitops.py` before every push, fetch, `ls-remote` and clone, and the runner's publishing helpers before each publication; it prints one line to stderr when it switches. A long run's final publications therefore go out on the workflow token, and the project's CI on that head waits for the owner's approval as it did before decision 33. Without the App nothing changes. **No credential is ever written to disk** (fix round 4 of the R49 review): every checkout runs with `persist-credentials: false`, so `.git/config` holds no token, and each git network call of the runner receives its credential through its own environment — git's command-scope config (`GIT_CONFIG_COUNT` and its pairs, git 2.31+, appended to any already there; an older git fails loudly) setting `http.https://github.com/.extraheader`, after an empty value that resets any header a file carries (`app_token.git_auth_env`, used by `state/gitops.py`, the release record's push and `checkout_check.py`'s fetch; on a runner only — by hand the owner's own git credentials apply). The token it hands out is the App's while fresh and while the git config is clean, else the workflow token: before it hands out the App's token it judges the config as git resolves it (`checkout_check.py config_findings`, one `git config --list --show-scope` over the worktree, local and global scopes, on every call, since a session could plant a key later), and a proxy, TLS verification off, another CA, a URL rewrite, an include, a credential helper or a per-worktree config — or a listing git refuses — hands out the workflow token instead, switches `GITHUB_TOKEN` and `GH_TOKEN` with it so the API calls follow, sticks for the process and prints one stderr line "the git config carries <key> (<scope>)"; the project's CI on that head then waits for the owner's approval, as in the fallback. **The model's session receives the workflow token's only**: as `GITHUB_TOKEN` and `GH_TOKEN` and as git's header in its environment (`run_phase.session_env`, triage included), never the App's, so its own pushes work and start no workflow run without the owner's approval, as before decision 33 (a session cannot push a branch or a tag as the App and start the project's push- or tag-triggered workflows; that it cannot read the runner's process through `/proc` either rests on the sandbox giving it its own process namespace, not verified live); the runner's own publications after the session carry the App's identity. A job that minted the App's token without handing over the workflow token leaves the session no GitHub token. **Project code finds no token in its own environment or in `.git/config`**: the commands step's targets, the toolchain install (`commands.setup`) and the judge run in `run_phase.commands_env` or its like — no GitHub token, no git header (`app_token.strip_git_auth`), no model credential — and no checkout persists one. An unsandboxed process can still read the runner's initial environment through `/proc`, as it already could for the workflow token and the model key (T29, R44). That now includes the App's token (choice 227): a project's setup or target could read it from the runner's process and push as the App. The owner left it to R44, which hides the credentials from shell commands for all three secrets together. This narrows T29 for the workflow token too: before, the token the checkout persisted was readable to any code run in the checkout; the session still holds the workflow token, accepted as before (T29, R44). The deploy and detect jobs still verify the project checkout's config before their second step (`checkout_check.py config_problems`, judged as git resolves it: one `git config --list --show-scope` over the worktree, local and global scopes, git 2.26+; a proxy, TLS verification off, another CA, a URL rewrite, an include, a credential helper, a per-worktree config or a diff driver is refused), and every git call of that check runs with `core.hooksPath` pointed at an empty directory and the filesystem monitor off, so a hook the session planted never runs. `actions/checkout@v6`'s separate credentials file does not arise with `persist-credentials: false`. **Concurrency is keyed on the change's work branch**: `group: sdlc-${{ inputs.head_ref || github.event.pull_request.head.ref }}`, `cancel-in-progress: false` (GitHub keeps one running and one pending run per group); every dispatch passes `change_id` and `head_ref` (the next phase's work branch, `sdlc/<id>/b` or `sdlc/<id>/c`), and a merge- or label-fired run keys on the PR's head branch, so all runs of one change serialise. The abandon and runbook workflows have their own groups, `sdlc-abandon-<head ref>` and `sdlc-runbook-<head ref>` (0.2.22): a close without a merge also fires the merge-guarded design and build workflows, a label event also fires the fix, test and deploy workflows whose guards skip, and on a shared group GitHub displaced one pending run at random (live, the sample's PRs #34 and #35, 2026-09-25); the abandon run is the only writer of the end state (decision 25) and the Go must never be the run displaced (decision 14). A merge-fired design or build workflow starts for every merged PR: a 20-second "find the change" step (`run_phase.py --find-change`) reads the PR's files and ends the job green when they touch no `changes/<id>-<slug>/` folder, before any install; the earlier head-name rule missed intent PRs pushed from a web session. **Permissions per job**, least privilege, and no deploy or runbook secret in any step that runs a model: the phase jobs (design, build, test, deploy, fix) declare `contents: write`, `pull-requests: write`, `issues: write`, `checks: write` and `actions: write` (build, test and fix use the last to dispatch the next workflow, and design on the fast lane, §4; deploy carries it too and dispatches nothing); the detect job the same but `actions: read` (it reads the runs API and dispatches no workflow); the abandon job `contents: write` and `pull-requests: write`; the comment dispatcher `actions: write`, `contents: read` and `pull-requests: read` (decision 34: it dispatches the fix round and writes nothing); the runbook and scan jobs `contents: write`, `pull-requests: write` and `issues: write`; the digest `contents: read`, `issues: write` and `pull-requests: read`; the release job `contents: read`, `pull-requests: read` and `issues: read` (the project's own toolchain and `deploy.command` run there and must not be able to push), and the release workflow's second job, `record`, `contents: write` alone (0.3.1, issue #66: it runs the framework's record step and nothing of the project's); the evals job `contents: read`. The project's own secrets reach three steps only, and only when the owner adds them to that step's `env:` — the release step (`deploy.command`), the detect job's `finish` step and the runbook job's Go step (a project runbook with a command). One secret is the exception (1.0.17, the owner's request): every step that hands a session the model credential also hands it `GEMINI_API_KEY`, empty while the owner has not added that secret, so a session can call the Gemini API; ## 5. Change requests

At any human gate, "ask for changes" = review comments on that PR, submitted as a "Request changes" review. That submission starts the fix round by itself (decision 22): `sdlc-fix.yml` runs `/sdlc-fix <id>` on the PR's own head, which reads the unresolved comments and failing checks, re-runs the phase with them as constraints, and pushes to the same branch. This applies to intent, spec+plan and build PRs alike — on the unmerged intent PR the round corrects `intent.md` without re-running the brainstorm — and no owner-launched command is needed; `/sdlc-fix` stays for by-hand runs. The owner's PR comment that starts with `@claude` starts the same round (decision 34): `sdlc-comment.yml` dispatches it, so on a PR the owner opened by hand, where GitHub refuses the owner's own "Request changes", the owner writes the line comments as a comment review and adds one `@claude` comment instead of dispatching `sdlc-fix.yml` from the Actions tab. The comment is a trigger, never a verb (decisions 24 and 28): it accepts and waives nothing, and its words are a request like any review comment. Only the owner's account starts a round, on both paths (`state/unpark.py is_owner_actor`: the repository owner, or `sdlc.yaml: owner` on an organization repository, read from the default branch); a review or comment by the workflow token, any `[bot]` account, a member who is not the owner, or anyone else starts nothing, and a head in another repository (a fork) is refused. Whose words reach a round stays the member rule of `ci/fix_requests.py`. A PR comment cannot be resolved and a comment review cannot be dismissed, so the round marks each request it applied in the committed `evidence/fix-requests.json` and the next round lists it under `not_applied` without its text.

## 6. Park, never page

When a confidence gate fails (under deferred review: on anything but the fixed list the panel settles, §3), a run limit is hit (iterations, wall-clock, budget, pause flag), or the gate's reviewer escalates on a risk-list item (decision 35: a risk-list hit itself never parks; it is a line of the "Needs your close look" banner on the PR the owner merges, with the reviewer's brief on the item, and the merge accepts it, recorded in `status.yaml: risk_acceptances`), the run **parks**: it finishes every artifact it can, writes a "what I need from you" section into the PR description, records the reason in `status.yaml`, labels the PR `sdlc:needs-human`, and requests the owner's review on the PR (decision 31, 1.0.7), the only notification (§7). Parked and finished work waits in the review queue. One failure no longer parks at once (decision 29, 1.0.3): a red target the runner's commands step finds after the session starts the next fix round by itself (the PR carries `sdlc:fixing`, its summary says which automatic round of the cap is running and that nothing is needed, and the digest lists it apart); the change parks only at the iteration cap, after the one judged reset, with the cap and the judge's reasons in the "what I need from you" block. The owner un-parks by settling the item on the PR (decision 24): a "Request changes" review (→ the fix round), or one of two labels — `sdlc:reset-iterations` (the fix-iteration and panel-call counts back to 0 after either cap), `sdlc:unlock-tests` (thaws the test-file lock of a fix-type change); the third, `sdlc:accept-risk`, retired with decision 35, since a risk-list hit no longer parks (a `risk_accepted_by` entry recorded before 1.0.15 is still confirmed by its label event). Each label starts the fix round, which performs it, records the label's actor in `status.yaml` (`iterations_reset_by` with its stamp `iterations_reset_at`, `tests_unlocked_by`), removes the label from the PR (one application is one act) and re-runs the phase; a label applied by the automation identity or a `[bot]` is rejected and left where it is, and the gate's `owner_actions` check re-judges the recorded actor. The gate believes a recorded actor that is a person, and the session can write `status.yaml`, so in CI the runner (`ci/run_phase.py`, loaded from the pinned framework checkout the session cannot edit) is the check (since 0.2.26, choice 103): it reads the owner-only fields right before the `claude -p` session — its own label handling included — and again right after, and a `risk_accepted_by`, `tests_unlocked_by` or `iterations_reset_by` entry or a `risk_acceptances` line (decision 35: the runner's record of the merges that accepted a risk, each confirmed against GitHub's record of that merge) the session added that the runner did not record and the default branch's copy does not carry, or an `iterations` or `panel_calls` count lower than before the session, restores the fields to their pre-session values and parks the change before any commit of the run (`owner_fields` in `evidence/gate-<phase>.json`, naming the field, the session's value and the expected one); a change of `profile_override` or `review_override` on the branch is reported, never honoured (§3). By hand the gate's commit-author rules are the check, as before. The CLI commands `accept-risk`, `set-iterations` and `unlock-tests` stay for by-hand runs (their commit author is the act); `paused: false` stays in `sdlc.yaml`, because pausing is a reviewed change. `paused` and `deploy.production` are booleans: `yes`, `on` or a quoted word is a string to YAML 1.2, and since 0.2.26 every reader (the gate's `limits`, the preflight, the runner's guard, the production-gate hook, the release workflow) fails closed on it instead of reading it as unset.

## 7. Review queue

The queue is the PR list filtered by `sdlc:*-ready` (a run stopped at a human gate) and `sdlc:needs-human` (parked). Every PR the framework opens or updates starts with a ≤5-bullet summary: what changed and why, evidence status, review findings by severity, plan conformance, and — if parked — what is needed; under deferred review "Decisions taken for you (N)" stands above the bullets, one line per panel decision of the phases the PR covers, and a review comment on a line overturns it. A scheduled job rewrites the body of one pinned issue ("SDLC review queue") with the digest. One thing pushes to the owner (decision 31, 1.0.7): when an automated publication leaves a PR waiting (`sdlc:*-ready` or `sdlc:needs-human`), the runner, the detect workflow and the weekly scan's incident intents request the owner's review on it (`pr/cli.py upsert --request-review`, `pr/review_request.py`; the owner read from the default branch's `sdlc.yaml` on a runner, as decision 34 reads it). A request still pending from an earlier wait is removed and requested again, so every new wait gives one fresh push, and a publication that leaves the PR not waiting (`sdlc:fixing`, a gate that continues) withdraws it, so GitHub's "Review requests" list is the owner's waiting queue. Its limits: no request on the owner's own PR (GitHub refuses a review request to a PR's author), none on the runbook PRs of `detect/runbooks.py` or the dismissal PRs of `detect/cli.py dismiss` (they are not published through `upsert`), and none from the model's own in-session upserts. Not verified: whether GitHub's push reaches the owner for a request on a draft PR (the build PR waits as a draft at (c)), and whether a remove-then-request pair sends a fresh notification. Nothing else pushes: the framework never comments, assigns or @mentions; the owner sets the repository watch to "Participating and @mentions", and may turn off GitHub's default e-mail for failed Actions runs — a parked phase is a green job by design (only an infrastructure failure is red).

## 8. Conventions

- One folder per change: `changes/<id>-<slug>/` with `intent.md`, `spec.md`, `plan.md`, `evidence/`, `status.yaml` (phase, profile override, change type feature/fix, entry route idea/ticket/incident, gate result, parked reason, iteration count, external reference; since 0.3.1 the release record `released_at` / `released_sha` / `released_pr`, written by the release workflow on the work branch, issue #66). `<id>` is a four-digit sequence allocated from the folder (`0000` is the framework's own installation); `<slug>` is the kebab-case title. `plugin/state/` is the only writer.
- Branches `sdlc/<id>/<phase>`: `a` carries the intent PR, `b` the spec+plan PR, `c` the build PR that stays open through (d) and (e). A fix round runs on the PR's own head, which for an intent PR pushed from a web session is a `claude/…` branch. Labels `sdlc:<phase>-ready`, `sdlc:<phase>-approved` (Full only), `sdlc:release-approved` (the owner's release approval on a declared production, §4), the owner's un-park verbs `sdlc:reset-iterations`, `sdlc:unlock-tests` (§6; `sdlc:accept-risk` retired with decision 35), `sdlc:needs-human`, `sdlc:fixing` (the runner's own, since 1.0.3: an automatic fix round of decision 29 runs, so nothing is needed from the owner; it stands in place of `sdlc:needs-human` until the round's own run replaces it, and a round that does not finish parks with `sdlc:needs-human`); phase (f): `incident` (every intent PR the maintain loop or the security review opens: the triage queue is the set of open PRs carrying it, step 39), `schedule` (the owner's "not now"; nothing runs), `sdlc:go` (the owner's per-incident authorization of a runbook whose route says `go`, decision 14; read by `sdlc-runbook.yml`, performed once and removed). Every label is created by the first CI run (`run_phase.ensure_labels`); the gate labels are exclusive (one at a time, set by the PR upsert), the owner's labels are never removed by an upsert. `status.yaml: phase: abandoned` is the end state of a change whose PR was closed without a merge (§4). An incident change stays at phase `f` on `sdlc/<id>/a` until its intent PR is merged (the design workflow reads a merged change at `f` as at `a`); its PR title is `maintain(<id>): …`.
- `evidence/` also holds the run's own records beside the toolchain logs: `diff-<phase>.patch` (the merge base…HEAD diff the adversarial reviewer judges — the reviewer has no shell, the run writes the diff and passes HEAD's sha), `release-notes.md` (phase (e)), `hook-log.jsonl` (the hooks' allow/block decisions), `decisions-<phase>.json` and `.md` (the panel's ledger, decision 21) with the members' files under `evidence/panel/`, and for an incident change `detection.json` (the finding as the detection script recorded it: metric, tier, rule, mean, sigma, the latest point, the failed runs, the default branch's commits in the breach window, `forced`) or `scan-finding.json` (a security review's finding: signature, class, bounded), `proposal.json` (the diagnosis's route) and `runbook-<name>.json` (what the runbook did, or `go-requested`), all committed with the evidence commit; and the CI runner's own records, `claude-<phase>.json` + `.stderr.txt` (the headless run's result and stderr, one file per run: the second run of a phase — a fix round, a re-run — is `claude-<phase>-2.json`, and so on) and `run-<phase>.json` (start time, the last session's spend) with `spend.json` (the change's spend ledger since 0.3.1, issue #71: one entry per run — the review pass and each fix round their own — and the total the budget cap is compared with), which the runner stores after a run ends and commits under `run(<phase>): …`; they describe the run that produced them, never the diff a later reviewer judges.
- The repo is the source of truth for every artifact; any external tracker holds the issue number ↔ commit SHA link.
- `plan.md` is produced at the end of phase (b) by a read-only run (Read/Grep/Glob only) and approved with `spec.md`; the implementation run of phase (c) is the first run with edit and shell tools on source. (Phase (a) writes only `changes/<id>-<slug>/intent.md`, interactively with the owner — or, in a fix round on the unmerged intent PR, from the owner's review comments, decision 22.) In (c) a hook on `git commit` denies a commit that changes source without changing `plan.md` in the same commit.
- Process content (commands, skills, agents, hooks, gate logic) lives in the plugin, pinned per project by version; project content (`CLAUDE.md` body, test commands, protected paths, `sdlc.yaml`, `REVIEW.md`, `bands.yaml`, `evals/`) lives in the project.
- Every hook, gate check, detection script and eval check is Python with no third-party dependency; one task runner works on Windows and Linux. Hooks are registered in exec form (`python` plus the script path), so no shell is involved on any platform. A hook reads its JSON input from the byte stream as UTF-8 and the CLIs whose output a model reads write UTF-8 (0.2.25): Windows' console encoding is not UTF-8, and a text-mode stdin turned a project path with an accented letter into one no protected path matched, so the hook allowed the edit. Until B3 the phase commands run by hand, on the owner's PC or in a Claude Code cloud session; from B3 they run in GitHub Actions under the automation identity.
- Test-file lock for fix-type changes (build guide step 25; article p.28 step 4, p.35): in a change whose `status.yaml` says `change_type: fix`, the build run writes and commits the reproducing test first and then sets `status.yaml: tests_locked: true`; from that commit until the owner's merge the plugin's PreToolUse hook denies every edit under the project's test paths on the `sdlc/<id>/c` branch (phases (c), (d), (e) share it), and `REVIEW.md` rejects a diff that touches a pre-existing test in a fix task. Test paths are `sdlc.yaml: test_paths` (globs; `/sdlc-init` writes the defaults for the detected language). Only the owner unlocks (`state/cli.py unlock-tests`, or the `sdlc:unlock-tests` label, §6), in a reviewed PR, when the test itself was wrong; the gate's `owner_actions` check parks a lift that a run's own commit introduced without a recorded owner actor (0.2.25).
- Guardrails protect themselves in three layers (decision 6). (i) The protected-path hook in the plugin covers `.claude/**`, `CLAUDE.md`, `REVIEW.md`, `sdlc.yaml` (the copies at the project root; a same-named file in a subdirectory is project content unless `protected_paths` lists it) and the plugin's own files, and a Bash/PowerShell command that would write to the same paths (`plugin/hooks/shell_guard.py`, change 0002), with `Edit(...)` deny rules in the project settings as a second net; the hook has no exception. The only sanctioned writer of guardrail files in a run is `/sdlc-init`'s install script, which only adds (rules, keys, sections) and whose output rides in the change-0000 PR — with the workflows and the pin script under `.github/` and `lessons/` (the commit of `/sdlc-init` step 5 lists them since 0.2.25; before, a project set up by the book merged with no automation); every other guardrail change is made by the owner in a reviewed PR. (ii) On the owner's machine a *managed* settings file (system path, see `docs/owner-machine/`) sets `allowManagedPermissionRulesOnly` and `allowManagedHooksOnly`; because those keys ignore project permission rules and block non-managed plugin hooks, that file also carries the permission rules and force-enables `sdlc@sdlc-framework`. Cloud sessions never read it: there, the repo's `.claude/settings.json` and the plugin it declares are the layers. (iii) CI loads hooks and permissions from the pinned plugin, never from the PR branch, and the sandbox's `filesystem.denyWrite` block in `plugin/ci/settings.ci.json` (change 0002) is CI-pinned content the same way, carrying one more block beside hooks and permissions. Bypass-permissions mode is never used and is disabled in every settings file.

## 9. Phase adapters (per project, in `sdlc.yaml`)

- `profile`: standard | full (lite was removed in 0.2.14, decision 21; a file that still says it reads as standard)
- `review`: parked | deferred — whether a judgment item of the fixed list parks the change or goes to the review panel (§3; `/sdlc-init` proposes `deferred` since 1.0.8, decision 32; an unset key reads as `parked`); `panel_advocate_model`: the model of the devil's advocate (the template's `claude-fable-5-1` since 1.0.14; where the session runs on it, the advocate runs on `adversarial_model`); `session_model`: the CI session's model, one model or `default` plus per-phase entries, passed as `--model` (a fix round takes its change's phase; unset = the CLI's default; the workflow's `SDLC_MODEL` wins); `adversarial_model`: the adversarial reviewer's model, which the gate's `reviewer_model` check holds the verdict to (unset = not checked). Each is a full id or a family alias; the phase commands start the reviewer and the advocate with the family alias (`panel/cli.py models`), and the runner pins what each alias resolves to with `ANTHROPIC_DEFAULT_<FAMILY>_MODEL` (1.0.14, ROADMAP R7, NOTES §51)
- `commands.build` / `commands.test` / `commands.lint`: the one-command targets that exit non-zero on failure (detected or created by `/sdlc-init`); the framework refuses to enter phase (c) without them
- `protected_paths`: the project's own frozen paths, added to the always-protected set
- `risk_list`: an item touched is a line of the "Needs your close look" banner on the PR the owner merges, with the gate's reviewer's brief on it (`evidence/roles/security-policy-<phase>.md`), and the merge accepts it, recorded in `status.yaml: risk_acceptances`; it never parks, and only the reviewer's escalation on an item does, off the review panel (decision 35). An item is its words, matched in the committed diff's paths and in spec.md's "Flagged concerns", or `{item, paths}`, whose globs are matched on the committed diff and whose words in "Flagged concerns" only; no path under `changes/` is matched, and the design declares an item it touches as a closed line, `decided (decision 35): risk item '<item>': …`; `/sdlc-init` proposes globs for the folders the project has (default items: auth, data migrations, money movement, production config)
- `plan_sync.exempt`: globs (besides `changes/**`) whose changes do not require a `plan.md` update in (c); `hooks.format_on_edit`: switch for the formatter hook
- `paused` and `gate.*` (`max_iterations`, `max_iterations_non_routine`, `max_panel_calls`, `max_turns`, `max_wall_clock_minutes`, `build_max_turns`, `build_max_wall_clock_minutes`, `max_budget_usd`, `command_timeout`): the run limits every gate enforces; a limit hit parks with the partial evidence. The build run and every fix round have their own caps (decision 32, 1.0.8): `build_max_turns` (default 400) and `build_max_wall_clock_minutes` (default 180); every other run keeps `max_turns` (default 200) and `max_wall_clock_minutes` (default 120). An unset build key is the larger of the general setting and the build default, so no project's cap goes down. `max_budget_usd` is per change, binds CI runs only, and is 150 in the template (decision 32); each session gets what the change has left, and a run that reaches it parks
- `bands.yaml` (next to `sdlc.yaml`): the control bands of phase (f) — metric, source, baseline (`rolling_<N>d`), rules (`western_electric`), the three σ tiers (1σ `log`, 2σ `diagnose` with its `tools`, 3σ `propose` with its routes) and, per 3σ route, `authorization: preapproved | go`; optional `direction: above | below | both` and `min_sigma` (`plugin/detect/stats.py`). Project content the owner tunes in a reviewed PR: a dismissal never rewrites it (step 39)
- `commands.setup`: the one command that installs what the three targets need; every CI phase job runs it before the phase (`plugin/ci/project_setup.py`); empty = nothing to install
- `test_paths`: the globs of the project's test files that the test-file lock freezes in a fix-type change (§8)
- `automation_identity`: the login(s) whose commits and label applications never count as the owner's act (default `github-actions[bot]`); read by the gate's `owner_actions` check and by the release approval
- `plugin`: name, marketplace and pinned version of the process in force; `plugin.claude_code`: the Claude Code CLI version the phase jobs install (the framework's minimum is 2.1.304 since 1.0.16, the first version read to run a sub-agent on a full model id, NOTES §54; it was 2.1.278)
- `deploy.action`: what makes a merged change live (publish package · schedule job · regenerate report · promote to paper trading · deploy service · none)
- `deploy.command`: the one command `sdlc-release.yml` runs after the build PR's merge (and, with a declared production, after the release approval) — e.g. `python -m build && twine upload dist/*`; empty = the release is prepared in the PR and nothing runs. It runs on the GitHub runner with the repository's own secrets; the framework holds no deploy credential
- `deploy.production`: true/false — turns on the release approval (§4): the release workflow waits for it, `/sdlc-deploy` says so in the PR body, and the production-gate hook guards the adapter's commands inside Claude sessions
- `deploy.guarded_commands`: shell-style patterns the production-gate hook blocks until the approval exists, added to the plugin's defaults for the adapter; read only when `deploy.production` is true
- Deploy, status and rollback as tools (build guide step 31; article p.40 step 4 "Deploy, status, and rollback become tools"): not built. The plugin ships no runtime dependency (§8) and no project has named a real deployment yet, so the interface is recorded here and built when an adapter needs it: three MCP tools, `deploy(change_id)` (runs `deploy.command` for a merged change and returns the run record), `status(change_id)` (the last release's outcome and the current metric from `maintain.source`) and `rollback(change_id)` (runs the `rollback` runbook of `maintain.runbooks`); every call passes through the production-gate hook, so on a declared production none of them runs without the release approval, and `rollback` is the pre-approved runbook only under decision 26 (B5). Until then the release workflow is the one deploy route and the DORA measures come from the CI system and the deployment tooling, as the article says (p.41), not from the framework
- `maintain.metric` and `maintain.source`: the watched metric and where the detection script reads it (default for every new project: CI test failure rate from the CI API)
- `maintain.runbooks`: the project's own runbooks, each with a `name` (what a `runbook:<name>` route of `bands.yaml` refers to), a `command` (no shell; `&&` steps; run on the runner with the repository's own secrets) and `authorization: preapproved | go` — CI-scoped reversible actions are pre-approved, anything touching a running system waits for the owner's "Go" as a parked item (decision 14); a `go` here is stricter than the bands' value and wins. The plugin ships two runbooks that need no entry: `quarantine-flaky-test` (adds `--deselect <node id>` to pytest's `addopts` on a branch and opens the PR; never edits the test; Python projects only) and `revert-pr` (`git revert` on a branch from the default branch and the PR; never merges). `rehearsed_at` (decision 26): on a project with `deploy.production: true`, a runbook whose name contains `rollback` and whose `rehearsed_at` is a date the owner set after a staging rehearsal is pre-approved whatever the two files say
- `lessons/` (the incident record, step 36): one file per incident, `lessons/<yyyy-mm>-<slug>.md`, written when the fix ships (the (e) run of an incident change, §4.1 step 0b) and read before every diagnosis; `evals/cases/<id>-<slug>/` (the eval of that incident, step 35) beside it. Both are project content. Each lesson opens with a frontmatter block (type, title, description, tags, change, detected, fixed, generated, status, stale_after, sources) a script can follow, and `plugin/lessons/index.py` keeps a generated `lessons/index.md` (a heading per tag, `## Retired`, `## Unsorted`) that the (f) run reads first so it opens only the lessons its tags name.
