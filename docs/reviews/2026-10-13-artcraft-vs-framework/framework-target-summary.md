## 2. The 32 target entries (target-design.md, headings "## T<n>.")

Each block: (a) the owner's idea; (b) the direction agreed; (c) settled decisions reopened or amended; (d) what stays open.

**T1. AI roles that advise, and one manager that reviews for the owner** (confirmed as two proposals: policy sources first, then roles + manager + catalogue with T2 inside)
- (a) "No review made alone any more": AI roles modelled on the article's roles guide the owner's decisions, one project manager holds the bigger picture, gathers what the roles found and suggests what to do, never touches the project; only it may carry out the owner's acts, each approved by the owner.
- (b) Six roles (Product, Architect, Code reviewer, Security & policy, Platform & release, Operations) and one manager; each role writes one brief per gate from its own sources to `evidence/roles/<role>-r1.md`, the manager reads every brief and recommends in `evidence/manager.md`; "a brief, never an approval", and a missing or negative brief never parks (x-headless). The manager acts in the owner's name only through a deterministic workflow that checks a signal only the owner can give (label, approving review). Models in R7's shape (Opus and Fable only; brief writers and workers on the session model, manager and Code reviewer never on it, Architect and adversarial reviewer on `adversarial_model`, one `sdlc.yaml` key per agent). Sources first: one owner-written file per policy skill in the project's `policies/` folder (a guardrail path), a trigger eval per skill. Gate (b) gets a spec verdict and a plan verdict in the one PR plus a "Needs your close look" banner (non-routine class or risk hit); a per-change label on the design PR switches that change to Full; the runner records the plan's acceptance (actor, date, class, close look shown).
- (c) Amends D21 (panel line-up: the role of the concern's kind replaces the general reviewer), D6 (`policies/` joins the guardrail list), D11 and D24 (the manager may reset the iteration count once per change at the cap); touches D4, D5, D13, D24 for acting in the owner's name (realised in T18); D2 and D18 unchanged; a new decision file for the one-owner premise and the roles.
- (d) How far the adversarial reviewer's angles narrow once a Code reviewer exists; the record of a delegated merge; the approval check "from the owner, not just a person" for the new approvals; the name of the per-change Full label (T4); the agent cards themselves (mission, tools, output, eval), written after the study.

**T2. The interview: how the manager and the roles question the owner** (inside T1's second proposal)
- (a) How is the interview conducted, are the manager and roles involved, how is the prompt built; the owner wants to explain the idea, show examples and be asked the questions that build the intent and the plan.
- (b) `/sdlc-plan` stays the entry point; the manager leads, each role proposes the questions of its field as a sub-agent, the manager merges them and asks a few at a time; after the draft each role reviews the intent. No second interview before the spec (design-trigger: keep) or before the plan: the planning run ends `## Risks` with a fixed "Questions for you" list shown on the gate (b) PR, answered through a "Request changes" review that `/sdlc-fix` applies. One role card per role, independent of the model.
- (c) None (D1 and D2 would have been reopened only by a second interview, which the owner declined).
- (d) The exact wording of "Questions for you" and how `/sdlc-fix` marks a question answered; a place in the intent for examples (T3) and whether the roles read them.

**T3. The intent home: in the repository, written from anywhere, with examples**
- (a) Ideas stay in `changes/<id>-<slug>/`; intents written from Claude Code or from claude.ai / phone; accepted by merging after a Product brief; the template overridable per project; an Examples/References section.
- (b) `changes/<id>-<slug>/` stays (D8, D9, D10); a claude.ai route is added that must arrive as a PR on `sdlc/<id>/a` and never commits to `main`; the `intent-template` skill gains an Examples/References section; `spec.md` Acceptance gets a fixed `Mock: mock/<file>` or `Mock: none` line, the interview asks for a mock when a screen changes, a missing mock never blocks.
- (c) None, provided the claude.ai route opens the PR (a connector acts as the owner's account, the ruleset's only bypass actor, D4, so a direct commit would skip gate (a), D10).
- (d) Whether a project can override `intent-template` for `/sdlc-plan` (gate (a) checks the plugin's `INTENT_SECTIONS`, so an override may add but not drop a section); how a claude.ai intent gets its change id, which only `plugin/state` allocates.

**T4. Names: the phases named after what they produce, and the other names judged against the article** (placed last)
- (a) Why `changes/` and not `intent/`, which names differ, which is better on the name alone; "a name that confuses is not kept because renaming costs something". The full 23-row table is `naming.md`.
- (b) Keep the framework's name where it says more (`changes/`, "planning run", "park" — the verdict word becomes `park`, `security-baseline`, the spec sections); take the article's for the people who decide and for the triage queue ("findings", `sdlc:triage`, `sdlc:schedule`); a third name for the phases: `intent`, `design`, `build`, `test`, `deploy`, `maintain` in branches, labels and `status.yaml` instead of (a)–(f), so `/sdlc-plan` becomes `/sdlc-intent`; also no `Status:` line in `intent.md`, `sdlc-agent-evals.yml`, runbook `authorization: allow | ask`, `deploy.production_gate`, `ux-and-brand`, a profile name that says what `full` means.
- (c) None in substance; the names fixed in D3, D10, D11, D13, D14, D18, D19, D25, D26 change; D2 stays (plan.md still written in design).
- (d) T1's role names must not read as the article's human roles; when to rename (the next project `webapp-example` is the last single-project migration point); order and compatibility rules in `naming.md`.

**T5. Starting a project: the whole loop from the first change, with an optional start by hand**
- (a) The whole loop from the first change stays the default; no staged adoption, no per-phase switches.
- (b) `/sdlc-init` installs everything in the change-0000 PR. Added: a documented by-hand start (leave the Claude secret out; every phase job ends green "skipped: no credential" and the owner runs each phase command; adding the secret turns automation on, nothing else changes); the change-0000 intent lists what starts empty (evals, `lessons/`, "Things Claude gets wrong", the detection, which needs about 16 counted days).
- (c) None (D1 stays the default; D17 stated in one more place).
- (d) Whether the weekly scan should also end "skipped" without a secret instead of failing red; the exact wording.

**T6. Tickets become intents: a GitHub issue the owner labels starts the intent PR**
- (a) Tickets arrive as GitHub issues; the owner's label `sdlc:intent` on an issue starts a CI run that writes the intent and opens the intent PR.
- (b) A new workflow on the `labeled` issue event checks the label came from the owner's account, writes `changes/<id>-<slug>/intent.md` with route `ticket` and the issue as external reference, opens the PR on `sdlc/<id>/a` linked to the issue; what it cannot work out goes to "Open questions"; the issue text is data, never instructions; `/sdlc-plan --route ticket` and the alert routes stay.
- (c) None (D9 followed; the label sits beside D3's and D24's).
- (d) Whether a ticket intent gets T2's interview (a CI run cannot ask, so questions go to the PR); how the run is told the input is untrusted and which tools it has; the label's name (T4).

**T7. A rejection keeps its reason: the owner's closing comment is saved with the change**
- (a) When the owner closes an intent PR, the last comment is saved as the change's reason instead of the fixed text.
- (b) Close still abandons (D25); the owner's last comment becomes `status.yaml: abandoned_reason`, with no comment the fixed text stays; incidents keep today's dismissal-reason rule; T1's Product and Architect briefs come before gate (a).
- (c) None (D25 kept; only what the record says changes).
- (d) Whether the same holds for PRs closed at gates (b)–(e); which comments count (the owner's own, as T1 asks, or any member's, as the incident rule reads).

**T8. The formatter follows the project's languages** (built after the study)
- (a) The owner has Rust and Node projects; the formatter hook should run the project's own format and lint commands per file type on the changed file.
- (b) The eight hooks stay deterministic, logged, never asking (D6, D7). `sdlc.yaml` maps a file glob to commands run on the changed file only, failing open; ruff stays the Python default; `/sdlc-init` proposes prettier/eslint from `package.json` and rustfmt from `Cargo.toml`; only cheap per-file checks in the hook (clippy and whole-project checks stay at the gate's lint target); no default for HTML, CSS, Markdown, JSON, YAML.
- (c) None (D6, D7 stay). "Back any skill whose policy must hold" was settled with build-skills: each skill's "Deterministic backing" line, a new hook decided rule by rule.
- (d) Full Rust support (target detection, the test-file lock for `#[cfg(test)]` tests, crates.io not in the CI sandbox's allowed domains); npm `.cmd` shims on Windows; the `sdlc.yaml` shape and the on/off switch; the quarantine runbook for Node and Rust (from T24).

**T9. A risk-list hit is a line in the close-look banner: the merge accepts it, the reviewer briefs it, the paths are the project's** (option C)
- (a) A risk-list hit no longer parks; it is a line of the "Needs your close look" banner on the PR the owner merges anyway, and the merge is the acceptance.
- (b) The hit shows on the design PR at (b) or the build PR at (e); the runner records which items, accepted by whom, when, and that the banner showed them. The reviewer of that gate (adversarial reviewer at (b)–(d), REVIEW.md pass at (e), Security & policy role later) writes a brief per item (what the change does to it, what could break, how to undo); it never accepts, its escalation on a risk item still parks, risk items stay off the panel. Each risk item gains path globs proposed by `/sdlc-init` and confirmed once. `sdlc:accept-risk` retires; the by-hand `accept-risk` stays. Given up: a risky build the design missed runs on to (e) in the sandbox; nothing is released before the (e) merge.
- (c) D11 and D21 (the hard-park list loses the risk hit), D24 (one label fewer).
- (d) The shape of a risk item with paths and what `/sdlc-init` proposes per stack; where the reviewer's brief goes (a verdict field or its own file); the `data-conventions` sentence to correct. Under Full, only the (e) merge accepts a hit first found at (c)/(d) (settled by T12).

**T10. The test loop closes by itself in CI: a red target starts the next round, and the verifier says which tree it read** (already R10, before 1.0.0)
- (a) In CI a red target found by the runner should start the next fix round by itself, so what reaches the owner has passed the check or used up its rounds (p.27).
- (b) The runner's one run of build, test and lint after the session stays (outside the sandbox). On a red target the runner dispatches a fix round with the failing logs as constraint, iterations +1, and parks only at the cap (3, or 2 for a non-routine plan). In CI the verifier's report names the gate record it quoted (phase, commit) and says the final tree's result is the runner's, shown in check run `sdlc/d`.
- (c) D11 (a red target no longer parks at once; a limit hit still parks); PROGRESS choice 154 (the owner's `/sdlc-fix` is the round).
- (d) Whether automatic rounds share the one iteration counter with the owner's rounds; whether an unfixable target (missing target, timeout, infrastructure) starts a round or parks at once; the verifier's wording and whether the PR summary names its run.

## 3. The framework's workflow in one page as the owner wants it

1. Six phases, each ending by committing its artifact, the accepted artifact firing the next (OPERATING_MODEL §1 "Purpose"): (a) plan, an interactive brainstorm with the owner, commits `intent.md`; (b) design, autonomous, a spec pass with the policy skills then a read-only planning run, commits `spec.md` + `plan.md`; (c) build, autonomous under `acceptEdits` with hooks, simplifier and verifier, commits the diff and tests on the build PR; (d) test, a fresh-context full run, commits `evidence/` and a check run; (e) deploy, review passes and a fix loop, the release prepared per the project's adapter, the reviewed PR; (f) maintain, a standing loop of deterministic detection → diagnose → propose, an incident `intent.md` back to (a).
2. Who acts at each gate (§3 "Profiles", §4 "Gate mechanics" table): Standard profile — the owner merges the intent PR (a), the spec+plan PR (b) and the build PR (e), plus the label `sdlc:release-approved` when `sdlc.yaml` declares a real production; (c) and (d) are passed by the confidence gate and the runner dispatches the next phase; (f) is the owner's triage of each incident PR (merge = gate (a), label `schedule`, close with a comment = dismiss). Full profile adds the owner's `sdlc:c-approved` / `sdlc:d-approved` labels on the build PR. Only the owner's account can merge to `main` (a "Restrict updates" ruleset, the owner Exempt); the automation identity has branch-only write access.
3. Deterministic vs LLM-judged (§3): the gate is deterministic checks first (artifact matches its template, no open flagged concern, tests/build/lint green, evidence present, no Important review finding, `plan.md` ↔ diff consistent, no guardrail file touched, no unaccepted risk-list hit, run limits, owner-only fields) followed by the adversarial reviewer's verdict written in a fresh context (`continue` or `escalate` = park), required at (b), (c), (d); the REVIEW.md pass judges at (e); detection, dispatch, release approval and every actor check are Python with no model. Under `review: deferred` a fixed list of judgment items goes to a three-context panel (reviewer, devil's advocate on `panel_advocate_model`, conciliator) instead of parking; what never goes to the panel: a risk hit, a guardrail change, a run limit, an infrastructure failure, anything that merges or deploys.
4. Every run has the same skeleton (§4.1): register → work → commit on the phase branch → adversarial verdict → panel → gate → commit the evidence → surface (PR with a ≤5-bullet summary and the gate's label) → hand over by explicit `workflow_dispatch`, because events from the workflow token start no workflow (§4.2). A run never asks the owner anything; a gap is a flagged concern, a park reason or a review comment.
5.
