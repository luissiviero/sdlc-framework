## 6. Corrections to the record

1. **"Nothing in `Framework checks` verifies that a committed index matches its sources"** (row A5) is wrong for the notes index: `tests/test_notes_index.py:142-147` does it, run by `python tasks.py check` (`framework-checks.yml:60-61`). It was on `main` before the study (5.1).
2. **"The drift the notes-index PR (#160) is fighting by hand"**: PR #160 is the PR that made the index generated and checked it in CI. Nothing is fought by hand.
3. **G5 "the lessons index can drift … without a red check"** is partly true. In a project, gate (e) checks it on every incident change, the one automated path that writes it. In this repository nothing checks its own `lessons/index.md` (5.2). That is the whole remaining gap.
4. **"One `--check` mode per generator"** already exists for the lessons index (`plugin/lessons/index.py:300-317`). The notes index's check is a test, with no CLI flag, and needs none.
5. **"Checklist rows are verified against the code (`ci.yml:154-158`)"**: those lines run a text comparison. The statuses are hand-written TOML, and the row-against-code check is pdfcraft's, cited elsewhere (5.5).
6. **"One step in `framework-checks.yml`"**: photocraft itself has the step and a test for the same check. The framework's test is the equivalent of both (5.3).
7. **"The same for the lessons index in the template's evals workflow"** is a project change, which this batch's premise ("only this repository's own workflows") excludes. It would also start the paid suite on every lesson edit (5.4).
8. **"`cancel-in-progress` on PRs"** (row A10's landing) is already in `framework-checks.yml:28-32`. The real difference is the reverse: `main` runs cancel each other here, 4 of the last 10 (10.1).
9. **"The evals run nightly and on the guardrail paths"**: `framework-evals.yml` runs on `plugin/**`, `template/**` and `evals/**`. The guardrail paths are the template's `sdlc-evals.yml` (10.5).
10. **"Windows only when `plugin/hooks/**`, `plugin/ci/**` or `tasks.py` changed"** is too narrow. Windows code spans eight `plugin/` folders, and the one Windows-only failure on record was a tests-only defect (10.3).
11. **"Zero-risk hygiene"**: 10.1 is close to zero risk. 10.2 is not: it moves a Windows-only defect's detection from the PR to `main`, and it changes a standing HANDOFF precondition (sections 4 and 7).
12. **"The gain is the owner's wait"** is right, and now measured: about 14 of the 16 minutes on a documentation-only PR (10.2).
13. **"Caches are saved from `main` only"** has nothing to apply to here: no cache, and an install of 4 to 16 s (10.4).
14. **The `full-ci` label** does not transfer: a label starts no `pull_request` run with the default types, and this repository's PRs carry `sdlc:*` labels (10.6).
15. **The pick step cannot be copied as written**: it is bash, and every `run:` line here calls python (section 2, after the table).
16. **Missed by the row:** the release tag does not wait for `Framework checks` (`sdlc-tag.yml:18-22`). With `main` runs cancelled, a tag lands on a commit whose suite never finished. That already happened to `v0.3.6` (run #279). It is the strongest reason for 10.1.
17. **A `--check` flag for the notes index** cannot be added as a second argument without changing the runner: `tasks.py:223-228` accepts exactly one argument and prints the usage otherwise. The test makes it unnecessary (from the reviewer, point 4).
18. **Missed by the row:** `framework-evals.yml:26-28` keys its PR runs by `head.ref` with `cancel-in-progress: false`. So every push to a plugin PR queues another paid eval run behind the stale one, under the head-ref key that `framework-checks.yml:29-30` stopped using because two forks' branches can share a name (from the reviewer, point 10; 10.8).
