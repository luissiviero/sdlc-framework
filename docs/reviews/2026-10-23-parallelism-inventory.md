# Parallelism in the framework: what is built, accepted, proposed and dropped, and whether a central session should become a pipeline feature (2026-10-23)

The owner asked for a study, report only, as the basis for one question: should the "central session" of choice 262 (one coordinator that knows the order of the work, runs several build sessions in parallel, keeps them from clashing and relays between them and the owner) become a pipeline feature for projects? This file inventories what exists, names the gaps, and sets out the options with a recommendation. It decides nothing and changes no code.

## 2. Gap analysis: what a pipeline-level coordinator would need

| Need | What exists | Gap | Where it would live |
|---|---|---|---|
| **Ordering across changes** | Nothing: no field says one change waits for another (the code search for `depends_on`, `blocked_by`, `merge order` found none) | A change that must follow another has no way to say so; the owner holds the order in their head | A field in `status.yaml` or the intent (plugin `state/`, the intent template skill); the (c) dispatch waits on it (`run_phase.py`). A wait is close to R60's dropped serial queue, so it needs the owner's word |
| **File-overlap pairing** | Each `plan.md` lists its "Files that change" (`plugin/skills/plan-template/SKILL.md:18`); step 33's design reads it within one change | Nothing compares the lists of two open changes | A deterministic check in `plugin/state/` writing a line into R9 part 1's `changes/index.md`, the (b) and (e) PR bodies and R20's digest. No model needed |
| **Number and version allocation** | Change ids are reserved (A5). A project's other numbers are not the framework's | None for a project. In this repository: B4 is advisory, B5 and B6 fire only after a merge | Repository only: `tasks.py version-check` could read the fetched branches as `next-free` does, and fail a bump another open branch already holds |
| **Relaying the owner's answers** | The PR is the channel: the review request is the one notification (decision 31); the owner's acts are labels and reviews counted only from the owner's account (decision 24) | None that a coordinator may fill: a relay outside the PR is the rejected second channel (`docs/decisions/31.md:13`), and a relay by label is not the owner's act | Nowhere in the pipeline. In this repository it is the central session's `send_message` (B8) |
| **Merge order** | The owner merges, or the merge App on the owner's approving review (decisions 4, 36); A6 makes each merge safe on its own; the release re-check (A8) catches what moves after | No recommended order, and no withdrawal of the (e) offer on a later push (R51 check 8) | A line in the digest and in each (e) PR body ("merge #N first: it shares X"), from the overlap check above; R51 check 8 in `plugin/ci/`. The coordinator can only recommend |
| **Starting work in parallel** | Every change's phases dispatch themselves, unattended (A1, A4) | Nothing caps the number in flight or their total spend | R25 parts 3-4 (the weekly ceiling, the budget per change), already accepted for after the trial |
| **Context of one coordinator** | — | A long-running model session does not exist in a project's CI: each phase is one `claude -p` run in one job. Whether the claude.ai session tools (`create_session`, `send_message`, `create_trigger`) can be driven from GitHub Actions is not verified | A scheduled workflow (template) running one read-only session, like the digest |

**Where a clash costs the owner today.** Two open changes that edit the same file both run (b), (c) and (d) in full. The clash shows only at the second one's base update before gate (e): a conflict parks as `base_update` (`docs/OPERATING_MODEL.md:88`; `plugin/ci/base_update.py:80`), after the build and test spend, and it waits for the owner. So the price of a clash is paid in the owner's attention (weight 3), late, and once per clash.

## 3. Options

Two rules bound every option. "Wait sits at the owner's gates only: (c) and (d) never wait" (`docs/OPERATING_MODEL.md:77`), so a hold between changes is new behaviour. **Why O3 is not recommended even later.** Its five functions are already covered or not allowed. Starting the phases is the dispatch, which already runs every change unattended (A1, A4). Pairing and the merge order are deterministic (P1). Clashes no file list shows need judgment, and R28's manager is the actor the owner already accepted for judgment (P4). Relaying the owner's answers is not allowed: a second channel was rejected (decision 31), and only the owner's own act counts (decision 24). What is left is choosing the work, which R28 excluded. The worktree half of decision 17 stays with R50's trigger.

1. **P1 as a candidate of its own, placed with R9 part 1**, which it extends. It is the half of R51 that R51 left to R9 and R20 (`concurrent-changes.md:50-53`), and it moves the clash to gate (b), where the owner already looks.
