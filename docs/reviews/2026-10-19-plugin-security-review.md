# Security review of the framework's own plugin (2026-10-19)

The owner asked for a security review of this repository's plugin. The review applies the `sdlc:security-baseline` skill to the plugin itself rather than to a project. It reports only and fixes nothing.

## Scope and method

- **Baseline:** the `sdlc:security-baseline` skill, loaded through the Skill tool from the installed plugin 1.0.12. Its deterministic check (`check.py --root .`) printed "nothing found", which is expected: it reads the added lines of a diff, and this branch adds one document.
- **Contract read first:** `docs/OPERATING_MODEL.md`. Then `docs/proposals/sandbox-closes-gaps.md` (R44), so that its known gaps are not reported again as discoveries.
- **Code reviewed, at `main` 7960377:**
  - `plugin/hooks/`
  - `plugin/gate/`
  - `plugin/ci/`, the directory of the CI session runner, together with the parts of `plugin/pr/`, `plugin/state/`, `plugin/release/` and `plugin/evals/` that it calls
  - `plugin/detect/`
  - `plugin/scan/`
  - every `template/.github/workflows/sdlc-*.yml`
- **How the work was split:** three fresh-context sub-agents read the hooks, the runner, and gate/detect/scan, each in report-only mode. The workflows were read in the main session. Every finding kept below was then re-read in the code by the main session. Severities were re-judged against the settled decisions; one Important finding a sub-agent proposed is Minor here (M4) because decision 34 keeps that rule.
- **Reproduced locally:** two findings, in throwaway repositories in the session's scratchpad.
  - I2: a test that reuses the `tests/test_pr.py` fixture builds a PR body that contains a fixture `.env` through a symlink.
  - I3: `gate/diff.py committed_files` misses a rename source and a file turned into a symlink.
- **Nothing ran against GitHub.** No exploit was tried against a live repository or workflow. Everything else is traced in the code only. "Not verified live" marks the claims that depend on runner or platform behaviour.
- **Already recorded by R44, not repeated as findings:**
  - the sandbox's `denyWrite` is not proven on a runner;
  - there is no `policies` entry on `denyWrite`;
  - glob `protected_paths` entries are skipped, and bare names deny only the copy at the root;
  - the model credential is visible to sandboxed commands, and `~/.ssh` and `~/.aws/credentials` are not denied to them;
  - the build preflight's test target runs with the full environment;
  - the head's `commands.setup` runs before the guardrail park, and `framework/` is writable to it;
  - the workflow token sits in the session's environment (accepted);
  - a session can push a forged `refs/sdlc/released/<id>`;
  - an unsandboxed process can read the runner's environment through `/proc` (choice 227, left to R44).
- **One R44 statement is out of date.** R44 says the token sits in every checkout's `.git/config`. Every checkout in the 13 workflow templates now sets `persist-credentials: false`, and git takes its credential through the environment (`ci/app_token.py git_auth_env`, R49).

## Important findings, traced

### I1. The eval workflow runs the head's code with the model credentials, unsandboxed

1. **Entry.** In phase (e) of an incident fix, `/sdlc-deploy` tells the session to create `evals/cases/<id>-<slug>/` with `plugin/evals/case.py new` and to complete its checks (`plugin/commands/sdlc-deploy.md:94-96`). The session can write anything under `evals/`, including `evals/check.py` and the `command:` lines of `checks.yaml`. Neither is a guardrail path: `ALWAYS_PROTECTED` is `.claude/**`, `CLAUDE.md`, `REVIEW.md` and `sdlc.yaml` (`plugin/hooks/protected_paths.py:46`), and `template/sdlc.yaml:156` ships `protected_paths: []`. The session may be steered by text it read: the incident's logs, or a review comment (M4).
2. **Trigger.** The runner pushes `sdlc/<id>/c`. With `vars.SDLC_APP_ID` set, the push is the App's, and its `pull_request` event starts workflows (decision 33). `sdlc-evals.yml` fires on a pull request to the default branch whose paths include `evals/**` (`sdlc-evals.yml:30-35`). Without the App, the next event that starts runs on that PR does the same: an owner's push, or a reopen.
3. **Execution.** The job checks out the event's ref, which is the PR's merge ref and so carries the head. It then runs `python evals/check.py --framework framework ...` with `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` (`sdlc-evals.yml:91-93`). That file is the head's own. Even with an untouched `check.py`, `plugin/evals/run.py` runs each case's `command` check through `run_commands` → `run_bounded(..., env=None)` (`run.py:343`, `:370-388`, `:578`), which inherits both credentials. It runs outside Claude Code's sandbox and with no network allow-list.
4. **Effect.** Code the session wrote reads the model credentials and sends them to any host. Inside its session, the same code met an allow-list (R44's known gap is visibility inside the sandbox). Here there is none, and R44's proposed `sandbox.credentials` would not reach this job.

### I2. A symlink in `evidence/` publishes any runner-readable file in the PR body

1. **Entry.** The phase session holds `Write` and `Bash(python *)`. Inside the sandbox, `python -c "import os; os.symlink('../../../.env', 'changes/0001-x/evidence/claude-md-proposals.md')"` creates the link. Creating a link does not read its target, so `Read(.env*)` and the sandbox's read deny are not involved. The change folder is not protected.
2. **Read.** After the session, the runner calls `pr/cli.py upsert` through `_cli_call` with `env=None`, that is the runner's own environment, outside the sandbox (`run_phase.py:5109-5114`, `:4957-4965`). It does so on the park path too (`:5027-5040`). `build_description` reads `evidence/claude-md-proposals.md` with `art.read_text`, which is `Path.read_text` and follows the link (`artifacts.py:324-328`, `description.py:708`), and quotes it line by line under "Proposed CLAUDE.md lines". At phase (e), `release-notes.md` is read the same way (`description.py:584`).
3. **Reproduced.** A test that reuses the `tests/test_pr.py` fixture wrote `FAKE_SECRET=...` into the fixture project's `.env`, linked `evidence/claude-md-proposals.md` to it, and called `desc.build_description(root, "0001", "e")`. The body contained the secret. The test was run from the scratchpad; no repository file changed.
4. **Effect.** The project's `.env*` and `secrets/**`, which the deny rules keep from the session, are published in the PR body. So is any other file the runner user can read: a token file a setup step wrote, or possibly `/proc/self/environ` of the `pr/cli.py` process, which holds the runner's environment (both model credentials and both tokens). Whether the GitHub API accepts that file's NUL separators in a body is not verified. On a public repository the body is public, and Actions log masking does not apply to it. The next phase's session also reads the body, which defeats the "never in the model's context" promise for `.env`.

### I3. The gate's diff misses renames' sources and type changes

1. **Entry.** With `Bash(git *)`, the session commits a change without touching a protected working-tree file:
   - `git update-index --add --cacheinfo 100644,<blob>,docs_CLAUDE.md`, then `git rm --cached CLAUDE.md`, then commit; or `git mv`;
   - or `git update-index --cacheinfo 120000,<blob>,sdlc.yaml`, which turns the file into a symlink in the commit.

   These calls write only `.git/`, so `denyWrite` on `CLAUDE.md` and `sdlc.yaml` does not apply. The shell guard models neither.
2. **Miss.** `committed_files` runs `git diff --name-only -z --diff-filter=ACMRD` (`diff.py:318`); `collect` (`:450`) and `check_test_lock` (`checks.py:1386-1396`) use the same filter. Status `T` is filtered out, and with git's default rename detection `--name-only` prints only the destination. Reproduced on git 2.43: a branch with `git mv CLAUDE.md docs_CLAUDE.md` and `sdlc.yaml` replaced by a symlink gives `committed_files = ['docs_CLAUDE.md']`, while `--name-status` shows `R100 CLAUDE.md docs_CLAUDE.md` and `T sdlc.yaml`.
3. **Effect.**
   - `check_guardrails` (`checks.py:694-740`) passes a branch that removes `CLAUDE.md`, `REVIEW.md` or a `.claude/` file by renaming it.
   - `gate.py:211` reads the approved `sdlc.yaml` only when the file is in `d.files`. For a working-tree symlink, the gate therefore loads the session's file, with its limits, risk list, `protected_paths` and `commands.*` (N4).
   - In a fix-type change, a locked test replaced by a symlink to a weaker copy passes `test_lock` and `ratchets`, which only handle D, R and C (`checks.py:1448`).
   - The runner's own guard (`run_phase.py:1015`, `--name-only` with no filter) sees the `T` entry but not a rename source, and misreads non-ASCII names (M9).
   - The owner's merge at (e) remains the last check, and GitHub's PR view does show a rename. But the deterministic net that R44 calls "the second net" does not hold.

### I4. The runner's post-session git calls run programs the session configured

1. **Entry.** The session holds unscoped `Write` (`settings.ci.json:20-35`; the scan prompt's `ALLOWED_TOOLS`, `scan/prompt.py:44`) and `Bash(git *)`. No permission rule, hook or `denyWrite` entry covers `.git/**` (M1). It can add to `.git/config` either `[filter "x"] clean = <program>` plus `* filter=x` in `.gitattributes`, or `commit.gpgSign = true` with `gpg.program = <program>`. The framework's own code assumes this write is possible: `gitops.runner_args`' docstring and `app_token.git_auth_env`'s both say "a session can plant ... in .git/config". Whether the sandbox's mandatory deny, or Claude Code's own protection of `.git/`, refuses it on a runner is not verified; eval case 0006's proof could check it.
2. **Execution.** After the session, the runner commits the run's record:
   - phase runs (build, design, test, fix): `_cli_call(state/cli.py commit-phase ...)` with `env=None` (`run_phase.py:3462-3466`, `:4957-4965`);
   - the failed-run path: `gitops.commit_files` directly (`run_phase.py:2503`);
   - the scan job: `scan/cli.py route` (`sdlc-scan.yml:128-136`).

   `commit_files` runs `git add -- <files>` and then `git commit` (`gitops.py:379`, `:401-410`). `runner_args` adds only `core.hooksPath=<empty>` and `core.fsmonitor=false` (`gitops.py:131-143`). `git add` runs the clean filter, and `git commit` runs the signing program. The gate/detect/scan reviewer reproduced the filter running, with `GITHUB_TOKEN` in its environment, under exactly those two `-c` options. `app_token._config_finding` lists the filter and `gpg.program` keys (`checkout_check.py:60-81`), but it only switches the push to the workflow token; it does not stop the git call.
3. **Effect.** The planted program runs outside the sandbox, with the runner's environment (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, the App token, the workflow token) and an open network. The deploy and detect jobs' second steps run `checkout_check.py`, which refuses these keys. The phase runners' own `commit-phase` and the scan job's `route` have no such check.

### I5. A pre-approved project runbook runs in the tree the diagnosis session edited

1. **Entry.** The phase (f) session in `sdlc-detect.yml` holds `Write` and `Bash(python *)` in the project checkout. It reads failed-run logs and finding text; a fork's `pull_request` runs count towards the failure rate the detection reads. It proposes a route; a project runbook whose `bands.yaml` authorisation is pre-approved (decision 26) needs no Go.
2. **Execution.** The `finish` step runs in the same checkout (`sdlc-detect.yml:224-233`), after the framework has been re-cloned and `checkout_check.py` has judged the git config only. `cmd_finish` → `_act` → `runbooks.run` → `project_runbook` (`detect/cli.py:1056`; `runbooks.py:800-824`, `:729-782`) runs the command with `cwd=root` and the full environment (`runbooks.py:757`). There is no `_dirty` check or `_switch_to` the default branch, which the built-in runbooks do. The step holds the App token, plus whatever production secrets the owner adds to it, as the template tells the owner to.
3. **Effect.** If the runbook's command executes any file in the checkout (`python scripts/rollback.py`, a module, a `package.json` script), the session's edit to that file runs with the production credentials. No human sees it first.

### I6. The App's private key is in reach of unsandboxed session-written code

1. **Entry.** Code the session wrote runs outside the sandbox in the same job as the App mint step:
   - the runner's commands step (decision 29: the targets run after the session), with `commands_env`, which strips variables only (`run_phase.py:2387-2395`);
   - `commands.setup` (`:591`, and the workflows' setup step);
   - in the scan job, `pip-audit`, which builds the project or resolves `requirements*.txt` the scan session can edit.
2. **Path.** Each of those workflows mints with `private-key: ${{ secrets.SDLC_APP_PRIVATE_KEY }}` in that job (`sdlc-build.yml:82-94` and the six others). On a GitHub-hosted runner the `runner` user has passwordless sudo, and the job's worker process holds all of the job's secrets in memory. Reading that memory is the publicly documented technique of the 2025 `tj-actions/changed-files` compromise. Not verified live here.
3. **Effect.** The long-lived App private key leaks, and with it the ability to mint installation tokens until the owner rotates it. Choice 227 records the `/proc` exposure of the hour-long tokens and the model key; R44's proposed fixes (`sandbox.credentials`, the setup step) reach neither the commands step's process nor a memory read.
