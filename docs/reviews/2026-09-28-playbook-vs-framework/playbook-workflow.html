The playbook's workflow, as the article describes it

How a project would run if it followed the article exactly: no adaptation, nothing added. Every step cites the PDF page it comes from; connector nodes such as "Closed" or a tier split carry no page. Where the article leaves a detail open, the diagrams leave it open too, and the list near the end names those gaps. The article's measurements ("How to measure it") are out of scope here.

A human decision (review, approval, triage, authorization) Claude's work, or a step a person runs with Claude A branch point (a tier, a confidence gate) Conditional, optional, or an example the article gives

How the loop comes to run itself

"First, you prompt each step by hand with the end state being a loop in which each accepted artifact fires the next gate. Human attention concentrates at the gates, reviewing what the agent flagged rather than starting each stage from scratch." (p.8)

Start

Each stage is prompted by hand. Stages 1 to 5 each need "a human to launch the initial steps" (p.42).

Then (the article's example)

A step is codified: the design pass becomes "an organization-level slash command" (p.13).

End state

The accepted artifact is the trigger, e.g. "a non-interactive job that fires on the merge" runs the design pass (p.13). Stage 6 runs headless (p.42).

The hand-offs, verbatim: "An accepted intent.md triggers the requirements and design pass, an approved spec.md triggers plan mode, a merged PR triggers the pipeline, and a breached control band in production writes the next intent.md and so the loop continues." (p.7)

Test has no stage-boundary gate of its own in the hand-prompted loop. The article replaces "QA gates at stage boundaries" with "continuous evals woven through implementation" (p.6); the feedback loop's evidence lands in the PR's check run, and the code owner reviewing the PR approves (p.29). Evals are "the AI-native equivalent of stage-gate QA" (p.29) and "give QA a gate" (p.31), but that gate is the pass rate on changes to the agent's configuration, not a gate on each product change (p.30-31). In a headless run an independent confidence gate sits between stages (p.42).

The PR review loop

Stage 5's first play. Claude both gives and receives reviews; human attention moves to "whether the change does what the plan intended and whether the risk is acceptable" (p.32).

Stage 6: the maintain loop

"A trigger invokes Claude with no person in the invocation path, and what it finds re-enters the pipeline as intent.md" (p.41-42). Three parts of Stage 6 feed it: closing the loop on a control band (the play), recurring codebase scans, and Claude on call with Claude Tag.

The article's examples: a CI test failure rate breach at 3σ, where "the agent quarantines the flaky test or opens a revert PR, and the review gate decides"; a post-deploy 5xx breach at 3σ with a deployment in the window, where "the agent triggers the existing rollback pipeline"; and a PR cycle time that trips a drift rule, where "the agent writes a report for engineering leadership" (p.45).

Headless mode between stages

How the loop runs without a person starting it (p.42). "People triage and review that work, and no longer have to start it" (p.42). The review and production gates still hold.

How a headless run is wired (p.43-44): "The trigger layer can be a scheduled workflow in GitHub or GitLab, a webhook from the existing monitoring stack, or a Cron Job inside the network." Claude runs stateless, "either as a non-interactive step on a CI runner or as an Agent SDK service in a sandboxed container". "The tier boundaries are enforced from version-controlled config, with permissions and managed settings denying production access."

Set up once or alongside the plays: the intent home is "a one-time task for the platform or engineering team", and a technical team member decides "who can write to it" (p.10); the intent template can be a skill "set up by a technical team member and signed off by a lead" (p.11); engineering leadership, with change management and compliance, "lists the human approval gates that must survive" (p.36); the platform engineer expresses each approval gate as a hook, with non-negotiable hooks in managed settings owned by the platform or IT admin (p.36).

What the article leaves open

The diagrams do not fill these gaps in.

  • Who presses merge. The intent's acceptance "is recorded as the merge" (p.11) and code PRs need a code owner's approval (p.33), but no role is named as the one who merges.
  • Whether human code review is universal. The stage table reserves human review "for regulated and critical code" (p.6); the PR review play says branch protection "still requires approval from a code owner" (p.33).
  • How an approved spec.md starts plan mode without a person. A headless run goes "through the requirements, plan, build test and review phases" (p.42), but only the design pass is described as a job that fires on a merge (p.13), and plan mode is started by the engineer (p.16).
  • Which tier writes the intent.md. At 2σ Claude is read-only (p.43), yet "the agent writes its diagnosis as intent.md" (p.44).
  • Whether a 3σ PR carries an intent.md, spec.md or plan.md, and whether the small PRs from scans and Claude Tag carry a spec.md or plan.md. For scans and Tag the article implies no intent.md: "a fix that fits in one PR goes through the review gate, and anything larger becomes an intent.md" (p.46); p.49 says the same for Claude Tag.
  • Which check the headless confidence gate uses at each stage, its thresholds, and which human it escalates to (p.42).
  • Whether the production-gate hook, which needs a named release manager for a release (p.41), exempts a rollback. At 3σ the agent triggers the pre-approved rollback itself (p.43, p.45), yet the Claude Tag example still asks "shall I run it?" and waits for "Go." (p.49).
  • Whether the product owner also corrects an idea-route intent.md before it is committed (p.9), when the idea route has the originator correct and commit it and the product owner pick it up afterwards (p.11).
  • Where the product owner's review before commit (p.9) and the service owner's triage (p.44), which the article applies to event-triggered intents, sit in a headless run whose stages are otherwise passed by a confidence gate (p.42).
  • Who triages scan findings and who reviews the suggested patch (p.47); the security lead organizes repositories "so ownership of findings is clear" (p.47) but no triage role is named. Who authorizes in a Claude Tag channel: "anyone in the channel" can guide and action the response (p.49), and no role is named.
