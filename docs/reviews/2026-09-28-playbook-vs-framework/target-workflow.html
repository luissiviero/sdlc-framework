The workflow as you want it to become

The third workflow beside the playbook's and the framework's. It draws only what docs/reviews/2026-09-28-playbook-vs-framework/target-design.md has discussed so far: AI roles that advise and one manager that reviews for you (T1), the interview (T2), the intent home (T3), the names (T4), how a project starts (T5), tickets that become intents (T6) and the reason a rejection keeps (T7). Steps the study has not reached yet are left out or marked "not discussed yet".

Nothing here is decided. Every entry is tentative until the whole study is done; then each confirmed entry becomes a proposal and a candidate row in docs/ROADMAP.md. The framework as it is today is on the framework page.

  • You stay the only approver. The manager prepares an act; you approve it from your own account (a label or an approving review); a deterministic workflow, not a model, checks that the approval came from you and carries the act out. sdlc-runbook.yml already works this way for sdlc:go, though it checks only that a person applied the label, not that it was you.
  • No new gates. Intent, design, deploy and maintain keep their gates, with build and test in the Full profile. sdlc.yaml keeps the risk list, protected paths and production settings, and the enforcement stays as today.
  • A risk-list hit still parks. The brief of the matching role comes before your sdlc:accept-risk.
  • Your own edits to the gates get a role's brief before you merge them. Your edits to CLAUDE.md, skills and sdlc.yaml, and the skill sign-off, are where the roles would help most; the details are not discussed yet.
  • The manager never touches the project. Its job is a reviewer's. The intent gate gains the most: today it has no reviewing agent, only deterministic checks.
  • Decisions this would reopen or amend: D4, D5, D13 and D24 for the manager acting in your name; D21 (who sits on the panel) and D11 (whether a missing brief parks); the one-owner premise has no decision of its own yet. The names change what D3, D10, D11, D13, D14, D18, D19, D25 and D26 call things, not what the framework does.
  • Separate verdicts, not separate gates. The spec and the plan each get a verdict inside the one design PR, so plan.md is still approved with the spec. You approve both or reject one; a rejection is a "Request changes" review whose comments /sdlc-fix applies, as today.
  • The go to build: a close look, not a second approval. When the adversarial reviewer classes the plan non-routine, or a risk-list item is hit (that still parks for your sdlc:accept-risk), the design PR opens with "Needs your close look" and the reasons. You decide in the same merge; a separate approval for a higher-risk plan was considered and not chosen, since you would wait on yourself. The banner needs no roles: the class and its reasons are already written for the gate and today only lower the iteration cap, so it can come before the roles do.
  • How a project starts (T5): added, nothing replaced. The whole loop from the first change stays the default. Optionally you leave the Claude credential (the repository secret GitHub needs to run Claude) out at first: every automatic phase job then ends "skipped", you run each phase's command yourself, and adding the credential later turns the automation on. The weekly scan fails until then. The change-0000 intent also lists what starts empty, so nothing about the first weeks is a surprise. No settled decision changes.
  • Tickets become intents (T6): added, nothing replaced. Tickets arrive as GitHub issues. Your label sdlc:intent on an issue starts a CI run that writes the intent and opens the intent PR, linked to the issue; you correct and merge it at the intent gate as today. Only your own label starts a run, and the issue text is read as data, never as instructions, since anyone can open an issue on a public repository. Alerts and /sdlc-intent by hand stay as they are; the repository stays the record and the issue holds the link (D9).
  • A rejection keeps its reason (T7): added, nothing replaced. Closing an intent PR still abandons the change (D25). Your last comment on it, if there is one, becomes the change's recorded reason instead of the fixed "pull request N closed without a merge"; with no comment the fixed text stays. Incidents keep today's rule.

The interview T2 · T3

The manager leads and the roles feed it. You explain the idea, show examples of what you want, and answer questions that build the intent.

Where you write it

From Claude Code with /sdlc-intent, or from claude.ai on a computer or a phone. The intent stays in changes/<id>-<slug>/ in the project repository. Either way it must arrive as a PR on its branch, never as a commit to main: a claude.ai connector acts as your account, which the ruleset lets bypass, so a direct commit would skip the intent gate. That the claude.ai route can do this is still to check.

The template and the examples

The plugin's intent template by default, overridable per project (to verify). A Product role reviews a change to it, and you approve. The template gains an Examples/References section; mock/ stays the slot for screens. When a change touches a screen, the interview asks for a mock or example screens, and spec.md names the mock or says "none"; a missing mock never blocks. A competitor's screens can be references, never what the build matches.

The prompts

One role card per role, independent of the model: mission, sources, what it must output and in which format. The manager builds each prompt from the card, the change's files and the project's sources. Per role only the model setting changes, and each role gets an eval that checks it stays in its lane (article p.22, step 4). Claude Code sub-agents run Claude models, so "which model" means a Claude model.

How the roles and the manager talk T1

A sub-agent hands back only its final message, and a CI runner is thrown away, so the roles and the manager talk through files, as the review panel already does. The roles keep no memory on purpose: each judges from the files alone.

A brief, never an approval. On the record a role writes "security brief", not "security lead: approved", so the ledger never reads stronger than what a model can give. Roles on a model bring back a second perspective, not a second accountability.

Still open

The roles and the manager T1

  • Which model each role runs on.
  • Which documentation each role reads: the five policy skills each say "no owner source yet".
  • How many roles after merging.
  • Whether a ruleset can let a workflow merge on your behalf, or a dedicated GitHub App is needed.
  • The approval check must confirm the signal came from you, not just from a person.
  • The record of a merge made on your behalf: the merge commit, your approval signal and the manager's recommendation in evidence/.
  • Whether a brief is advice only, or a missing or negative brief parks the change.
  • Cost: every role is one more run per change, and the dollar cap compares only the last session's cost today (issue #71).

The interview and the intent T2 · T3

  • A second interview before the plan (the article's plan mode interviews the engineer, p.15-16). Before the spec there is none: what the design pass cannot answer goes to its flagged concerns, which park for you.
  • Whether the roles read the examples.
  • Whether a project can override the intent template for /sdlc-intent; the gate's section check means an override could add a section but not drop or rename one.
  • How an intent written in claude.ai gets its change id and folder, which only plugin/state allocates.

The names T4

  • If your decisions take the article's role names, the AI role names (Product, Architect, …) are to be checked so they cannot be read as those people.
  • When to rename: every rename also reaches each project on the framework, and the next project, webapp-example, is the last point with only one project to migrate.

Starting a project T5

  • Whether the weekly scan should end "skipped" like the phase jobs when no credential exists, instead of failing (a code change).
  • The exact wording of the by-hand start (/sdlc-init §6, README) and of the "what starts empty" list.

Tickets T6

  • Whether a ticket intent gets the role-fed interview; a CI run cannot interview you, so its questions go to Open questions in the PR.
  • How the run is told the issue is untrusted input, and which tools it may use.
  • The label's name, judged with the other names (T4).

Rejections T7

  • Whether closing a PR of the later gates, which also abandons the change, keeps its reason the same way.
  • Which comments count: only yours, or any repository member's, as the incident rule reads today.
