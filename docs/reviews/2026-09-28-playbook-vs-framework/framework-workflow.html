How a project uses the SDLC plugin

What a project does once to connect, how one change travels from idea to production, and what happens when the owner does not simply merge. Drawn from the code (workflows, runner, gate, hooks); docs/OPERATING_MODEL.md is the contract, and the notes say where the two differ.

The owner's act on GitHub: merge, review, label, close, a setting A Claude run or a workflow step. Setup and (a) run in the owner's own Claude Code session; (b) onward run unattended as github-actions[bot] Full profile, a conditional path, or a label-triggered step

Beside this page: the article's workflow (Playbook SDLC Workflow) and the workflow as the owner wants the framework to become (Target SDLC Workflow, tentative).

  • An incident change ships through (b) to (e) like any other. Its (e) run is also told to write lessons/<yyyy-mm>-<slug>.md and one eval case under evals/cases/, which the next diagnosis and sdlc-evals.yml read. No gate checks that these files exist.
  • Full profile. OPERATING_MODEL.md asks for an approving review plus the label at (c) and (d). The code checks only that the label is on the build PR and that the workflow token did not apply it.
  • Merge the build PR only after sdlc:e-ready. The draft state is the only thing that stops an earlier merge. Since 0.3.1 an earlier merge releases nothing: a merge during (c) or (d) is skipped because the phase is not e, and one during (e) because the merged copy is not yet at phase e or has no gate (e) result yet; the running (e) job then opens a second build PR, whose merge releases. Each change releases once: after deploy.command exits 0, the release workflow's record job writes the release into status.yaml on sdlc/<id>/c and on refs/sdlc/released/<id>. The early merge still puts unreviewed code on the default branch.
  • Where OPERATING_MODEL.md says otherwise. It says an infrastructure failure parks (the code ends the job red) and lists a scan finding as an input of /sdlc:sdlc-maintain (the code files scan incidents without a diagnosis run).
  • Merging the 0000 PR also fires sdlc-design.yml. Since 0.3.1 the runner's guard skips change 0000, the installation, for every phase, so the run step skips it and the job ends green with or without the Claude secret, unless an earlier setup step fails.

When the owner does not just merge

A phase run in CI ends in one of three gate outcomes, or in a red job when the run itself fails. Nothing notifies the owner: ready and parked PRs wait in the review queue, the PR list filtered by sdlc:*-ready and sdlc:needs-human, summarised daily by sdlc-digest.yml in one issue, "SDLC review queue", pinned where GitHub allows.

  OWNP -- "sdlc:accept-risk, sdlc:reset-iterations<br/>or sdlc:unlock-tests: recorded, then a fix round" --> FIX
  OWNP -. "merge anyway" .-> STUCK["At (b) the build workflow skips a parked change;<br/>at (c) or (d) the release skips (phase is not e);<br/>at (e) the release prints the park reason<br/>and waits for sdlc:release-approved"]
  OWNR -- "close without merging" --> AB
  OWNP -- "close without merging" --> AB["sdlc-abandon.yml<br/>phase: abandoned, branches kept;<br/>an incident PR closed with a person's comment<br/>also opens a dismissal PR"]
  FIX --> G

Always parks, in both review modes: a risk-list hit, a guardrail file change, a run limit the gate reaches (iterations, panel calls, wall clock, budget), any failed deterministic check (tests, build, lint, evidence, plan sync, test lock and the rest), a gate commands step that could not run after the session, and, since 0.2.26, a session that wrote the owner-only fields of status.yaml. A pause (paused: true in sdlc.yaml) makes the next job skip instead. With review: deferred, the judgment items (flagged concerns, policy calls, escalations, review findings, verifier reports) go to a three-member review panel instead of parking, and the PR carries "Decisions taken for you (N)". A "Request changes" review with a comment on the line overturns one.

Inside one phase run

The steps of /sdlc:sdlc-design, /sdlc:sdlc-build and /sdlc:sdlc-test in a workflow job run by plugin/ci/run_phase.py. /sdlc:sdlc-deploy has the same shape, with the REVIEW.md pass as its fresh-context check. Run by hand, a command does Register through Surface behind its own preconditions and preflight, and its hand-over only reports the next command: nothing is dispatched, so the owner starts the next phase. Run by hand, the gate runs build, test and lint itself.

Hooks active in every session on the project: protected paths (guardrail files and the plugin itself), secrets check, plan sync on git commit on the build branch, formatter and linter on edit (ruff, Python files), the test-file lock for fix-type changes, the panel blindness hook (0.2.30: while the review panel writes its two blind verdicts, neither can read the other, and the advocate's model is recorded), and the production gate, which, when deploy.production is true, blocks a guarded deploy command until the owner's release approval exists.
