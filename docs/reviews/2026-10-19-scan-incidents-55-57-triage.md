## #55: the evals workflow runs on a plain `pull_request` trigger (change 0010, signature `992cb085c9e477eb`)

**The finding in one sentence.** Because `sdlc-evals.yml` runs on `pull_request` with only a paths filter, a fork's pull request that touches `CLAUDE.md`, `.claude/**` or `evals/**` runs its own copy of the workflow and of `commands.setup`, with `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` in the job and no network allow-list.

**Reachable today?**

- **The fork path, as stated: no.** GitHub passes no secret except a read-only `GITHUB_TOKEN` to a workflow that a fork's pull request triggers. On a private repository this is an opt-in setting that is off by default. On a public one it is never on, and a first-time contributor's run also waits for approval. So `${{ secrets.ANTHROPIC_API_KEY }}` and `${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}` (`sdlc-evals.yml:91-92`) are empty in a fork's run. This is GitHub's documented rule; I did not test it on the sample.
- **A same-repository head: yes, by my reading of the workflow. I did not reproduce it.** On a head in this repository the job runs the head's own code twice:
  1. `sdlc-evals.yml:85` runs `project_setup.py --root .` with no `--ref`. That reads `commands.setup` from the checkout's own `sdlc.yaml`, which is the head's copy (`plugin/ci/project_setup.py`, docstring lines 16-34). The step's `env:` holds no secret, but it can change files that the next step runs.
  2. `sdlc-evals.yml:93` runs `python evals/check.py`, which is the head's own file, with both model secrets in its environment. It runs outside Claude's sandbox and outside the allow-list. `evals/check.py` is not a protected path: `ALWAYS_PROTECTED` is `/.claude/**`, `/CLAUDE.md`, `/REVIEW.md` and `/sdlc.yaml` (`plugin/hooks/protected_paths.py:46`), and the sample's `protected_paths` is `[]` (`sdlc.yaml:65`). So a phase session can change `evals/check.py` without a park.

  Who can put such a head there: the owner, and the automation. A session's own push uses the workflow token and starts no workflow run. The sample has the GitHub App, though (`SDLC_APP_ID`, [NOTES §47](../notes/47.md) line 30, not verified by a run). The runner's later publications on the same head go out with the App's token, and since decision 33 those events do start the project's workflows. So a session that commits a change to `evals/check.py` would have the next App push run that file with both secrets. A session cannot change the workflow file itself. GitHub refuses a push that touches `.github/workflows/` from a token without the `workflows` permission: the workflow token never has it, and the sample's App has "Workflows: no access" (NOTES §47 line 30). That rule is documented by GitHub and not tried on the sample.
- **Exposure today.** It needs a session that writes hostile code into `evals/check.py`, for example a prompt-injected one. The model key it would carry out is already in that session's own environment (R44, "The model credential reaches every sandboxed command"). What this path adds is an exit to the open internet and the second credential.

**What R44 would change.** Point 5 closes the head's own setup command, here `sdlc-evals.yml:85`. Its recommendation (b) checks that `framework/` is clean and at the pin. Recommendation (c) runs the install inside the sandbox runtime. Recommendation (a), taking the token out of `.git/config`, is already met here: `persist-credentials: false` and `contents: read`. Point 3 (`sandbox.credentials`) hides the model credentials from commands inside a Claude session. It does not reach `evals/check.py`, which runs before any session and outside the sandbox.

**What would remain after R44.** Line 93 runs the head's `evals/check.py` with both model secrets, unsandboxed. R44 does not name that step. Closing it is a framework template change, outside this incident's sample-only patch. Two possible shapes, for the owner to weigh and not decided here: read `evals/check.py` from the default branch the way the pin step reads `sdlc_pin.py` (`sdlc-evals.yml:65`), or add `evals/check.py` to the template's `protected_paths` so that a session's change parks. A fork's run stays harmless either way.

**Why not merge now.** Merging the intent sends a fix change to apply `evidence/suggested-patch.diff`, which adds `if: … head.repo.full_name == github.repository`. That condition closes only the fork path, which GitHub already closes, and it leaves the same-repository path open. A build session also cannot push a change to `.github/workflows/` (see above), so the round would likely fail at the push. That is my reading and was not tried.

**Why not dismiss.** A real, narrower gap sits under the finding. A dismissal never expires, and its reason would tell every later scan to skip this meaning.

**Recommended verb: schedule.** Apply the label `schedule` to #55. The label takes no value, nothing runs, and the digest lists the PR (OPERATING_MODEL §4.2, `sdlc-digest.yml`). The weekly scan does not file the same signature twice while the change is open (`plugin/scan/route.py:141`, "already filed as change <id>"). The suggested point to revisit it is when R44's setup-command part ships with a fix for line 93. The owner then closes #55 with a comment that names the framework version that closed it.

**Comment to post with the label** (optional; it records why). If the owner later closes the PR without a newer comment, this one becomes the dismissal reason, so the closing comment below should be posted then.

> Scheduled, not fixed here. GitHub gives a fork's `pull_request` run no secrets, so the fork path this finding describes does not reach `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`, and the suggested `head.repo.full_name` condition would change nothing. ## #56: `sandbox.failIfUnavailable` is false (change 0011, signature `eda9f21137cf4079`)

**The finding in one sentence.** `failIfUnavailable: false` in the sample's `.claude/settings.json:41` lets a session run unsandboxed, without the network allow-list, wherever the OS sandbox cannot start.

**Reachable today?**

- **Phase runs in CI: no.** Every phase job passes the pinned framework's `plugin/ci/settings.ci.json` with `--settings` (`plugin/ci/run_phase.py:2131`). That file sets `enabled`, `failIfUnavailable: true` and `allowUnsandboxedCommands: false` (lines 39-42). The command line outranks the project's `.claude/settings.json` ([NOTES §4](../notes/4.md) line 41: managed > command line > local > project). The job also installs bubblewrap and socat first (`plugin/ci/runner_setup.py`, for example the sample's `sdlc-build.yml:155`). With the API key the run is `--bare` and reads no project settings at all.
- **The owner's Windows PC: yes, by design.** The sandbox does not run on native Windows. The template's `false` is the documented choice that lets Claude Code start there ([NOTES §5](../notes/5.md): `true` "would stop Claude Code from starting on the owner's PC"). The guard on that machine is the managed settings file and the plugin's hooks (decision 6 layer ii).
- **The project's evals job: only in theory today.** `plugin/evals/run.py` (docstring lines 25-36) runs each case with the project's settings in force and passes no `--settings`. The sample's `sdlc-evals.yml` has no `runner_setup.py` step. So on a runner without bubblewrap, an eval case's session would run unsandboxed under this `false`. The sample's `evals/cases/` holds only `.gitkeep`, so no case runs a session today. Whether `ubuntu-latest` ships bubblewrap is not verified.
- **The class.** It is filed as SSRF, but there is no server-side request built from untrusted input. It is a statement about sandbox posture.

**What R44 would change.** Nothing about this line. R44 keeps the CI posture (`failIfUnavailable: true` in `settings.ci.json`), proves the sandbox on the framework's own runner (`framework-evals.yml`, eval case 0006), and adds `sandbox.credentials` to the CI settings. None of that touches the project's `.claude/settings.json`.

**What would remain.** The project file stays `false` on purpose. The evals job's residual is real but separate from this finding: an eval case would run without the CI settings and without the runner setup. That is a candidate for the owner: a `runner_setup.py` step in the evals template, or the eval runner passing a CI settings copy. It is not decided here, and it does not argue for this patch. Flipping the project file to `true` would stop Claude Code from starting on the owner's PC and would leave the evals job's missing bubblewrap a hard failure instead of a fix.

**Why not merge.** The patch reverses a recorded design choice (NOTES §5). It also edits `.claude/settings.json`, a guardrail, so the runner would park the build branch unless the intent said `Framework change: yes` (OPERATING_MODEL §4.2, the pinned framework's guard).

**Recommended verb: dismiss** (post the comment, then close #56 without merging). Then merge the dismissal PR that `sdlc-abandon.yml` opens on `sdlc/0011/dismiss`. No band or schedule value applies: a scan finding has no band, and a scan dismissal has no `until`.

**Dismissal comment:**

> Dismissed: a deliberate setting, not a defect. `failIfUnavailable: false` in the project's `.claude/settings.json` is the framework template's documented choice (sdlc-framework NOTES §5): Claude Code's sandbox does not run on native Windows, where the owner works, and `true` would stop Claude Code from starting there. Every CI phase run passes the pinned framework's `plugin/ci/settings.ci.json` with `--settings`, which outranks this file and sets `failIfUnavailable: true` and `allowUnsandboxedCommands: false`, and the job installs bubblewrap first. It is not SSRF. Report it again only if the CI settings stop requiring the sandbox.

## #57: `Bash(git *)` gets around the guardrail `Edit` deny rules (change 0012, signature `d6f98f0dff40c7c4`)

**The finding in one sentence.** The sample's `.claude/settings.json` denies only the `Edit` tool on the guardrail files (lines 19-29) but allows `Bash(git *)` (line 32), so a session could rewrite `CLAUDE.md`, `.claude/**`, `REVIEW.md` or `sdlc.yaml` through git and defeat the rule that only the owner changes guardrails, in a reviewed PR.

**Reachable today?**

- **The commands it names: no.** The pinned plugin's PreToolUse hook `plugin/hooks/shell_guard.py` judges every Bash and PowerShell command. It denies `git checkout <ref> -- CLAUDE.md`, because `checkout` takes the paths after `--` as write targets (lines 712-720; `restore`, `rm`, `mv` and `apply` at 721-722). It denies `git show <ref>:sdlc.yaml > sdlc.yaml` through the redirection target. Its eval case `0002-security-authz-the-guardrail-self-protec` passed live on 2026-10-12 (R44, "today", NOTES §39). The scan did not see this layer: the hook lives in the plugin, and `framework/` is outside the review's scope (`plugin/scan/prompt.py:48-61`).
- **A git verb with no pathspec: yes, in the working tree.** The hook's docstring names it as out of reach (lines 43-46). Examples are `git reset --hard <ref>`, a merge, a cherry-pick or `git stash pop` that brings in a guardrail change. Such a change cannot reach `main` unreviewed:
  - In CI, the runner refuses to run a phase whose branch changed a guardrail and parks it (`run_phase.py:2916`, `guardrail_changes`).
  - The gate's `check_guardrails` (`plugin/gate/checks.py:694`) refuses the diff.
  - Only the owner can merge to `main` (decision 4's ruleset).
  - In CI the sandbox's `filesystem.denyWrite` also lists `.claude`, `framework`, `CLAUDE.md`, `REVIEW.md` and `sdlc.yaml` (`settings.ci.json:55-57`). That layer has not been proven on a runner (R44 point 1).
- **What the policy actually promises.** It promises that a guardrail change merges only through the owner's reviewed PR. That holds. What a session can do is change its own working copy, which the next check parks.

**What R44 would change.** Point 1 runs the sandbox proof on a runner (eval case 0006). That proof shows that a sandboxed shell write to a `denyWrite` entry is refused, which is the layer that catches a pathspec-less git verb in CI. Point 2's `denyWrite` list is already built (0.3.7); R44 adds the runner proof and, with R27, the `policies` entry.

**What would remain after R44.** Sessions outside CI have no `denyWrite`: the owner's Windows PC has no sandbox, and a cloud session runs on the project's own settings. There a pathspec-less git verb can still rewrite a guardrail in the working tree. The diff checks and the ruleset catch it, which is decision 6's design. Narrowing `Bash(git *)`, the intent's outcome, would edit `.claude/settings.json` (a guardrail, so the build would park) and would break the session's own commits and pushes.

**Why not schedule.** The literal claim is already closed, and the residual is tracked by R44 in the framework, not by a change on the sample. A scheduled incident would wait on a framework proof that this repository cannot ship. The alternative, if the owner prefers to keep it in sight until R44's proof passes, is `schedule`. The cost is one more open incident in the digest.

**Recommended verb: dismiss** (post the comment, then close #57 without merging). Then merge the dismissal PR on `sdlc/0012/dismiss`. No band or schedule value applies.

**Dismissal comment:**

> Dismissed: the guardrail policy is enforced by layers this review could not see, because it read only the project's settings. The pinned sdlc plugin's `shell_guard` hook denies a Bash or PowerShell command that names a guardrail file beside a write idiom: `git checkout <ref> -- CLAUDE.md`, `git restore`, `git rm`, `git mv`, `git apply`, and redirections such as `git show <ref>:sdlc.yaml > sdlc.yaml`. A git verb without a pathspec can change the working tree, but in CI the sandbox's `denyWrite` covers the guardrail files, the runner parks a phase whose branch changed one, the gate's guardrails check refuses the diff, and only the owner can merge to main. The CI sandbox proof is tracked upstream as sdlc-framework roadmap R44. `Bash(git *)` stays: sessions need it to commit and push. Report it again only if a guardrail change can reach main without the owner's merge.
