# ArtCraft and the framework compared (2026-10-13)

The owner found a project that seems to do what this repository does, with one difference: the framework is an untested prototype, and the ArtCraft "Crafting Apps" (github.com/storytold) are a product family that real users have hammered for two weeks. The owner's three questions: where are the gaps in the framework's process; which decisions were taken differently, and why; which of ArtCraft's decisions would be worth taking over the framework's. This record answers them. It compares ArtCraft's process, as its repositories show it, with the framework as the owner wants it: plugin 0.3.7 on `main` plus the 32 confirmed target entries of the playbook-versus-framework study (`2026-09-28-playbook-vs-framework/target-design.md`, T1 to T32). Everything here was read-only; nothing under `plugin/`, `template/`, `docs/decisions/` or a guardrail file changes, and nothing below is a decision until the owner takes it.

## 3. ArtCraft in one page

**What it is.** Eight clean-room reimplementations of Adobe and Avid desktop apps in Rust, started between 2026-09-30 and 2026-10-06, each at "alpha" or "pre-alpha", each a one-to-one parity target against a pinned installed build of the incumbent. Two maintainers (Brandon Thomas and BFlat) merge almost everything; a community of up to 282 author names per repo sends PRs; Claude Opus 5.5 is named co-author on 48% of all commits and about 76% of non-merge commits (`study-d-statistics.md` §5, §9). Thirteen days produced 12,867 commits and 5,574 merged PRs across the nine repos. PhotoCraft alone merged 1,850 PRs, peaking at 341 in one day and 90 in one hour.

**How a change is made.** The loop every `AGENTS.md` describes, and the history confirms:

| Step | What happens | Where it is written |
|---|---|---|
| Orient | read the rules file (it "wins" over the working file and over the task), the working file, `ROADMAP.md`, `docs/gaps.md` (the ranked work list), `docs/scorecard.md` ("its numbers are measured; prefer them to estimates"), the crate's README; maintainers also read the gitignored `plan/STATUS.md` | `photocraft AGENTS.md:7-22, 75-87`; `effectcraft AGENTS.md:3-4`; `filmcraft CLAUDE.md:5-9` |
| Pick | "take the highest-ranked entry that nobody is working on"; stability and crash reports outrank features | `photocraft docs/gaps.md:5-7`; `pdfcraft docs/gaps.md:139` |
| Plan | "Write down the acceptance test before writing code" | `filmcraft docs/agents.md:282` |
| Build | one agent per crate, its own worktree, build dir and control port; surgical edits to shared files; manifests written atomically | `photocraft AGENTS.md:117-121`; `lightcraft AGENTS.md:113` |
| Verify | `cargo xtask ci` (fmt, clippy with warnings as errors, tests, layering, asset licences, wasm) locally before every commit; for UI work drive the running app through the control channel, take a screenshot, "look at the PNG" | `filmcraft CLAUDE.md:21`; `photocraft AGENTS.md:67, 93-105` |
| Record | update the parity row, the gap entry, the roadmap and the ROADMAP log in the same change, with the date and a revision-history row; say whether each number is measured or estimated | `vectorcraft AGENTS.md:66`; `filmcraft docs/agents.md:322-332` |
| Decide alone | "Don't stop to ask"; ask a human only about licences, money, publishing or pushing, personal data, destructive git | `filmcraft docs/agents.md:301-307` |
| Done | a checklist the agent ticks itself: command registered, tests incl. undo and disabled, UI wired, automation ids, driven and screenshot reviewed, gates green, docs updated, committed with the task id | `filmcraft docs/agents.md:309-320` |
| Merge | a human merges in the web UI or locally; in lightcraft and effectcraft the agent's own credential merges contributor batches after running the gate on each; PRs the maintainer's own agent wrote are merged by the same maintainer (480 of 892 in vectorcraft) | `study-b-ci-review-release.md` §2 |
| Release | bump one version field, fast-forward `main` into `release`, a shared workflow builds signed packages into a draft release, a human publishes; a daily family-wide release train | `photocraft docs/releasing.md:3-39` |
| Learn | users file issues (about 1,230 on PhotoCraft in ten days); the parity numbers are revised down with the reason kept "for the record"; gaps are re-ranked | `photocraft docs/target-app-parity.md:25-29` |

**"Battle-tested" means tested by users, not by gates.** This matters for the comparison. Six of the eight apps run no test on a pull request at all: their workflows are release, packaging lint, FreeBSD and Windows ARM64 builds, and their own gap files say so ("none runs `cargo test` or `cargo xtask ci` on a pull request, so 243 PRs merged since 10-05 were gated by contributors' local runs", `filmcraft docs/gaps.md:95-97`; "`main` has no branch protection", `designcraft docs/gaps.md:100`). Only photocraft and pdfcraft have a PR gate. No repository documents a mandatory review, has a `CODEOWNERS` file or a review bot, and there is no `Reviewed-by` trailer in about 11,000 commits. Red `main` happens and is fixed forward ("Fix main: …", `photocraft 184c226a`). The product's robustness comes from the inner loop (the gate run locally, the never-crash lints, the fuzzers, the oracle corpora, the screenshots) and from the users, not from anything between "the agent says done" and "merged".

## 6. Why they differ

The differences in section 5 come from a handful of causes. Each one explains several rows.

| Cause | ArtCraft | The framework | Rows it explains |
|---|---|---|---|
| **What is being built** | eight products with an external reference: Photoshop's menu is the spec, its PSD composite is the oracle, its users are the testers | a process for any project, with no product of its own and no users yet; correctness means "the artifact matches what the owner approved" | 3, 7, 14, 17 |
| **Who is accountable** | two maintainers who read every merge, plus a community; the agent's output is one more contributor's PR | one owner who looks in once or twice a day and wants to hand over as much as possible (the crosswalk weights: attention 3, autonomy 3, safety 1) | 9, 11, 12, 20 |
| **Where the agents run** | on the maintainers' machines, with worktrees, 6 to 30 GB build dirs, the disk filled twice; the gate is local because the machine is | on GitHub-hosted runners under a sandbox, with the workflow token; nothing counts unless the runner saw it | 5, 6, 10 |
| **The stage and the stakes** | alpha software, free, no telemetry, forward-fix only; a regression costs a patch release the same day | a framework meant to run unattended on projects with a declared production, money movement on the risk list; a wrong merge costs trust in the whole loop | 11, 13, 19 |
| **Speed as the goal** | 142 merged PRs a day on one repo; everything that slows a merge was left out (review, PR CI, branch protection) and recorded as a gap | three changes through the pipeline on the framework itself in three weeks, each with 4 to 12 fix rounds and 50 to 85 USD of spend; everything that makes a merge safe was built first | 9, 10, 18 |
| **Privacy of the plan** | the plan, status and dev log are maintainer-local; the public docs are "the equivalent if you don't have it" | everything is in the repository; the repository is the record (decision 9) | 4, 15 |
| **Legal exposure** | the clean-room posture shapes what evidence may exist and how it is stored (target output gitignored, only aggregates committed) | none | 7, 17 |

Two things are the same underneath and worth saying plainly. Both projects put the rules in files the agent reads first and treat tests as the gate. Both require the reproducing test before the fix and refuse a weakened test. Both write down, for the next session, what landed and what is open. The divergence is where judgment sits: ArtCraft lets the author agent certify its own work and relies on a human merge and on users; the framework never lets the writer judge and relies on fresh contexts, deterministic checks and one owner's approval. The earlier session's reading, "ArtCraft is fast because it has an external oracle", is half the story. ArtCraft is fast because it has an oracle *and* because it removed every gate between "done" and "merged"; its own gap files count the cost of the second half.
