**R44, the additions of choice 257.**
5. **I1:** the evals workflow starts `framework/plugin/evals/run.py` directly, never the checkout's `evals/check.py`; a case's `command` check runs with `run.check_env`, without either model credential or a token. On a runner each case's session gets `--settings` with `run.CI_EVAL_SETTINGS` (the sandbox on, `failIfUnavailable`, no unsandboxed commands, both credentials denied to shell commands; an inline JSON value is documented, NOTES §59), and the workflow prepares the runner's sandbox first.
6. **I4:** `state/gitops.refuse_planted_config` refuses every runner git call (`gitops.run`, `gate/diff._git`, the runner's own `git merge`) when the local or worktree config carries a key that runs a program (`checkout_check.RUNS_PROGRAM`: a filter driver, a signing, diff or merge program, an alias, a credential helper, `core.sshCommand`, a conditional include). The redirect keys stay `app_token`'s, which switches to the workflow token (R49), and `core.hooksPath` and `core.fsmonitor` stay `runner_args`' (a project's own husky install sets the first). `runner_args` also turns off the global attributes file, commit and tag signing and the external diff. The scan job removes the framework and checks it out afresh after the review session, then runs `checkout_check.py` before the route. Every runner git call, and `checkout_check.py`'s, also passes `--no-replace-objects`, and a `.git/info/grafts` file or a `protocol.*.allow` key is refused. git-lfs's own filter (`filter.lfs.*` with its `git-lfs` value, which `actions/checkout` writes with `lfs: true`) is allowed. `commit.gpgsign` is not added to the refused keys: `runner_args` sets it false on every call, and the eval runner sets it in its own scratch repositories.

It reads the lock from the working copy and from the `status.yaml` committed at HEAD, at the locked branch's tip and at `origin`'s copy of it, so the session must rewrite all of them to lift it. The review asked for the merge base: the lock is set on the branch itself, after the merge base, so the merge base never carries it.

## Known limits, recorded
- **The setup command still runs the head's manifests** in the fix and evals workflows. The framework is checked out afresh after it, but an install script can still change the Python or Node installation the next step uses (a `.pth` file in `site-packages`, a global npm package). Closing that needs the install in another job, I6's shape.
- **The `/proc` read of choice 227:** `sandbox.credentials` unsets the model credentials for sandboxed commands; an unsandboxed process (the setup command, the commands step) can still read the runner's environment. Choice 227 had left this to R44; R44's accepted points hold no mechanism for it, so it goes with I6. `docs/OPERATING_MODEL.md` carries a dated annotation beside that sentence.
- **A worktree shares `.git`:** the runbook's tree holds the approved files, but its git calls read the checkout's config, which `refuse_planted_config` judges. R3's fresh clone stays the full answer.
- **This repository's installed `sdlc-fix.yml`** keeps its setup line without `--command-from`, which the root pin (1.0.17) does not have, until the pin moves (R14's turn); the copy test says so.
- **The runner's other evidence reads and writes** (`read_gate`, the run records, `spend.json`, `status.yaml`) still follow a link; they parse JSON, and a write through a planted link lands where the runner user can write. The gate's `evidence_links` runs inside the session, which could forge its verdict (N1). Left for R3's clone, recorded.
- **This repository's own CI workflows** (`framework-checks.yml`, `framework-evals.yml`) still name actions by tag; R60's port covers the templates.
- **A runbook that relied on what `commands.setup` installed**, or on an unlisted variable (an OIDC-set `AWS_*`), now fails until its entry installs or lists it; `template/sdlc.yaml` says so, but an existing project gets no warning before its first run.
- **Not verified live:** that `sandbox.credentials` holds on the runner (Claude Code 2.1.304), and that the new `denyWrite` entries that do not exist in a project (`CLAUDE.local.md`) behave as `REVIEW.md` does.
