# Runner fix (2026-10-08, a one-fix session between sessions 21 and 22): the runner's push check takes the branch it prepared as the session's own, parks a session that ends elsewhere, and a dispatched fix round reads its head from the open pull request; plugin version to be decided by the owner (0.3.6, or riding with change 0003)

## Summary
- **The defect** (T29's last "Open" item in `docs/reviews/2026-09-28-playbook-vs-framework/target-design.md` on PR #127, found by the review of 2026-10-08): after each session `run_phase.py` called `session_push_mismatches(root, gitops_current_branch(root), …)`, so the branch it treated as the session's own was the one the session *ended on*, read after the session, not the one `prepare_branch` returned (`branch["branch"]`). A session that switched to another of the change's `sdlc/<id>/` branches (the next phase's), pushed it and stayed there was not parked by that check, and the next run's `prepare_branch` started from what it planted (the 0.2.26 review's M1 scenario, re-read). Reproduced in the container: the new M1 test on the old runner parked the session only because its planted owner fields tripped `verify_owner_fields` (`status.yaml: the session wrote owner-only field(s) …`); the switch and the push themselves went unseen, so a plant that is not an owner field (a gate record, evidence) would not have parked at all.
- **The fix** (`plugin/ci/run_phase.py`, PR #N): `session_push_mismatches` is told the prepared branch; a new `session_branch_mismatches` parks a session that ends on another branch than the runner prepared (names compared, never `prepare_branch`'s `switched` flag), under the same `owner_fields` park (exit 0, the owner-fields "what I need" block); before that park is committed `return_to_branch` puts the checkout back on the prepared branch — a plain checkout, then `checkout -f` when the session's uncommitted files stand in the way (they sit on the wrong branch, and the park says so) — and the result JSON records the move under `branch.returned`. The normal result JSON now carries `branch` too (the (f), review and final emits), so a live read shows which branch the runner prepared.
- **Verified before changing anything**: every phase command ends a normal run on the branch `prepare_branch` returns — `/sdlc-design` step 1 `sdlc/<id>/b`; `/sdlc-build` step 1, `/sdlc-test` step 0 and `/sdlc-deploy` step 0 `sdlc/<id>/c`; `/sdlc-maintain` step 0 `sdlc/<id>/a`; `/sdlc-fix` step 0 the pull request's head (`sdlc/<id>/a` or the web session's `claude/…` for phase a, `sdlc/<id>/a` for f, `sdlc/<id>/b` for b, `sdlc/<id>/c` for c, d, e); `state/cli.py commit-phase` commits on `conventions.work_branch` (`WORK_PHASE`: d and e on c, f on a) or on `--branch`; the runner's `work_branch_for` adds `review → e → c` and `fix_branch_for` mirrors the fix command's table; the review pass's prompt names the current branch and switches nowhere; a runbook "switches back to the branch it started on" (`detect/runbooks.py`) and in CI runs after the session anyway (`detect/cli.py finish`). `tests/test_ci.py::test_the_phase_commands_end_on_the_branch_the_runner_prepares` pins the step-0 texts to `work_branch_for`'s answers.
- **The exception, fixed upstream rather than exempted** (choice 167): `sdlc-fix.yml` dispatched by hand with no `head_ref` on an intent PR whose head is a `claude/…` branch. `fix_branch_for` answered `sdlc/<id>/a`, which exists nowhere; `prepare_branch` reported "the pull request's head is gone" without stopping; `collect_fix_requests` found no pull request for `sdlc/<id>/a` and parked the round on a runner before the session, while a by-hand run's session switched to the `claude/…` head as `/sdlc-fix` step 0 says — which the new branch check would have parked. Now `fix_branch_for` takes `repo` and `pr_number`, and when the phase's work branch exists neither locally nor on origin `dispatch_head` reads the head from the pull request `--pr-number` names (`pr_by_number`, `head_ref`) or from the open pull request of the branch the checkout is on (`find_open_pr`; a `workflow_dispatch` run from the pull request's head checks that head out, `github.ref`) — never the default branch, never a detached `HEAD`; no route or no pull request gives the old answer. Such a dispatch must therefore be run **from the pull request's head branch** ("Use workflow from"); from the default branch the checkout has no change folder and the guard skips the run ("no change folder for id"), as before.

## Choices made where the pack left it open (continuing session 21's numbering)
166. **The session's own branch is the one the runner prepared, compared by name, and the checkout goes back there before the park is committed.** `prepare_branch`'s `switched` flag is not the test: it is false on a run the session creates its own branch in, with the same name, and true for "already on the work branch". A session that ends elsewhere is parked under the owner-fields park with both the branch and the push reasons; before `park_and_publish` the checkout is returned to the prepared branch — plainly, else with `checkout -f`, dropping the session's uncommitted files, which sit on the wrong branch — so the park lands on the branch whose pull request the owner reads, where `commit-phase` would otherwise fail on the dirty tree. Not chosen: a separate park check and label for the branch (the owner-fields park already names a session that acted outside its mandate, and its "what I need" text fits); stashing the session's files (nothing reads them afterwards; the park says what happened).
167. **The dispatch exception is fixed where it starts, not exempted from the check.** An exemption for a "head gone" run would have left the round collecting requests for a pull request that does not exist (a park before the session on a runner) and would have reopened the hole for exactly that run. `fix_branch_for` now reads the head from the pull request when the phase's work branch exists nowhere: by `--pr-number` first, else the open pull request of the branch the checkout is on, never the default branch. Not chosen: listing the repository's open pull requests and matching their files to the change folder (a new paginated route in the runner before the live read; a dispatch from the pull request's head is a one-click rule instead); making `head_ref` required on the dispatch form (a template change, and the review-event rounds never need it).
