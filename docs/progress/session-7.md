## Choices made where the pack left it open (continuing session 6's numbering)
89. **Members' words only**: the workflow gate decides who *starts* a fix round (D9, 0.2.21); the run's own step 1 decides whose words reach it, by `author_association`, and lists the rest as not applied rather than silently dropping it.
90. **The Go job's setup command comes from the default branch; the phase jobs keep the head's.** The runbook workflow's Go step holds the runbook secrets and its head is the incident branch, so `commands.setup` is read from `refs/remotes/origin/<default>` there (choice 80's pattern), and because the command still runs in the head's tree (its `pyproject.toml`, `package.json` scripts), the step refuses a head that changed any file outside `changes/` relative to that ref — the incident head is the framework's own branch and only the change folder is written there. The phase workflows keep `project_setup.py --root .`: their heads are the framework's own branches created from the default branch and guarded by `run_phase.py`'s guardrail check, a fork's `pull_request` runs with a read-only token and no secrets, and a project may legitimately change its setup command on a `Framework change: yes` branch. Revisit only if a fork PR ever reaches a phase job.
91. **The init report says whether the metric can observe anything** (`maintain.observation`) instead of creating a CI workflow: the project's CI is project content the owner writes, and the report names the one-line workflow to add.
92. **The first real detection needs sixteen points, not eight days**: `MIN_BASELINE = 8` baseline points plus the `TAIL = 8` points the rules read, one point per UTC day *with* a counted run, and a day counts once it is over (choice 82). The brief's "eight complete days" was the tail alone.
93. **A NOTES section per session, dated**: environment facts (what a container can reach or run) go into a new section with their read date (§15) rather than growing §14, so a later session knows how old a fact is (R2's rule).
94. **A run by the workflow token's login is not an observation** (D12): GitHub records a `pull_request` run for a PR the workflow token opened or pushed to, never starts a job, and ends it as a failure; excluding by that one actor (`github-actions[bot]`) is deterministic from the listing alone. Not the project's `automation_identity` (a PAT or App identity there does start jobs, and its runs are real), and not every `[bot]` (Dependabot's runs are real test runs).
