## Choices made where the pack left it open (continuing session 10's numbering)
107. **The approval's record is `status.yaml: build_pr`, and the checkout must be the PR's own commit.** The brief assumed `upsert` already recorded a number; it did not, and `Status.from_dict` refuses unknown keys, so the field is new (default null: every existing `status.yaml` still loads). `upsert` writes it only for the work branch `sdlc/<id>/c` (the spec PR of (b) and the intent PR of (a)/(f) are not the build PR) and the runner commits it in its own commit after `ensure_pr`, so the branch and, after the merge, the default branch's copy carry it; by hand the working tree carries it until the next commit. The hook then reads the PR by that number and accepts it only while its head is this change's `sdlc/<id>/c` and the checkout's HEAD is the PR's own head commit (open or merged: the by-hand deploy runs on `sdlc/<id>/c` after the owner's merge) or its merge commit: a branch rebuilt locally with other commits, another change's PR number pasted into the file, and a closed-unmerged PR all refuse; what the check binds is the committed content, never the working tree (an untracked `dist/` is the session's, as it always was). Consequence: a change whose `status.yaml` predates 0.2.27 is not approved until an `upsert` records its PR — the next phase run does it; no change on the sample is at phase (c)–(e) today. The release workflow's path is unchanged but for one skip: an event PR that is not the recorded one.
108. **The detect snapshot is a step output, not a file.** A file the detect step wrote would live in the checkout the session edits; `$GITHUB_OUTPUT` lives in the runner. `run` prints the sha256 of `evidence/detection.json` after filing, the workflow passes it to `finish --detection-sha256`, and a mismatch parks the change (`DETECTION_SNAPSHOT_PARK_PREFIX`), commits and pushes the park, opens or refreshes the intent PR and exits red — the M5 pattern of 0.2.26 (`finish` never runs gate (f) over a park). By hand no digest is given and the record's word stands, as before; `proposal.json` is the session's own output and is judged by `validate_proposal` against the record and the approved bands, so it needs no snapshot.
109. **The framework is checked out again, not inspected, and the project checkout is judged from that fresh copy.** The first build of this item was a verify mode of the pin script, run by the pin line's own form between the two steps; the fresh-context Opus review of the diff defeated it four ways before the commit (H1–H3 below: a planted verifier on the local ref the line reads, `update-index --skip-worktree`, a moved tag, a planted `__pycache__`, and `url.<x>.insteadOf` redirecting its own fetch) and found it missing from this repository's own copy of the script (H4). The build that stands: a `python -c` line removes `framework/`, the runner's own `actions/checkout` clones it again at the pin from the step output, and `plugin/ci/checkout_check.py` — from that fresh copy, stdlib only — refuses a wrong `remote.origin.url` or fetch refspec, the config keys that redirect a fetch or run a command (`url.*.insteadOf`, `include`, `core.hooksPath`, `core.fsmonitor`, proxies, `pushurl`, `uploadpack`, credential helpers, aliases, signing and filter programs in the local config; the redirect keys only in the global config, whose other keys are the runner image's), a framework commit that is not what the framework's origin carries for the tag (`ls-remote`, the network as the truth), and a pin the default branch does not carry after a fetch by the repository's URL with the global and system config disabled; exit 3 ends the job red before the second step, the setup-step convention of 0.2.24. The same config denylist is read by `detect/cli.py origin_mismatch` on a runner before the approved copies are fetched. What it does not close, recorded: every git command in the second step still reads the project's local config, so a key the denylist does not name could run something (only a fresh clone of the project would close the class — ROADMAP, a candidate); the head's workflow file on a `pull_request` event stays GitHub's rule (choice 95). Not verified on a real runner yet: session 14's dispatched detect run, after the sample's upgrade PR, is the first live run with the three new steps.
110. **A rejected dismissal is read from the PR, not by deleting the branch.** The brief allowed either; reading `find_pr(state="all")` in `run` works for every project at its next detect run with no workflow upgrade, and the abandon workflow stays the single writer of the end state. Without a repository (a by-hand run) the branch's word stands, as before; an open PR, a merged one and a branch with no PR yet stay pending.
111. **A local runbook branch is reused only at origin's tip.** The by-hand second run of a runbook reuses its own branch (the existing tests); a local branch origin does not carry, or carries at another tip, is what a session could have planted and is refused by name. No remote and an existing local branch: refused too (nothing can vouch for it).
112. **The tag guard lives in the script and reads the event.** `GITHUB_REF_NAME` is what a `workflow_dispatch` was started from; the repository's default branch comes from the event too; by hand the checkout's branch and origin's `HEAD` symbolic ref decide, with `main` as the last resort (the script is the framework repository's own, not a template).
