## Choices made where the pack left it open (continuing the second sitting's numbering)
140. **The deferral is an environment variable the runner sets for the session, not a flag the model passes.** `SDLC_GATE_COMMANDS=runner` rides into the `claude` process with the credential (`credential_env` copies every other variable), the gate reads it once in `build_context`, and no command's prose changes: the model cannot forget it, a by-hand gate (no runner, no variable) runs the targets itself as before, and any other value of the variable means "run them here". The gate's own code runs the targets in the runner's process (`run-commands`), so one implementation judges them wherever they run.
141. **A deferred check is recorded `ok` with `details.deferred: true`, never as a failure.** Recording it as failed would make the session park, open the PR with "What I need from you" and report a park that the runner then lifts; recording it `ok` keeps the session's flow as designed, and the runner's upsert refreshes the PR from the final record minutes later. The reason says "not yet run" for anyone who reads the record in between; a runner whose step cannot run exits 1 rather than passing the mark on, so the next phase is never dispatched on targets that never ran.
142. **The step runs whatever the session's verdict was.** A record already parked on another check gets its real `commands` entry too, so the owner sees every red check at once; a green one leaves the session's `wait` or `continue` standing; the session's `at` and `head` are kept, the entry's `ran_by` says who ran the targets. A `panel_models` park after the step still overwrites the record in the gate's shape, as in 0.2.30.
143. **The runner waits `3 × gate.command_timeout + 300 s` for the step.** The gate's per-command timeout (900 s by default) fires first and the record names the target that hung; `_cli_call`'s 600 s default would have killed the step before a slow suite finished and reported an infrastructure failure instead.
144. **The stand-in sandbox is a `sitecustomize` module, not a `chmod` and not a cooperating target.** `chmod 000` is no denial for root (this container) and none on Windows (the suite's Windows job); a target that fails on request proves nothing about the order. The module denies `open()` of a `.env*` in every Python process of the session's tree and nowhere else, so the fixture's real suite fails inside the session the way it did live and is green outside it; the end-to-end test asserts the asymmetry first (the denial bites; the target is green outside) and the order second.
