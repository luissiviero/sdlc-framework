## Choices made where the pack left it open (continuing session 15's numbering)
145. **The release record lives on a ref and on the work branch, and the release reads it three ways.** The release job's checkout is the merge commit and the default branch is never written (decision 13). The record goes to `refs/sdlc/released/<id>` — no branch, so GitHub's auto-delete of head branches never removes it, no pull request comes from it and one `ls-remote` finds it — and, while the branch is still there, to `sdlc/<id>/c`, the only branch a later pull request of the same change comes from. The release reads the merged copy (a later PR from the branch carries the record), the ref, then the branch's own copy (the `labeled` event and a dispatch run on the same merge commit, whose copy never changes). The first draft kept the record on the branch alone and recorded the auto-delete gap; the review's finding 2 showed that gap to be the whole of 0.3.0's exposure on such a project, and the ref closes it without recreating a branch.
146. **The record is a second job's, with the only write token; a release that ran without its record is red; a record for a release that did not run is never written.** The review's finding 4: the release job runs the project's own `commands.setup` (third-party installs) and `deploy.command` with the job's token in its environment and in the checkout's `.git/config`, so `contents: write` there would let any dependency's install step or deploy script push. The `record` job needs `release`'s `released=true` output, checks out the project and the pinned framework, and runs the framework's record step and nothing else. Exit 1 on a push that fails, with the release's `done` line already in the first job's log, so the owner knows the command ran and the next event would run it again; nothing is recorded for `deploy.action: none`, an empty command or a failed command, so a failed release stays retriable by a dispatch and a project that releases nothing gets no commits on its branches. The remote read fails closed (finding 3): a failed `ls-remote`, `fetch` or `show` is exit 2, never a release on a read that did not happen; a checkout without `origin` reads as "no remote" so a by-hand run still works.
147. **Every park waits for the label (issue #68's first suggestion).** The second — a lift for park kinds the owner can accept by merging — would make the release decide which parks matter; the label is one more act the owner already knows, applied on GitHub, and `label_approval` refuses the automation identity's as before. The park reason is its own `release: parked:` line, so the summary shows what was accepted even after the label.
148. **#67's skip is the guard's, not the find step's.** The find-change step still resolves 0000 from the PR's files or the head, and the job ends green at the guard after the framework install (about a minute); one place judges the change for every route, the dispatched and by-hand ones included, and the reason names the issue.
149. **The spend ledger is a file keyed by the stored result, not a `status.yaml` field.** `evidence/spend.json` holds the entries (the review pass and each fix round their own, under the run's name as the workflow gives it — `review`, `fix` — not the `SPEND_PHASE` mapping that sends the review's figure to `run-e.json`) and their sum; a repeated record of one source replaces its entry, so a re-run step never counts a session twice; `run-<phase>.json` keeps the last session's figure as the run record and binds alone when no ledger exists, so a change recorded before 0.3.1 is judged as before, never on a total it never kept.

Step 41 keeps its OpenTelemetry half as "later" and gains the transcript half as "not built", so the step reads as what it is.
