## Choices made where the pack left it open
16. **Digest medium** (27a.0): one pinned issue titled "SDLC review queue" whose body the daily job rewrites; the owner sets the repository watch to "Participating and @mentions". The GitHub docs do not state whether body edits notify, so the design does not rely on it: the issue is opened by the workflow token and the owner never comments on it (NOTES §11a).
17. **Owner-only state** (24.5): `accept-risk` and `set-iterations` stay CLI commands; the gate's `owner_actions` check honours a risk acceptance or an iteration reset only when the commit that introduced it is not authored by the automation identity (`sdlc.yaml: automation_identity`, default `github-actions[bot]`), and parks on an uncommitted one. By-hand runs are the owner's own sessions, so their commits count as the owner's act.
18. **Sandbox for phase jobs** (30.7): the GitHub-hosted runner (ephemeral VM, only the CI credential) plus Claude Code's sandbox with `failIfUnavailable: true` and an allowed-domain list (`plugin/ci/settings.ci.json`, passed with `--settings` because bare mode reads no settings); `ci/runner_setup.py` installs bubblewrap and socat and the AppArmor profile when needed. `permissions:` per job: contents, pull-requests, issues, checks, actions — which endpoint needs which could not be verified from the reachable docs (NOTES §11a); the first live run verifies.
19. **Test-file lock semantics** (25.1): as the handoff proposed — `status.yaml: tests_locked` set by the build run after the reproducing test is committed; `sdlc.yaml: test_paths` with defaults per detected language; the lock holds on `sdlc/<id>/c` through (d) and (e); only the owner unlocks.
20. **Lite profile at (b)**: spec+plan are committed on `sdlc/<id>/b` (no PR) and `/sdlc-build` starts `sdlc/<id>/c` from that branch, so branch names keep one meaning.
21. **A park at (b) still opens the PR** with `sdlc:needs-human` and the "What I need from you" block: the queue is the PR list (OPERATING_MODEL §7), and the by-hand runs showed 6–9 open concerns per first spec, so the first (b) PR is usually a parked one whose work is closing concerns (article p.14 step 4).
22. **Verdict and gate ordering** in every phase run: commit the artifacts → the adversarial reviewer judges HEAD → the gate records → the evidence is committed. A later re-check sees a stale verdict by design; each run produces its own.
23. **Minimum Claude Code version 2.1.278** (the pinned CLI, `sdlc.yaml: plugin.claude_code`), since `--permission-prompts none` needs 2.1.259.
24. **Review in CI is its own `claude -p` job** (`run_phase.py --phase review`: the prompt from `review/cli.py prompt`, Read/Grep/Glob/git and one Write), then the (e) phase run finds the findings file for HEAD and validates it instead of delegating (decision 12's "writer ≠ judge").
25. **A park is a green job**: `run_phase.py` exits 0 on `park` (it is a queue item, not a CI failure) and 1 only on infrastructure failures (the CLI failing, no gate file after the run).
26. **`/sdlc-fix` never comments** (decision 20): a fix round records what it did per request in `evidence/fix-response.md`, committed with the evidence and visible in the PR diff; it posts no reply, review, assignment or @mention. Every round also calls `start-run` first, so the wall clock of the previous run does not park the round.
27. **CI refuses a phase on a branch that changed a guardrail file** (`run_phase.py` guard; decision 6 layer iii as prevention): `.claude/**`, `CLAUDE.md`, `REVIEW.md`, `sdlc.yaml` or a protected path differing from the base parks the change before `claude -p` starts, unless the merged intent says `Framework change: yes`. The residual exposure is documented in OPERATING_MODEL §4.2 and NOTES §11a: whether Claude Code honours a `hooks` or `env` block from an untrusted project checkout is not documented.
28. **A CI park is durable**: `run_phase.py` creates or switches to the phase's work branch before the guard, and a park commits `status.yaml` there, pushes and upserts the PR with `sdlc:needs-human`, so the queue item exists even on an ephemeral runner.
29. **Phase (b) in CI runs without Edit tools** (`--disallowedTools Edit,MultiEdit,NotebookEdit`); `Write` cannot be path-scoped (NOTES §6), so the `design_scope` gate check remains the net against a source file written in (b). The command's allow rule is `Write` (unscoped) for the same reason.
30. **A failed job is red, a park is green**: GitHub e-mails failed Actions runs by default; that is the one push left, and it signals an infrastructure failure, not a gate. The owner may turn it off in GitHub's notification settings. The digest's first run opens the pinned issue and may notify once.

## By-hand design runs (build guide step 22, the ladder's first rung)
Three Opus sub-agents ran the article's p.14 prompt verbatim on fixture copies (a percent helper, a remote exchange-rates module with an API token, a Node CLI with JSON output). Results: specs of 1009 / 1740 / 1741 words with the five sections in order and 6 / 6 / 9 open concerns each. The prompt in `/sdlc-design` (v1) differs from the article's because of them: it names the five sections; states the `[x]`/`closed`/`resolved`/`decided` convention and that the closing word must be the first word of the item (a `C3:` label keeps a concern open); demands every open question answered or carried forward with its source; turns assumptions into concerns; replaces "brand guidelines, security policies and UX standards" (three of five skills, and it calls the output "the plan") with "every organization skill, apply or say why not, cite the rule"; drops "ready to hand to the engineering team", which pulled files and order of work into the spec in all three runs; says read-only Read/Grep/Glob with a single write; and asks for `CLAUDE.md` and `sdlc.yaml` to be read and flagged when missing. Kept verbatim: "especially where you cannot satisfy contradicting policies" — it produced the real contradictions (coding standards versus UX wording in error messages; security's "validate against a schema" versus "no new dependency"). Skill effects: coding-standards and security-baseline load-bearing; ux-conventions found the true contradictions even for library changes but half of it assumes screens; data-conventions matters only when something is stored; definition-of-done shapes Acceptance. The intents lacked precision (rounding mode, exit codes, API shape): the intent template could ask for examples — noted for the owner, not changed.
