## Choices made where the pack left it open (continuing session 4's numbering)
66. **Runtime of the loop: a CI step** (37.4): the scheduled `sdlc-detect.yml`, not an Agent SDK service — the trigger table of §4.2 is workflows, no webhook source exists, and decision 7 forbids a runtime dependency. `workflow_dispatch(force_tier)` rehearses the whole loop on demand and is recorded as `forced` in the detection record.
67. **Observations and the window** (37.1, 37.2): one observation per UTC day = failed runs / counted runs (completed, `success` or `failure`, events push / pull_request / schedule / workflow_dispatch, workflows not named `SDLC …`; `source: github-actions:<workflow name>` narrows to one); `baseline: rolling_<N>d` is the window; the baseline never contains the points it judges: the last eight points of the window are the tail the rules read, the rest the baseline (mean, sample standard deviation); fewer than eight baseline points → tier 0 "insufficient baseline".
68. **The rules and their tiers** (37.1): the four classic Western Electric rules, each satisfied by a run ending at the latest point (an older breach inside the tail was reported by an earlier run): `we1` one point beyond 3σ → 3σ; `we2` two of three beyond 2σ → 2σ; `we4` eight points on one side of the mean → 2σ (a shift of the mean is the slow drift p.43 wants diagnosed); `we3` four of five beyond 1σ → 1σ (the early warning that only logs). Ties: the highest tier, then `we1`, `we2`, `we4`, `we3`. `direction: above` by default (a failure rate is worse when higher); `sigma == 0` makes any point above the mean an infinite breach — the article's own example (p.45: one bad day after a clean month) — and `min_sigma` is the owner's floor.
69. **One finding per metric at a time** (37.4, p.44 step 6): the detection skips filing while an incident of the metric is in flight (a remote `sdlc/<id>/a` with a detection record for the metric, not abandoned, and not at phase e on the default branch) or while its signature is dismissed; a finding is "the same" when the same metric trips the same rule (`detect|metric|rule`), a detection dismissal expires after one baseline window, a scan dismissal never.
70. **The proposal is the diagnosis's, the verdict the dispatcher's** (37.4, 37.5): the model writes `evidence/proposal.json` (route, args, rationale); `detect/cli.py dispatch` validates it against the tier and `bands.yaml`, resolves the authorization (the bands' value; a stricter `go` in `sdlc.yaml: maintain.runbooks` wins; decision 26 on top) and acts; a refused proposal is rewritten once by the run and then parks with the reason. At 2σ the only route is `pull_request`; the intent PR is the diagnosis's whole artifact (p.44 step 5).
71. **"Go" is a label** (37.4, decision 14): `sdlc:go` on the incident PR, read by `sdlc-runbook.yml`, performed once by `detect/cli.py go` when a person applied it (never the token or a `[bot]`), recorded as `status.yaml: runbook_authorized_by`, the label removed — the un-park labels' shape (decision 24). A comment is never a Go.
72. **The two shipped runbooks never touch a test and never merge** (37.4, p.45): `quarantine-flaky-test` adds `--deselect <node id>` to pytest's `addopts` (`pytest.ini`, `pyproject.toml`, `tox.ini`, `setup.cfg`, in pytest's order; created when none exists) on `sdlc/<id>/quarantine` and opens the PR (Python projects only; a Node project gets "unsupported" and the intent PR alone); `revert-pr` reverts one commit of the default branch (`-m 1` for a merge) on `sdlc/<id>/revert-<sha7>` and opens the PR; both idempotent; a project's own runbook is a `command` under `maintain.runbooks`, run without a shell like `deploy.command`.
73. **An incident change stays at phase f until its intent PR is merged** (39.1): the maintain run leaves `status.yaml: phase: f` on `sdlc/<id>/a`; the design workflow's guard accepts `f` as the phase before (b) (`PHASE_BEFORE`), so the owner's merge is gate (a) of that change (decision 25) with no write to the default branch; `read_status(on_default_branch=True)` needs nothing new. The PR title is `maintain(<id>): …`, the gate label `sdlc:f-ready`, plus `incident`.
74. **Every security finding is an incident intent** (38.1, decision 16): a bounded finding becomes a `change_type: fix` intent whose Proposed outcome is the patch, with the reviewer's suggested diff in `evidence/suggested-patch.diff` for the build run; a wide one a `feature` intent describing the class; at most three per weekly run; no route skips gates (a) and (b). The vulnerability-class eval (p.47 step 7) is the incident's eval of step 36. The scanners (`pip-audit`, `bandit`; `npm audit`) run in the same workflow, reported as artifacts, never a gate: the owner reads them; a finding worth a change is filed by the review.
75. **The eval runner is the framework's own** (35.1, 35.2): `claude plugin eval` loads only the plugin in a throwaway workspace, has no custom-code graders, puts a repository into a run only through a Bash scaffold script, doubles the cost with its baseline arm and can be switched off server-side (NOTES §13a); the framework's per-project suite tests the project's `CLAUDE.md`, hooks and settings (so the runner never passes `--bare`) with checks that are commands and file states. Cases are `prompt.md` + `checks.yaml`; the report is JSON; the pass rate is the job's verdict.
76. **Every hook logs every decision** (41.1): `run_hook` appends the line (a hook that crashes logs its fail-closed block too); the cost is one `git rev-parse` per hook call to find the change's evidence folder, inside every hook's time budget; the production gate keeps computing its own path (choice 39). The log is evidence, committed with the change, and an artifact of every phase run.
77. **The counters ride in the digest** (42.2): `pr/counters.py` over the change folders of the default-branch checkout; no report PR (the guide's "you merge or ignore" would be one more queue item), no model; the digest issue's last section.
78. **`evals/check.py` locates the framework** (35.3): `--framework`, `$SDLC_FRAMEWORK_DIR`, or `framework/` beside `evals/` (the CI checkout); a project runs its suite by hand with the framework checkout it pins.
79. **A bands change is a `bands.yaml` PR** (39.1, p.44 step 6 "Dismissals tune the bands"): the dismissal store mutes a metric + rule pair for one window; widening a band is the owner's edit of the file, reviewed like any project content; nothing in the loop writes `bands.yaml`.

## Choices made where the pack left it open (continuing session 3's numbering)
31. **What counts as release approval** (29.1): the label `sdlc:release-approved` on the build PR applied by a person — the actor of the last `labeled` event, read through the PR's timeline, never from an environment variable; a label applied by the automation identity or any `<app>[bot]` account never counts, and a removed label no longer counts. The handoff and build guide step 29 also offered "a signed tag on the merge commit"; the fresh-context review showed it is not owner-only (a session allowed `git *` can create a key or set the gpg config and `git tag -s` HEAD, and on the owner's PC the signing key is already configured), so the tag route was removed before the commit: the label is the one form, and the hook blocks any command that names the label (`gh pr edit --add-label`, the REST endpoint, a script) — decision 11, a run cannot approve itself. The hook only allows or blocks: the run is unattended, so "ask" would hang it; the block text carries the route.
32. **Both `closed` and `labeled` fire the release workflow** (32.3): the owner may apply the release label after merging, when the `closed` event has fired and found no approval (a green `waiting` job); the `labeled` event, filtered to `sdlc:release-approved`, re-runs the check. Whether GitHub fires `labeled` on a merged PR is not stated in the docs (NOTES §11a); the design is correct either way and a `workflow_dispatch(pr_number)` is the fallback.
33. **Release preparation in two halves** (32.1): the adapter's artifact (version bump, regenerated report, schedule entry, promotion record, manifest) is committed *before* the review pass, so the review and the gate judge HEAD with it — an artifact outside the change folder is listed in `plan.md` in the same commit or `commit-phase` refuses it; the release notes are evidence and are written *after* the gate into the evidence commit, because they quote the final findings tally and a second review pass per deploy run would double the (e) cost.
34. **A find step, not a head rule** (4(a)): every merged PR to the default branch starts the design and build workflows; the first step (`run_phase.py --find-change`, before any install, about 20 s) reads the PR's files and ends the job green when they touch no `changes/<id>-<slug>/` folder. A head that names another phase (`sdlc/<id>/b` merging into the design workflow) keeps its skip and is never looked up by its files, or the merge of a design PR would re-run the design.
35. **Deploy/status/rollback tools: not built now** (31.1). The plugin ships no runtime dependency, an MCP server would be one, and no project has a deploy target (this repository and the sample repository both say `deploy.action: none`). The interface is in OPERATING_MODEL §9 (three tools, every call through the production-gate hook, `rollback` pre-approved only under decision 26); `sdlc-release.yml` running `deploy.command` is the one deploy route until then.
36. **`deploy.command` runs without a shell**: one command, or steps joined by `&&`, globs expanded against the project root; `|`, `;`, `||` and redirections are refused as a configuration error (exit 2); a failing command is a red job (exit 1: infrastructure, not a park); the timeout is `gate.command_timeout`. GitHub environment protection stays the owner's: the template carries a commented `# environment: production` line.
37. **The adversarial reviewer without a shell** (6(e)): the sub-agents reference documents exact tool names and MCP patterns for `tools`, not permission-rule specifiers, so `Bash(git *)` cannot be given (NOTES §11c). The calling run writes `evidence/diff-<phase>.patch` (`--output=<file>`, one command, no redirection) and passes HEAD's sha; a brief without them makes the reviewer escalate; its "Proof" angle compares the committed evidence logs and `verifier.md` with the tests in the diff instead of running the toolchain (the verifier already did, p.27).
38. **The hook's time budget**: a PreToolUse command hook that reaches its timeout does not block the tool call (NOTES §8), so the production gate has a 60-second `timeout` and bounds each GitHub request and git call to 10 seconds with a 45-second deadline for the whole check; a timeout of its own is a block ("cannot verify the approval in time").
39. **The hook log lives with the change**: the default `changes/<id>-<slug>/evidence/hook-log.jsonl` when the branch names a change, because the gate's `clean_tree` parks on an untracked file outside the change folder and the evidence commit carries it; `changes/.hook-log.jsonl` is the fallback off a change branch; `SDLC_HOOK_LOG` overrides. Step 41's "kept with the change" is met; its "CI artifact" wording is B5's to reconcile when 41.1 extends the log to the other hooks.
40. **The release runs for the build PR only**: `release/cli.py` requires the merged PR's head to be `sdlc/<id>/c` (the branch the framework itself creates); a later owner PR that touches `changes/<id>-<slug>/` of a finished change (a `status.yaml` fix, say) is a skip, so a release never runs twice. Found by the fresh-context review.
41. **Gate (e) reads as passed on a declared production too**: the merge is the phase gate in every profile (decision 13: "merge is the whole gate"); the release approval is a release-level act the release workflow enforces, so `read_status(..., on_default_branch=True, production=True)` keeps `passed` and its reason names the second act. `status.yaml` does not track the release.

Found while building the production gate; no live run had hit it (both repositories have lower-case paths).
44. **The fix round runs on the PR's own head, whatever it is called** (5(a)): `run_phase.py --phase fix` takes the head from the event (`--head-ref`) and switches to it without creating anything; `commit-phase --branch <head>` and `upsert --head <head>` follow it, so an intent PR a web session pushed from `claude/…` is corrected on that branch and refreshed as the same PR. The gate file, the spend record, the run record and the hand-over use the change's own phase (`gate_phase`), never "fix": a fix round is the phase re-run, and a `continue` at (c) or (d) dispatches the next phase as the phase run would. A review by the workflow token or any `[bot]` starts nothing (the job's `if`), so the round cannot loop on itself.
45. **A label is one act**: the run performs the label, records the actor, and removes the label from the PR; the `labeled` event stays in the timeline as the audit line, `status.yaml` carries the actor. Without the removal every later run would reset the count again and the iteration cap would mean nothing. A label the automation identity or a `[bot]` applied is rejected and left where it is, so the owner sees it. `sdlc:accept-risk` accepts the hits the last gate of the change's phase reported (`evidence/gate-<phase>.json`, check `risk_list`, `details.hits`): the label carries no item name, and that file is what the owner read in "What I need from you"; with no recorded hit there is nothing to accept and the label stays. The PR upsert never removes the owner's labels (the release approval and the three verbs) when it sets the gate label — until 0.2.13 it swept every `sdlc:` label but the gate's, which would have removed a release approval applied before a fix round.
46. **`risk_accepted_by` is a list of `{item, actor}`**, not a mapping: a risk item may carry a space (`data migrations`) and `state/yamlish.py` supports no quoted keys.
47. **Abandon marks every branch of the change** (5(c)): the closed PR's head first, then every other `sdlc/<id>/*` branch the checkout knows from its remote-tracking refs or `ls-remote`, each with its own commit under the automation identity; a later `workflow_dispatch` of any phase switches to one of those branches before its guard reads `status.yaml`, so it skips. The branches stay: nothing is deleted, the owner may reopen by hand (a new intent is the documented route). Dismissing an incident finding on the close of an incident intent PR waits for step 39 (B5): nothing detects yet.
48. **The hosting rule reads the URL's host only**: `https://`, `ssh://` and scp-style `git@host:path` remotes name a host; a local path, a Windows drive path or a `file://` URL name none and pass with the note (the fixture tests, an owner's local mirror). `github.com` and `*.github.com` are GitHub. `--detect-only` is refused the same way: a detection report for a project the framework will not install on would mislead.
49. **`outdated`, not `kept`**: the installer cannot tell an owner's edit from an older framework's copy, so an existing workflow that differs from this version's template is reported as `outdated: differs from what plugin <version> installs; replace it ... or keep your edits` and the command shows those first. Replacing is the owner's act (delete the file and re-run `/sdlc-init`), never the installer's: a workflow is project content.
50. **The abandon step's reason has no `#`**: a `#` after a space starts a YAML comment even inside a `run:` scalar; `sdlc-abandon.yml` first lost the tail of its run line to it, and `tests/test_templates.py` now parses every workflow and compares the run line.
51. **The panel runs after the verdict and before the gate, and the verdict is re-run when a decision changed a file** (16a): the items come from a dry-run gate (`panel/cli.py items`), so an `escalate` verdict is an item; a concern the panel closes changes `spec.md`, the run commits it and the verdict is taken again for the new HEAD (a verdict never outlives the diff it judged). An `escalate` is keyed by its reasons, not by the head: the same reasons on the new HEAD are the item already decided, new reasons are a new item (bounded by the iteration cap, one per panel call).
52. **The three members are sub-agents by hand and in CI alike**: the phase run's session delegates the reviewer and the conciliator to general-purpose sub-agents and the devil's advocate to `sdlc:adversarial-reviewer` with a per-invocation model (`sdlc.yaml: panel_advocate_model`, default `opus`; NOTES §11c: the per-invocation model wins), instead of three separate `claude -p` jobs: the CI job already is one `claude -p` run with `Agent` allowed, the cost lands in the same `total_cost_usd`, and the brief, not the transport, is what makes the members blind. The cost per decision is recorded when the run knows it (`record --cost-usd`), else `n/a`.
53. **A panel decision is a concern closed with `decided (by panel): <decision> — <concern>`**: the closing word first, so the existing `open_concerns` check and `/sdlc-fix`'s rule ("the closing word is the first word") hold unchanged; the original text stays on the line so the owner reads what was decided about what; the `panel` gate check ties every such item to a ledger line.
54. **The ledger is JSON with a rendered `.md`**: the gate, the PR summary and `/sdlc-fix` read `decisions-<phase>.json`; `decisions-<phase>.md` is the same ledger for a person (one line per decision, the two verdicts in one clause each, the decision, the rationale, the cost, "OVERTURNED" when the owner reversed it). Both are evidence, committed with the phase.
55. **`lite` in an old file reads as `standard`** (`conventions.LEGACY_PROFILES`): the sample repository and this repository never used Lite, but a `status.yaml` written before 0.2.14 may say it, and a validation error on read would have parked every reader.
56. **`review` is a top-level key, per project, with a per-change override**: the decision's wording; `/sdlc-init --review`, `new-change --review-override`. Upgrading a project adds the key through the installer's usual text-edit path (`missing_top`), default `parked`.
57. **Panel calls are their own count** (decision 21 amended in 0.2.15, the owner's choice): `status.yaml: panel_calls`, `sdlc.yaml: gate.max_panel_calls` (default 4, whatever the classification), `limits` parks past it with the two ways out (the label, or the key in a reviewed PR), `gate/cli.py set-iterations --panel-calls N` by hand, `record_owner_label(sdlc:reset-iterations)` zeroes both. The alternative, keeping one count and raising `max_iterations_non_routine`, would have made one budget cover two unrelated things.
58. **`record` commits, the verdict comes last**: `panel/cli.py record` commits the change folder on the current branch (`gitops.commit_paths`, the automation identity when the checkout has none) right after applying the decision; the runbooks re-run the verdict once after the last item and say that nothing but the gate evidence is committed after it. Prose alone did not hold: the live run followed "commit, then re-run the verdict" by committing the verdict file with the content it had not judged.
59. **The closing names its ledger line**: `decided (by panel #n): <decision> — <concern>`; `ledger.panel_closings` reads `n` (the 0.2.14 form without it is still read and matched on the decision text), `check_panel` refuses a number the ledger lacks. Matching on the decision's words was one tidy away from a park.
60. **One transcript per run** (`claude-<phase>.json`, `claude-<phase>-2.json`, …; `run_phase.run_record_paths`): the runner stores a transcript after the run ends, so during a fix round the only committed one is the previous round's; overwriting it would lose the record and keeping one name misled the reviewer. Numbered names keep every run and say which is which.
61. **The runner's records are not proof** (adversarial-reviewer.md): `evidence/claude-*` and `run-*.json` describe the run that produced them, never the diff a later reviewer judges; the proof the reviewer compares is the toolchain output and the artifacts. The alternative — teaching the runner to store the transcript before the verdict — is impossible: the transcript is the run.
62. **A fix round is a phase run** (`sdlc-fix.md` step 5): under deferred review its judgment items, the reviewer's `escalate` included, go to the panel before its gate, with the same block as the phase runbooks; and its iteration-cap park runs `gate/cli.py check` (the `limits` check writes the gate file, the label and the block) rather than `state/cli.py park`, because the PR's label and body come from the gate file.
63. **The pin is read from the default branch** (`sdlc_pin.py --ref origin/<default>`, every workflow): a phase branch's `sdlc.yaml` is a snapshot, and a pull request may outlive several releases; the run's configuration already comes from the base branch's copy, so the framework version does too. The alternative — merging the default branch into the PR branch before each run — would put a merge commit into every round and still not help a by-hand run.
64. **A reset is recorded by its stamp** (`status.yaml: iterations_reset_at`, set by `record_owner_label`): the `owner_actions` check reads the commit that lowered the count for a recorded act, and a second reset by the same person changes the stamp only. Reading the label event from GitHub instead would need a token in the gate, which by-hand runs do not have.
65. **A closing is matched against the ledgers of every phase so far** (`ledger.phases_up_to`, `load_ledgers`; `check_panel`): `spec.md`'s concerns are closed at (b) and stay closed, so a gate at (c), (d) or (e) finds the line in `decisions-b.json`. Validation, the never-to-panel rule and the mode rule still apply to the phase's own ledger; `escalate` and `finding` entries stay per phase.
